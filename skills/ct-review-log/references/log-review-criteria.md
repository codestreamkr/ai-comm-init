# 로그 검토 기준

로그 수준은 문구의 강도가 아니라 사건의 결과, 운영 대응 필요성, 발생 빈도를 기준으로 정한다.

## 공통 판정 기준

### `trace`

일시적인 상세 추적에 필요한 저수준 정보를 기록한다.

- 메서드나 함수 내부의 세부 단계
- 반복 처리의 개별 항목
- 파싱 전후의 세부 상태

운영 환경에서 활성화될 때의 출력량과 민감정보를 확인한다.

### `debug`

개발과 장애 분석에 필요한 내부 상태를 기록한다.

- 분기 선택 결과
- 조회 조건과 처리 건수
- 캐시 적중 여부
- 정상 처리의 중간 상태

정상 호출마다 발생하고 운영 모니터링에 필요하지 않은 정보는 `debug`를 적용한다.

### `info`

운영 상태나 주요 업무 흐름을 보여 주는 사건을 기록한다.

- 애플리케이션과 배치의 시작·완료
- 주요 업무 상태 변경
- 운영자가 추적할 외부 연동 결과
- 요청 단위의 대표 처리 결과

동일한 사건은 책임 경계에서 한 번 기록한다.

### `warn`

처리는 계속되거나 복구됐지만 운영상 확인할 가치가 있는 상황을 기록한다.

- fallback 수행
- 임계치 접근
- 일부 데이터 누락
- 재시도 후 복구
- 이후 장애로 이어질 가능성이 있는 상태

예상 가능한 입력 오류는 발생 빈도와 운영 대응 필요성을 확인한 뒤 판정한다.

### `error`

현재 작업이 실패했고 운영 대응이나 원인 분석이 필요한 상황을 기록한다.

- 요청이나 배치의 최종 실패
- 복구되지 않은 외부 연동 실패
- 데이터 정합성 훼손
- 트랜잭션 실패
- 계속 처리할 수 없는 시스템 예외

상위 계층이 같은 예외를 stack trace와 함께 기록하면 하위 계층의 중복 로그는 제거한다.

### 기타 수준

프레임워크가 `fatal`, `critical`, `notice` 같은 수준을 제공하면 해당 런타임의 의미와 프로젝트 설정을 먼저 확인한다. 프로세스 지속 가능성과 즉시 대응 필요성을 기준으로 기존 수준에 대응시킨다.

## 언어와 프레임워크 판별

파일 확장자만으로 확정하지 말고 의존성과 호출 구문을 함께 확인한다.

| 생태계 | 대표 프레임워크 | 확인할 특성 |
|---|---|---|
| Java·Kotlin | SLF4J, Logback, Log4j2 | placeholder, Throwable 인자, level guard |
| JavaScript·TypeScript | console, Winston, Pino, NestJS Logger | Error 직렬화, structured object, child logger |
| Python | logging, Loguru, structlog | `logger.exception`, `exc_info`, lazy formatting |
| C#·.NET | ILogger, Serilog, NLog | message template, exception 인자, scope |
| Go | slog, Zap, Logrus | key-value field, error field, context logger |
| Rust | log, tracing | span, structured field, instrumentation |
| PHP | Monolog | context array, channel, Throwable context |
| Ruby | Logger | block evaluation, exception backtrace, tagged logging |

표에 없는 언어도 로거 API, 설정과 프로젝트 사용 패턴을 근거로 같은 절차를 적용한다.

## 예외 기록

예외 원인을 재구성할 수 있는 기록만 허용한다.

- stack trace가 필요한 실패에는 프레임워크 방식에 맞춰 예외 객체를 전달한다.
- 예외 메시지만 출력해 stack trace를 잃는 코드를 변경 대상으로 판정한다.
- 같은 예외는 최종 처리 책임이 있는 경계에서 한 번 기록한다.
- 재시도 과정과 최종 실패를 구분한다.
- 정상 응답으로 변환한 예외는 변환 결과와 운영 대응 필요성으로 수준을 정한다.

## 메시지와 구조화 필드

로그만으로 사건과 대상을 구분할 수 있게 작성한다.

- 수행 작업과 처리 결과
- 업무 식별자
- 외부 시스템명
- 오류 원인이나 상태 코드
- 처리 건수와 소요 시간
- correlation ID, trace ID와 span ID

프레임워크가 제공하는 placeholder, message template 또는 구조화 필드를 사용한다. 문자열 결합, 불필요한 직렬화와 검색하기 어려운 자유 형식 메시지는 변경 대상으로 판정한다.

## 민감정보

프로젝트가 승인한 식별 정보와 마스킹된 값만 운영 로그에 기록한다.

- 내부 업무 식별자
- 마스킹된 사용자 식별값
- correlation ID와 trace ID
- 외부 요청의 비민감 상태 코드

비밀번호, 인증 토큰, 세션, 쿠키, 카드 정보, 개인식별정보와 전체 요청·응답 본문은 프로젝트의 마스킹 기준을 적용한다.

## 책임 경계와 중복

같은 사건은 운영상 가장 의미 있는 경계에서 기록한다.

- HTTP 요청·응답: 필터, middleware, interceptor 또는 Controller 경계
- 업무 상태 변경: 상태를 확정하는 Service나 use case
- 외부 연동 실패: 재시도를 종료하고 결과를 확정하는 Client나 Service
- 저장 실패: 예외를 최종 처리하는 트랜잭션 경계
- 전역 예외: 전역 예외 처리기

여러 계층에서 같은 예외를 기록하면 사건과 업무 문맥이 가장 풍부한 한 곳을 유지한다.

## 성능과 로그량

호출 빈도와 데이터 크기를 함께 확인한다.

- 반복문 내부 로그의 최대 발생 건수
- 정상 요청마다 발생하는 `info`
- 대형 객체와 전체 컬렉션 출력
- 요청·응답 본문 직렬화
- 비동기 처리의 과도한 로그
- 로그 인자를 만들기 위한 추가 조회나 연산

비싼 인자 계산은 프레임워크의 지연 평가나 수준 활성화 확인을 적용한다.

## 판정 우선순위

다음 순서로 결과를 정리한다.

1. 민감정보 노출
2. 장애 원인과 stack trace 유실
3. 동일 예외와 사건의 중복 기록
4. 잘못된 `warn`, `error`와 이에 준하는 수준
5. 과도한 `info`와 대량 출력
6. 필요한 로그 누락
7. 메시지와 구조화 필드 개선
