# CT Plan

사용자 목표와 프로젝트 근거로 문제를 탐색한다. 실행할 수 있는 계획을 정리한다.

- 계획 문서 외의 파일과 외부 상태는 변경하지 않는다. `.debrief/` 기록은 예외다.
- 이 스킬은 구현과 검증을 실행하지 않는다. 승인 후 구현과 검증은 `ct-apply`가 맡는다.
- 진행 표시는 [ct-progress](../ct-progress/SKILL.md), `.debrief/` 기록은 [ct-journal](../ct-journal/SKILL.md) 지침을 따른다.

## 호출

- 요청 없이 호출하면 역할, 필요한 입력, 예제만 안내한다.
- 탐색 요청에는 근거, 선택지, 미결정 사항을 대화로 정리한다.
- 계획 요청에는 기존 계획과 자료를 확인한다. 그다음 계획을 쓰거나 갱신한다.
- 계획 요청을 받으면 `ct-progress` 지침으로 맵을 연다. 이번 실행에서 실제로 할 일을 단계로 보낸다. 예: 코드 분석, 선택지 비교, 계획 작성, 계획 승인(선택 포함)

예: `$ct-plan 주문 취소 기능의 구현 계획을 작성해줘`

## 수행

- [ct-analyze](../ct-analyze/SKILL.md)를 읽고 그 지침으로 요청 범위의 코드를 분석한다.
- 요청과 프로젝트를 조사한다. 확인한 사실, 해석, 미확인 사항을 구분한다.
- `.debrief/decisions/candidates.md`의 미확정 ADR 후보를 확인한다. 남은 후보는 모두 계획 범위에 넣는다.
- `.debrief/debt.md`의 이해 부채를 확인한다. 남은 항목은 모두 계획 범위에 넣는다.
- 계획에 넣은 ADR 후보와 이해 부채는 `ct-debrief`에서 처리하도록 표시한다.
- `.debrief/`가 있으면 [ct-journal](../ct-journal/SKILL.md)의 통계 명령으로 보강 대상 도메인을 확인한다.
- 수정 영역이 보강 대상 도메인에 속하면 그 영역의 설명을 보강한다: 동작 흐름, 핵심 코드 위치, 실패 처리
- 선택지마다 영향과 근거를 제시한다.
- 사용자 결정이 필요한 선택지는 따로 묻지 않는다. 모아 두었다가 "승인과 연쇄"의 일괄 질문에 넣는다.
- 선택지마다 이유를 보기 설명에 쓴다. 사용자가 고른 보기의 이유를 그 선택의 이유로 쓴다. 사용자가 이유를 직접 쓰면 그 말을 쓴다.
- 선택과 이유는 ADR 후보로 맵에 보낸다. 이유는 위 규칙으로 정한 이유를 쓴다.
- 계획에 다음 항목을 쓴다: 목표, 범위, 제외 범위
- 각 요구사항을 완료 조건, 작업 순서, 검증 방법에 연결한다.
- 필요하면 전환, 중단, 복구 조건도 쓴다.
- 계획 순서대로 전체 흐름을 검토한다. 흐름은 시작에서 구현, 검증, 완료 보고까지이다.
  - 각 단계의 입력, 선행 작업, 도구, 권한이 준비되어 있는지 확인한다.
  - 준비되지 않은 항목은 앞 단계에서 확보되는지 확인한다.
  - 빠진 연결과 예상 차단 지점을 계획에 반영한다.
- 계획은 작업 순서에 따라 논리적인 수정 영역으로 묶는다. 기능, 처리 흐름, 데이터 규칙의 변화를 기준으로 영역을 구분한다.
- 각 영역에 변경 목적, 대상 파일, 작업 내용, 변경 전후 동작을 표시한다.
- 같은 목적의 여러 파일은 한 묶음으로 나열한다. 설명은 한 번만 쓴다.
- 대상 파일은 프로젝트 조사로 확인한다.
- 아직 특정하지 못한 파일은 미확정으로 표시한다.
- 실행 단계에서 범위가 바뀌면 계획에도 반영한다.
- 실행을 막거나 결과를 바꾸는 미결정 사항은 모두 계획 단계에서 찾는다. 실행 중에 사용자에게 묻지 않도록 미리 확인한다.
- 실행 중에 판단할 수 있는 사항은 판단 기준과 후속 작업을 명시한다. `ct-apply`는 이 기준으로 묻지 않고 판단한다.
- 예상 실패에는 필요한 조건을 정한다: 재시도, 대안, 중단, 재개
- 계획을 변경하면 관련 요구사항, 작업, 검증 기준도 함께 맞춘다.

## 완료

- 탐색은 요청한 판단을 마치면 끝낸다.
- 계획은 다음 조건을 모두 충족하면 끝낸다. 임의의 개선 횟수로 종료하지 않는다.
  - 모든 확정 요구사항이 작업, 완료 조건, 검증 방법에 연결되었다.
  - 한 작업 턴에서 구현, 검증, 완료 보고까지 이어지는 경로를 확인했다.
  - 이 경로에 해결되지 않은 차단 요인이 없다.
- 계획은 요청한 위치에 저장한다. 위치가 없으면 프로젝트 관례를 따른다.
- 별도 파일이 필요 없는 요청에는 대화로 답한다.
- 계획 단계에서 작업을 완료로 표시하지 않는다.
- 계획 완료 보고는 계획 순서에 따라 수정 영역별 표로 정리한다. 표 열은 다음 순서를 따른다: 수정 영역, 변경 목적, 변경 전 → 변경 후, 대상 코드
- 대상 코드에는 확인한 파일 경로와 메서드나 함수명을 표시한다. 아직 특정하지 못한 대상은 미확정으로 표시한다.
- 결정 사항과 미결정 사항, 계획 위치, `ct-apply`의 실행 준비 여부는 표 아래에 짧게 설명한다.
- 설명을 보강한 수정 영역이 있으면 표 아래에 쓴다. 영역마다 도메인과 통계 근거를 붙인다: 첫 시도 정답, 남은 부채, 근거 실행
- 계획 문서가 있으면 상세 작업 순서와 완료 조건은 문서에 둔다. 대화 보고에서는 표의 내용을 반복하지 않는다.
- 해결되지 않은 차단 요인이 있으면 계획을 실행 준비 완료로 표시하지 않는다. 필요한 입력, 결정, 권한과 재개 지점을 남긴다.

## 승인과 연쇄

- 사용자가 멈추는 지점은 계획 승인 한 번이다. 이 지점에서 필요한 질문을 모두 한 번에 묻는다.
  - 사용자 결정이 필요한 선택지
  - `.debrief/`가 없을 때 저장소 성격(개인 또는 공유). [ct-journal](../ct-journal/SKILL.md)의 커밋 범위에 쓴다.
  - 계획 승인
- 일괄 질문 전에 맵의 승인 단계를 `wait`로 보낸다. 선택 질문 도구가 있으면 질문을 한 번의 호출에 모은다.
- 승인을 받으면 같은 작업 턴에서 [ct-apply](../ct-apply/SKILL.md)를 읽는다. 그 지침으로 계획을 실행한다.
- 보완 요청을 받으면 계획을 고친다. 그다음 승인을 다시 요청한다.
- 사용자가 계획만 요청했으면 승인 후 `ct-apply`로 이어가지 않는다.
- 승인 또는 중단 시점에 `ct-journal` 지침으로 실행 기록과 ADR 후보를 남긴다.
