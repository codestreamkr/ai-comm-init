# KCP에서 토스로 바꿀 때 체크리스트

## 목차

- 먼저 정리할 것
- 매핑 표준
- 코드 치환 순서
- 운영 전 확인

## 먼저 정리할 것

전환 작업을 시작하면 아래를 먼저 문서로 남긴다.

1. 현재 KCP 결제 수단 목록
2. 승인, 취소, 부분취소, 조회, 빌링, 가상계좌, 에스크로 사용 여부
3. 프론트 결제창과 서버 승인 API 분리 여부
4. 웹훅 또는 결과 통지 처리 방식
5. 내부 결제 상태 코드와 운영 에러 코드
6. 정산 배치나 후처리 작업 존재 여부

## 매핑 표준

아래 표를 기본 템플릿으로 사용한다.

| 구분 | KCP 현재 값 | 내부 의미 | Toss 대응값 | 코드 수정 위치 | 비고 |
|---|---|---|---|---|---|
| 승인 API | `/approval` | 결제 승인 | `confirm` | Gateway, Client | 프론트 승인 완료 이후 서버 확정 |
| 취소 API | `/cancel` | 전체 또는 부분 취소 | `cancel` | Gateway, Client | 부분취소 정책 확인 |
| 상태값 | `0000` 등 | 성공/실패 | `DONE`, `CANCELED`, `ABORTED` 등 | Translator | 벤더 상태를 내부 상태로 통합 |
| 오류코드 | KCP 오류 코드 | 운영 장애 식별 | Toss 오류 코드 | ErrorMapper | 내부 에러 체계 유지 |
| 웹훅 | KCP 통지 스펙 | 비동기 상태 반영 | Toss webhook event | Controller, Service | 서명 검증과 멱등성 필수 |

## 코드 치환 순서

1. KCP 전용 코드를 찾는다.
2. 내부 공통 포트를 먼저 세운다.
3. KCP 구현을 포트 뒤로 밀어 넣는다.
4. 같은 포트에 Toss 구현을 추가한다.
5. 상태 변환기와 오류 매퍼를 벤더별로 분리한다.
6. 웹훅 진입점을 벤더별 경로로 나눈다.
7. 기능 플래그나 설정값으로 전환 순서를 제어한다.

## 운영 전 확인

- 주문 생성 시점과 결제 승인 시점의 데이터 일관성이 유지되는가
- 부분취소 금액 계산이 기존 KCP 정책과 달라지지 않는가
- 웹훅 중복 수신 시 상태가 되감기지 않는가
- 실패 코드와 고객 노출 메시지 체계가 유지되는가
- 운영 배치, 정산, 관리자 화면이 새 상태값을 이해하는가
