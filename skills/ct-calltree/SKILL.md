# CT CallTree

현재 프로젝트의 코드와 규칙을 근거로 호출 흐름 작업을 수행한다.

## 호출

- `$ct-calltree` 또는 `$ct-calltree ?`: 지원 작업과 대표 예제를 간략히 안내한다. 분석 대상이 없으므로 작업은 실행하지 않는다.
- `$ct-calltree <작업> ?`: 해당 작업의 입력, 출력, 예제를 안내한다.
- `$ct-calltree <작업> <대상>`: 지정한 작업을 실행한다.
- `$ct-calltree <대상>`: 지원 작업을 한 줄로 안내하고 `<대상>`을 `analyze`로 처리한다.

첫 번째 인수가 `analyze`, `transition`, `test` 중 하나가 아니면 해당 인수를 분석 대상으로 해석한다. 이때 `작업 옵션이 없어 analyze로 처리합니다. 지원 옵션: analyze, transition, test`라고 알린 뒤 선택을 기다리지 않고 진행한다. 단, `--`로 시작하는 알 수 없는 값은 대상으로 해석하지 않고 지원하지 않는 옵션으로 안내한다.

## 작업

- `analyze`: 진입점부터 의미 있는 호출과 데이터 흐름을 읽기 전용으로 분석하고 기본 결과를 대화로 반환한다. 사용자가 문서 생성을 요청한 경우에는 호출 흐름 문서를 생성한다.
  - 예: `$ct-calltree analyze OrderController.cancel`
- `transition`: 현재 구조와 목표 구조를 비교해 전환 계획 문서를 생성한다. 분석 대상 운영 코드는 수정하지 않는다.
  - 예: `$ct-calltree transition OrderService.cancel`
- `test`: 호출 흐름과 운영 코드를 근거로 테스트 코드를 생성하거나 수정하고 검증한다. 사용자가 별도로 요청하지 않으면 운영 코드는 수정하지 않는다.
  - 예: `$ct-calltree test .docs/callTree-StMainViewController-storeMainBene.md`

`$ct-calltree <작업> <대상>` 호출은 선택한 작업의 위 기본 산출물을 만들라는 작업 요청으로 취급한다. 도움말 호출과 대상이 없는 호출은 파일 생성 또는 수정 권한으로 간주하지 않으며, 선택한 작업 밖으로 변경 범위를 확대하지 않는다.

## 자료 수집

작업에 필요한 범위만 프로젝트에서 확인한다.

- 적용되는 프로젝트 규칙 문서
- 빌드 파일, 소스 루트와 테스트 구조
- 대상 심볼의 선언, 호출자, 피호출자와 데이터 변경 지점
- 관련 설정, 예외 처리와 기존 테스트
- 동일한 역할을 하는 기존 문서와 코드 패턴

프로젝트에서 확인되지 않는 버전, 패키지, 경로와 정책은 가정하지 않고 확인 필요 항목으로 분리한다.

## 실행

1. 대상 심볼과 작업 범위를 확정한다.
2. 실제 코드에서 필요한 깊이까지 호출과 데이터 흐름을 추적한다.
3. 선택한 작업에 필요한 결과를 작성한다.
4. 기존 프로젝트의 빌드와 테스트 방법으로 가능한 검증을 수행한다.

## 호출 흐름 문서

호출 흐름 문서의 파일명은 `callTree-<진입점>-<대상>.md` 형식을 사용한다.

- `<진입점>`에는 호출 흐름을 시작하는 클래스, 화면 또는 주요 컴포넌트 이름을 사용한다.
- `<대상>`에는 분석이나 전환의 중심이 되는 메서드, 기능 또는 심볼 이름을 사용한다.
- 코드에서 확인한 대소문자를 유지하고 메서드 괄호와 매개변수는 제외한다.
- 파일명에 사용할 수 없는 문자는 `-`로 치환한다.
- 사용자 지정 파일명과 경로를 우선한다.
- 지정이 없으면 프로젝트의 기존 호출 흐름 문서 디렉터리를 사용하고, 찾지 못하면 `.docs`에 생성한다.
- 같은 이름의 문서가 있으면 현재 호출 흐름에 대한 문서인지 확인한 뒤 갱신한다. 다른 문서라면 덮어쓰지 않는다.

예: `callTree-StMainViewController-storeMainBene.md`

### 문서 구조

문서는 아래 섹션을 이 순서로 둔다. 해당 없는 섹션은 사유를 한 줄로 적고 남긴다.

| 섹션 | 내용 |
|---|---|
| `## 문서 정보` | 대상 클래스, 소스 경로, 필터, 포함 메서드, 작성 시각, 판정 기준, 포함·제외 범위 |
| `## 뷰 해석 경로` | view 이름이 실제 JSP로 해석되는 tiles 경로 |
| `## 흐름 요약` | 진입 메서드가 하는 일과 분기를 문단으로 |
| `## 메서드별 호출 트리` | `### 1. <메서드>` / `### 2. 뷰 렌더링` / `### 3. 화면 이후 서버 호출` |
| `## [TC:✅] 노드 요약` | 아래 노드 표 규격 |
| ``## `[TC:✅]`로 본 메서드`` | 노드별 판정 근거 |
| `## 비대상으로 둔 메서드` | 제외 사유 |
| `## 특이사항` | 추적 중 확인한 사실 |
| `## 검증` | 수행한 검증과 하지 않은 검증 |
| `## 확인이 필요한 항목` | 미확인 항목 |

`문서 정보`의 필터에는 메서드명을 적는다. URL 매핑은 별도 `매핑` 항목에 둔다.

### 트리 표기

호출 트리는 ```` ```text ```` 코드펜스 안에 아래 규칙으로 그린다.

- 글리프는 `├─`, `└─`, `│`를 쓴다. ASCII `|--`, `` `-- ``를 쓰지 않는다.
- 한 단계는 3칸이다. `├─ `, `└─ `, `│  `, `   `.
- 한 노드는 한 줄이다. 시그니처를 여러 줄로 접지 않는다.
- 노드는 `Class.method()`로 적는다. 패키지 경로와 매개변수는 제외한다.
- 판정 대상 노드 앞에 `[TC:✅]`와 `[Nxx]`를 붙인다.
- 부가 설명은 같은 줄 뒤에 두 칸 띄우고 괄호로 적는다.
- 한 줄이 105자를 넘으면 설명을 트리 밖 산문으로 내린다.
- 리시버는 필드명이 아니라 클래스명으로 적는다. `service.selectX()`가 아니라
  `PopupMngServiceImpl.selectX()`다.
- 메서드가 아닌 판정 단위(본문 인라인 계산, 조건 분기)는 클래스명 대신
  무엇인지 한글로 적고 `[Nxx]`만 붙인다. 노드 표에도 같은 문자열을 쓴다.

### `[TC:✅]` 판정과 노드 표

`[TC:✅]`는 메서드 본문 기준으로 판정한다. 분기, 조립, 계산, 외부 연동,
예외 처리가 있으면 대상이다. DAO 단순 조회, 단순 위임, getter/setter,
모델 세팅만 있는 호출은 비대상이다.

노드 요약 표는 아래 7컬럼으로 고정한다.

```text
| nodeId | callNode | layer | family | bundle | branchType | priority |
```

- `nodeId`: `N01`부터 트리 등장 순. 같은 메서드가 여러 경로에서 불리면
  경로마다 한 행을 둔다.
- `callNode`: 트리와 같은 `Class.method()` 표기
- `layer`: `controller` / `service` / `helper` / `external` / `utility`
- `family`, `bundle`: 문서 안에서 일관되면 자유 문자열
- `branchType`: `always` / `applicable/skip` / `conditional` /
  `normal/exception` / `normal/skip` / `normal/early-return`
- `priority`: `critical` / `high` / `normal`

### 계약 임의 확장 금지

이 문서가 정의하지 않은 필드나 계약을 문서에 만들지 않는다.
소비하는 도구가 실재할 때만 추가하고, 그 도구 이름과 경로를 근거로 적는다.

## 출력

- 분석 대상과 근거 경로
- 호출 흐름 또는 전환·테스트 결과
- 수행한 검증
- 확인이 필요한 항목

문서 형식은 `## 호출 흐름 문서`의 템플릿을 정본으로 한다.
사용자 지정이 있으면 그것을 우선한다. 기존 문서를 갱신할 때도 정본에 맞춘다.

## 완료 조건

- 대상과 호출 관계가 실제 코드에 근거한다.
- 호출 흐름 문서는 `callTree-<진입점>-<대상>.md` 파일명 규칙을 따른다.
- `transition`은 전환 계획 문서가 실제로 생성되어야 완료된다.
- `test`는 테스트 코드 생성 또는 수정과 가능한 범위의 검증이 완료되어야 한다.
- 선택한 작업의 결과가 요청 범위를 충족한다.
- 검증 결과와 미확인 항목이 구분된다.
- 호출 흐름 문서가 위 섹션 템플릿과 트리 표기 규칙을 따른다.
- `검증`에 수행한 검증과 하지 않은 검증이 모두 적혀 있다.
- `확인이 필요한 항목`이 비어 있지 않다. 없으면 "없음"을 명시한다.
