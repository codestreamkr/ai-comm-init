# 개발자용 기술문서 작성

개발자가 전체 동작과 기능 간 관계를 이해하고, 변경할 위치와 영향을 찾을 수 있는 기술문서를 작성하라.  

## 근거 확인

- 관련 문서와 코드·설정을 확인하라.  
  문서 범위의 진입점부터 주요 호출·분기·반환·설정 적용·데이터 변경을 추적하라.  
- 실제 구현과 외부 규격을 구분하라.  
  외부 규격은 적용 버전의 공식 자료로 확인하라.  
- 현재 동작과 개발 요구를 구분하라.  
  확인하지 못한 동작과 설계 의도를 사실로 단정하지 마라.  

## 내용 선택과 설명

- 생략하면 동작 이해나 변경 판단이 달라지는 정보만 본문에 포함하라.  
  개념·데이터·규칙·예외·제약에 모두 적용하라.  
- UI와 구현 세부사항도 같은 기준으로 선택하라.  
  화면 요소나 코드 항목의 단순 나열은 제외하라.  
- 지원 조건·허용값·수행 절차를 중심으로 설명하라.  
  금지·제외 조건은 생략하면 동작이나 변경 판단을 오해할 때만 남겨라.  
- 실제 소스 연결에 업무 의미를 함께 설명하라.  
  선행 조건·판단·처리·결과를 인과관계로 연결하라.  
- 분기는 경로별 조건과 결과를 구분하라.  
  경로가 다시 합류하는 지점과 합류 후 상태를 밝혀라.  
- 판단 이유는 확인한 근거와 연결해 설명하라.  
- 전체 흐름과 결과를 이해하는 데 필요한 분기·데이터 변경·실패 영향을 보존하라.  
- 값을 만드는 처리, 값을 바꾸는 처리, 결과를 확정하는 처리를 구분하라.  
  예: 금액 계산, 주문 준비, 결제 확정
- 외부 시스템으로 이어지는 처리는 호출 시점, 전달 값, 실패 시 상태를 설명하라.  
- 기존 문서를 개편할 때는 사실·조건·예외를 담당 섹션에 모아라.  
  중복 설명은 담당 섹션 링크로 대체하라.  
  각 절에는 앞뒤 흐름을 이해하는 데 필요한 최소 맥락을 남겨라.  
- 기존 문서에서 제거하는 문장과 절은 대상 문서 옆의 `<문서명>.삭제검토.md`로 옮겨라.  
  링크로 대체한 중복 설명도 옮겨라.  
  의미가 같은 문구 수정은 제외하라.  
  항목마다 기존 위치, 원문, 제외 사유를 적어라.  
  대체 링크가 있으면 적어라.  
  제외 사유는 유형에 맞게 적어라.  
  - 중복: 담당 절
  - 구현과 불일치: 코드·설정 근거
  - 선정 기준 미달: 생략해도 판단이 같은 이유
- 사용자가 삭제를 승인한 항목만 `<문서명>.삭제검토.md`에서 제거하라.  
  모든 항목이 승인되면 이 파일을 지워라.  

## 문서 구성

전체에서 상세로 이어지도록 구성하라.  
다음은 참고 순서이며 고정 목차가 아니다.  

1. 전체 구조와 흐름
   - 목적과 범위, 소스의 시작·종료 지점, 주요 호출·반환·설정 경로의 연결
2. 기능별 상세 동작
   - 역할과 선행 조건, 입력과 출처, 판단과 처리, 결과와 후속 영향, 관련 구현
3. 주요 항목과 관계
   - 동작 이해에 필요한 개념·데이터·규칙의 의미와 관계
4. 예외·제약과 변경 시 확인사항
   - 여러 기능에 걸친 실패 영향과 복구, 공통 제약, 변경 영향과 검증 기준

- 실행 흐름이 있는 문서는 상단에 진입부터 종료까지의 전체 흐름을 그려라.  
  그림 바로 아래에 주요 단계별 상세 섹션 링크를 번호 목록으로 제공하라.  
- 실행 흐름을 설명하는 절은 실제 실행 순서로 작성하라.  
  각 단계에서 주요 코드, 판단 조건, 처리 결과와 다음 단계를 설명하라.  
- 여러 흐름이 공유하는 규칙·설정·검증은 별도 섹션에 두고 필요한 단계에서 링크하라.  
- 개요는 파일별 역할과 연결을 요약하고 상세 절로 안내하라.  
  상세에는 입력·출력·처리 조건·실패 영향을 설명하라.  
- 관련 파일의 역할과 연결 상대, 수정·추가할 위치를 밝혀라.  
  적용 대상별 차이는 필요한 경우 별도 절에 모아라.  
- 기능별 설명은 해당 부분만 읽어도 역할·조건·처리·결과와 앞뒤 연결을 이해할 수 있게 작성하라.  
- 기능에 속한 내용은 해당 기능에서 설명하라.  
- 중복은 문구가 아니라 설명하는 사실·조건·결과와 적용 범위·데이터 원천을 기준으로 판단하라.
  이름이 같은 필드도 소속 객체나 원천이 다르면 구분하라.
  개요·상세·변경 안내·주의사항을 대조하고, 같은 내용은 가장 관련 있는 절에 모아라.
  요약에는 전체 흐름 파악에 필요한 단계·관계만 남겨라.  
- 관련 문서의 공통 설명은 담당 문서 한 곳에 모으고 해당 절로 링크하라.  
  각 문서에는 대상별 차이와 독립적인 이해에 필요한 최소 맥락을 남겨라.  
- 문서 목적에 따라 항목을 합치거나 생략하라.  
  모든 기능에 같은 하위 제목을 적용하지 마라.  
- 실행 안내가 목적이면 짧은 목적 설명 다음에 Quick Start를 배치하라.
  확인한 설치·실행 명령과 선행 조건, 예상 결과를 함께 제시하라.
  구조 분석 문서에는 Quick Start를 일괄 추가하지 마라.

## 표현과 가독성

- 제목은 기능·처리·판단 대상을 드러내도록 작성하라.  
  제목 계층으로 전체 흐름과 세부 설명을 구분하라.  
- 핵심 설명은 별도 `요약:` 표시 없이 절의 첫 문장으로 써라.  
  상세 조건과 구현 설명은 뒤에 배치하라.  
  인용문은 실제 인용에 사용하라.
  렌더러의 콜아웃 문법이 인용문을 요구하면 해당 문법을 허용하라.
- 문단마다 한 가지 주제를 설명하라.  
  조건과 예외는 관련 처리 가까이에 배치하라.  
- 같은 주제는 짧은 문단으로 묶어라.
  문장마다 강제 줄바꿈을 넣지 마라.
  문단과 블록 요소 사이에 빈 줄을 두어라.
- 단순한 처리 순서는 번호 목록으로 표현하라.
  조건 분기와 합류는 흐름도, 시스템 간 요청과 응답은 시퀀스 다이어그램으로 표현하라.
- 단계별 조건·동작을 설명하는 상세 절차는 번호 목록으로 표현하라.  
  병렬 항목은 정보량과 비교 목적에 따라 표나 글머리 목록을 선택하라.  
- 파일·역할처럼 같은 속성을 짧게 비교할 때는 표를 사용하라.  
  셀은 한 구절 이하, 열은 4개 이하로 제한하라.  
- 여러 문장·조건·절차가 필요한 항목은 목록으로 풀어라.  
  표가 넓어지거나 셀이 길어지면 관련 항목을 나눠라.  
- 단계·분기·관계가 글보다 명확해질 때 다이어그램이나 콜트리를 사용하라.  
  한 그림에 여러 기능의 세부 처리를 몰아넣지 마라.  
- 콜트리는 실제 호출 계층을 유지하라.  
  호출·반환·설정 경로가 뒤섞이면 분리하라.  
- 표현 형식은 가독성과 문서 렌더링 환경에 맞춰 선택하라.  
  텍스트 콜트리는 언어를 `text`로 지정하고 들여쓰기·연결선을 통일하라.  
- 요약·표·그림에도 결과를 바꾸는 조건과 분기 우선순위를 유지하라.  
  조건은 해당 단계에 표시하고, 복잡한 분기의 상세는 연결한 절에서 설명하라.  
- 핵심 결론과 중요한 제약만 굵게 강조하라.  
  식별자·설정 키·코드값은 인라인 코드로 구분하라.  
- 코드 예시는 필요한 부분만 언어 지정 코드 블록으로 제시하라.  
- 파일 표기는 파일명을 포함한 마지막 3개 경로 요소를 기본으로 사용하라.  
  표시 경로는 `/`로 시작하고 문서 전체에서 같은 형식을 유지하라.  
- 파일 경로가 3단계보다 짧으면 전체 경로를 표시하라.  
  같은 표시 경로가 생기면 구분에 필요한 상위 경로를 추가하라.  
- 링크 문구에는 표시 경로를 쓰고, 링크 대상에는 실제 파일을 가리키는 경로를 유지하라.  
- 파일 설명을 표로 구성하면 표시 경로를 첫 열에 배치하라.  
  목록으로 구성하면 표시 경로를 첫 줄에, 설명을 다음 줄에 배치하라.  
- 한 곳에 링크를 3개보다 많이 나열하지 마라.  
  넘는 링크는 관련 기능 절로 나눠라.  
  전체 흐름의 단계 링크와 목차는 제외한다.  
- 문서 분량과 탐색 필요에 따라 목차와 절 간 링크를 제공하라.  

## 시각적 구성

- 문서의 렌더링 환경과 지원 기능을 확인하라.
  지원 여부를 확인하지 못하면 기본 Markdown으로 작성하라.
- H1은 문서 제목, H2는 주요 주제, H3는 해당 주제의 세부 설명에 사용하라.
- 글꼴·크기·표시 여백·색상은 렌더러 설정으로 관리하라.
  기본 Markdown에 표시 스타일을 강제하는 HTML이나 CSS를 추가하지 마라.
- 렌더러 디자인을 요청받으면 제목·본문에는 Sans-serif, 코드에는 고정폭 글꼴을 사용하라.
  제목 크기와 굵기로 계층을 구분하고, 문단·제목 사이 여백으로 주제를 구분하라.
  기본 배경과 본문 색상에 포인트 색상 하나를 조합하라.
  의미 구분에 필요한 색상만 추가하라.
- 코드 구문 강조·복사 버튼·언어 표시는 렌더러의 지원 기능을 사용하라.
  코드 색상은 문서 테마를 따르게 하라.
- 렌더러 디자인을 요청받으면 인라인 코드에 본문과 구분되는 배경색과 글자색을 적용하라.
  라이트·다크 테마에서 글자를 읽을 수 있는 대비를 유지하라.
- 문서 사이트 레이아웃을 요청받으면 넓은 화면에 3단 구성을 우선 검토하라.
  좌측에는 전체 탐색, 중앙에는 본문, 우측에는 페이지 목차 또는 대응 코드를 배치하라.
  현재 탐색 위치를 표시하고, 좁은 화면에서는 보조 영역을 접거나 본문 흐름에 통합하라.
- Mermaid를 지원하면 문서 안에서 관리할 다이어그램에 우선 사용하라.
  코드 블록 언어는 `mermaid`로 지정하라.
  노드 식별자와 표시 문구를 구분하고, 렌더러가 지원하는 문법을 사용하라.
  지원하지 않으면 텍스트 도식으로 표현하라.
  다이어그램은 회색 계열을 기본으로 하고, 포인트 색상은 1~2개로 제한하라.
  테마 연동과 실제 렌더링 결과를 확인하라.
- HTTP 메서드·버전·지원 중단 상태는 지원 환경에서 배지로 표시하라.
  확인한 값만 사용하고, 색상과 함께 텍스트로 의미를 표시하라.
  지원 중단 일정과 대체 경로는 본문에 설명하라.
  배지 디자인을 요청받으면 둥근 모서리와 연한 배경을 사용하라.
  배지를 지원하지 않으면 인라인 코드나 짧은 텍스트로 표시하라.
- 콜아웃은 주의·팁·참고를 구분할 필요가 있을 때 사용하라.
  지원하지 않는 환경에서는 굵은 표제와 문단으로 표현하라.
  콜아웃 디자인을 요청받으면 연한 배경과 좌측 테두리로 유형을 구분하라.
- 긴 로그와 보충 자료는 지원 환경의 접기 영역에 배치하라.
  핵심 조건·필수 절차·실패 영향은 펼친 본문에 표시하라.
- 언어별 대체 예시는 지원 환경에서 탭으로 구성하라.
  순서대로 실행할 예시는 본문에 모두 표시하라.
  탭을 지원하지 않으면 언어별 제목과 코드 블록으로 구분하라.
- 기존 문서 배포 환경을 우선하라.
  문서 사이트 구축을 요청받을 때 문서화 도구를 선정하라.
  Mintlify·Starlight·Docusaurus는 후보로 검토하되, 배포·비용·MDX·버전 관리 요구에 따라 선택하라.
  API 명세 중심이면 Redoc도 검토하라.
  도입 전 필요한 기능과 적용 버전을 공식 자료로 확인하라.

## 완료 확인과 저장

- 사용자가 지정한 파일과 위치를 우선하라.  
  새 문서는 저장소의 문서 배치와 파일명 규칙을 따라라.  
- 초안을 Markdown 파일로 저장하라.  
  저장된 문서를 다시 열어 별도의 최종 검토를 수행하라.  
- 독자의 순서로 전체 흐름을 따라가라.  
  주요 단계 링크가 올바른 상세 섹션을 가리키는지 확인하라.  
  상세 섹션의 코드 순서와 분기 조건을 실제 구현과 대조하라.  
- 문서만 읽고 전체 흐름과 기능별 조건·처리·결과를 설명하고, 변경 위치와 영향을 찾을 수 있는지 확인하라.  
- 값·산식·상태·코드 위치와 그 의미를 근거와 대조하라.
  수정한 설명에 해당하는 항목을 확인하라.
  - 분기: 조건의 AND·OR와 우선순위, 경로별 결과, 종료·합류 지점.
  - 데이터 계약: 필드명·소속 객체·원천, 필수 여부, 기본값, 누락·null·빈 값의 차이.
  - 산식: 비교 대상, 집계 범위, 단위와 적용 조건.
  - 검증 안내: 테스트 대상·범위, 실행 조건과 외부 시스템·데이터에 미치는 영향.
- 각 절에 선정 기준을 다시 적용하라.  
  제목·목차·상세를 반복하는 도입·요약 문장은 본문에서 제외하라.  
  기존 문서의 문장은 `<문서명>.삭제검토.md`로 옮겨라.  
- 기존 문서를 개편했으면 변경 전후를 비교해 삭제·축약·이동한 내용을 확인하라.
  기존 내용이 본문에 남았는지, 다른 섹션이나 연결한 문서로 옮겨졌는지, `<문서명>.삭제검토.md`에 보존됐는지 확인하라.
  링크는 존재 여부와 함께 대상 절의 실제 설명을 확인하라.
  같은 대상을 다루는 개요·표·그림·상세와 관련 문서의 조건이 일치하는지 확인하라.
  소스 연결·파일 역할·수정 위치를 찾을 수 있는지도 확인하라.
  링크·항목 수나 형식 검사 통과만으로 의미 보존을 판단하지 마라.
- 파일 표기가 일관되고, 표·목록이 정보량에 맞는지 확인하라.  
  표의 셀·열 기준과 코드 블록의 가로 스크롤 여부도 확인하라.  
- 제목 계층과 문단 구분이 일관되는지 확인하라.
  다이어그램·콜아웃·탭·접기 영역이 대상 렌더러에서 표시되는지 확인하라.
  렌더링을 확인하지 못하면 미검증 사항으로 보고하라.
- 문제를 발견하면 수정하고 파일을 다시 저장하라.  
  다시 저장한 파일을 열어 수정한 절의 흐름과 링크를 확인하라.  
  `<문서명>.삭제검토.md`의 보존 상태도 확인하라.  
  마지막 저장본에 문제가 없을 때 결과를 보고하라.  
- 문서 경로와 사용자가 판단할 항목을 보고하라.  
  `<문서명>.삭제검토.md`를 만들었으면 링크를 포함하라.  
  필요한 미확인·미검증 사항은 짧게 밝혀라.
