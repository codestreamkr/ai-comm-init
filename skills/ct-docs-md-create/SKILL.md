# 개발자용 도메인 문서 생성

- 지정된 도메인을 빠르게 이해하고 구현·수정에 착수할 수 있는 `.md` 문서를 작성하라.
- 핵심 개념, 연관관계, 주요 상태와 실제 코드를 연결하라.

## 요청 범위

- 문서 생성 요청과 스킬 수정 요청을 구분하라. 스킬 수정 요청이면 스킬 파일만 수정하라.
- 도메인과 개발 목적을 기준으로 필요한 정보를 선택하라.
- 고정 목차를 채우거나 일반적인 배경 설명으로 분량을 늘리지 마라.
- 기존 문서의 형식·문체만 정리하는 작업은 `ct-docs-md-format`의 범위다.
- 다른 문서의 통합·재배치는 명시적인 요청이 있을 때만 수행하라.
- 문서에는 현재 상태만 써라. 변경 이력과 작성 경위를 쓰지 마라. 결정 이유는 `.debrief/decisions/`의 ADR이 담당한다.

## 근거 수집

- 기존 도메인 문서와 관련 코드·설정·스키마·테스트를 확인하라.
- 대표 진입점에서 호출 흐름과 상태 변경 지점을 따라가며 문서에 필요한 범위만 읽어라.
- 저장소 구현은 저장소의 근거로 설명하라. 외부 자료의 일반 동작을 해당 구현의 사실로 쓰지 마라.
- 기술 개념이나 외부 API는 해당 버전의 공식 문서를 우선 참고하라.
- 잘 만들어진 개발 문서는 설명 순서와 표현 방식의 참고로 활용하라.
  불필요한 목차나 내용을 그대로 가져오지 마라.
- 구현 근거가 없으면 일반 개발 가이드로 범위를 밝혀라. 예제임을 표시하라.
- 개발 방향을 바꾸는 정보가 부족하면 사용자에게 확인하라.
- 확인되지 않은 동작·상태·의도는 확정하지 마라. 필요한 미확인 사항만 짧게 표시하라.

## 내용 구성

- 다음 순서를 기본으로 삼아라. 도메인에 필요한 항목만 선택하고 합치거나 생략하라.
- 실제 소스를 확인한 개발 문서에서는 아래 소스 구조 형식을 필수로 적용하라.

| 구성 | 필요한 내용 | 표현 방식 |
| --- | --- | --- |
| 도메인 한눈에 보기 | 역할, 필수 용어, 구성 요소·데이터의 관계 | 짧은 설명, 관계표 또는 작은 Mermaid 관계도 |
| 주요 상태·전이 | 상태값과 의미, 가능한 작업, 전이 이벤트·조건, 금지된 전이와 실패 처리 | 상태표, 전이표 또는 작은 Mermaid 상태도 |
| 소스 구조 | 소스 위치와 역할, 실제 사례의 호출 순서와 상태 변화 | `## 소스 구조` 아래 디렉터리·파일·메서드 트리, 필요한 핵심 코드와 흐름 설명 |
| 개발 방법 | 기능 추가·수정 위치, 연결 방법, 적용 예제 | 작업과 파일·함수의 대응표, 최소 코드 예제 |
| 필수 규칙·검증 | 구현에 영향을 주는 제약·예외 조건, 실행 방법과 기대 결과 | 조건표, 짧은 규칙, 검증 명령 |
| 상세 참고 | 추가 명세, 관련 문서, 공식 자료 | 맥락을 붙인 링크 |

- 상태가 있는 도메인은 주요 상태와 전이를 정리하라. 대표 흐름 및 상태 변경 코드와 연결하라.
  상태 코드만 나열하지 마라. 상태가 없는 도메인에는 상태 항목을 만들지 마라.
- 설명 바로 옆에 해당 코드와 위치를 제시하라. 파일 목록이나 전체 소스만 나열하지 마라.
- 코드에서는 이해와 적용에 필요한 부분만 발췌하라. 생략 부분과 예제 코드를 구분하라.
  핵심 분기·부수 효과·상태 변경을 숨기지 마라.
- 필수 개념과 판단 이유는 짧게 설명하라. 상세 설명은 해당 도메인 문서에 모아라.
  관련 문서는 필요한 맥락과 링크로 연결하라.
- 비교·대응은 표로 정리하라. 절차는 순서 목록으로 정리하라.
  코드는 언어를 지정한 코드블록으로 작성하라.
- 관계나 전이가 더 잘 드러날 때만 다이어그램을 사용하라. 같은 정보를 여러 형식으로 반복하지 마라.

## 소스 구조 형식

- 결과 문서의 `## 소스 구조`는 `text` 코드블록의 디렉터리 → 파일 → 메서드 트리로 시작하라.
  파일·함수별 하위 제목, 설명 문단, 표만으로 이 트리를 대체하지 마라.
- 도메인 개발에 필요한 파일과 메서드만 포함하라.
  파일에는 역할과 필요한 개수 정보를 붙여라. 메서드에는 실제 선언 라인 번호와 역할을 짧게 붙여라.
  엔드포인트는 HTTP 메서드와 경로도 표시하라.
- 라인 번호와 엔드포인트는 실제 소스에서 확인하라.
  실제 소스를 확인할 수 없는 일반 가이드에는 예제 구조임을 표시하라.
  가상의 경로·라인 번호를 사실처럼 쓰지 마라.
- 프로세스 흐름은 트리의 파일·메서드를 연결해 진입점부터 호출 순서대로 설명하라. 표로 대체하지 마라.
- 핵심 코드, 다음 호출과의 연결, 주요 분기·상태 변경은 트리 뒤에 필요한 만큼만 덧붙여라.

아래는 표현 형식 예시다. 경로·이름·라인 번호·주석은 대상 소스에 맞게 작성하라.

```text
src/main/java/example/order/
├─ OrderController.java                   # 주문 진입점
│  └─ createOrder                  :33     # POST /orders · 주문 생성 → OrderService.create
├─ OrderService.java                      # 주문 처리
│  └─ create                       :48     # 입력 검증 → 저장 · CREATED 상태 설정
└─ OrderRepository.java                   # 주문 저장
   └─ save                         :21     # 주문 데이터 등록
```

## 출력 파일

1. 사용자가 지정한 파일과 위치를 우선하라. 기존 문서를 대상으로 요청하면 해당 파일을 수정하라.
2. 새 문서는 저장소의 문서 배치·파일명 규칙을 따라라.
   `pg`로 시작하는 기존 문서가 있으면 실제 패턴을 확인해 적용하라.
   확인 없이 접두어나 파일명을 추정하지 마라.
3. 규칙이 없으면 저장소 루트의 `docs` 폴더에 도메인을 식별할 수 있는 이름으로 생성하라.
4. 대상이나 위치가 여러 개로 해석되고 기존 파일을 덮어쓸 수 있으면 사용자에게 확인하라.

## 완료 확인

- 문서만 보고 핵심 관계와 대표 흐름을 설명할 수 있는지 확인하라.
- 문서에서 개발을 시작할 위치와 방법을 찾을 수 있는지 확인하라.
- 실제 소스를 확인한 문서에 `## 소스 구조`와 `text` 트리가 있는지 확인하라.
  트리에 디렉터리·파일·메서드, 실제 라인 번호·역할, 해당 엔드포인트가 빠졌으면 보완하라.
- 트리 뒤의 흐름 설명과 핵심 코드가 트리의 파일·메서드에 연결되는지 확인하라.
- 상태값·전이 조건·코드 위치·명령이 근거와 일치하는지 확인하라. 저장소 링크는 대상 존재를 확인하라.
- 실행 가능한 예제·검증 명령은 환경과 권한이 허용하는 범위에서 확인하라.
  실행하지 못한 검증은 완료 보고에 밝혀라. 설명용 발췌 코드는 독립 실행 가능한 예제로 취급하지 마라.
- 결과를 `.md` 파일에 저장하라. 파일 경로와 필요한 미확인·미검증 사항만 짧게 보고하라.
