# CT Apply

다음 작업을 현재 프로젝트의 환경과 관례에 맞게 끝까지 실행한다.

- 확정된 계획
- `ct-verify`가 전달한 실패 수정 작업

진행 표시는 [ct-progress](../ct-progress/SKILL.md), `.debrief/` 기록은 [ct-journal](../ct-journal/SKILL.md) 지침을 따른다.

## 호출

- 요청 없이 호출하면 역할, 필요한 입력, 예제만 안내한다.
- 지정된 계획과 현재 상태를 읽는다. 완료, 미완료, 막힌 작업을 확인한다.
- `ct-plan`이 승인 후 이 파일을 읽으면 승인된 계획을 실행 계획으로 사용한다. 계획을 다시 확인하지 않는다.
- `ct-verify`가 실패 수정을 넘기면 실패 항목을 다시 처리한다. 이전 완료 표시는 무시한다. 그다음 아래 검증 루프로 재검증한다.
- 시작하면 `ct-progress` 지침으로 맵에 실행을 보낸다. 단계는 계획의 수정 영역, 검증, 이해 확인으로 만든다.
- `ct-verify`가 전달한 다음 기준이 확정되어 있으면 그 기준을 실행 계획으로 사용한다. 별도 계획 파일을 요구하지 않는다.
  - 요구사항
  - 기대 결과
  - 수정 범위
  - 검증 방법
- 그 밖의 경우에 다음 조건을 모두 충족하면 대상 계획을 사용자에게 확인한다.
  - 사용자가 계획을 지정하지 않았다.
  - 대화나 프로젝트에서 계획을 하나로 특정할 수 없다.
- 각 요구사항의 완료 조건과 검증 방법을 확인한다.
- 승인된 계획으로 실행하면 실행 중에 사용자에게 묻지 않는다. 결정은 계획 단계에서 끝났다.
- 단독으로 실행할 때만 다음 경우에 구현 전에 사용자에게 확인한다. 확인할 사항은 한 번에 모아 묻는다.
  - 계획이나 확정된 실패 수정 기준이 없다.
  - 필요한 기준이 빠졌다.
  - 결과를 바꾸는 미결정 사항이 있다.

예: `$ct-apply 주문 취소 구현 계획의 남은 작업을 완료해줘`

## 수행

- 프로젝트의 다음 항목과 기존 관례를 확인한다: 언어, 의존성, 빌드, 실행, 테스트 수단
- 확정 계획의 다음 항목을 실행 기준으로 사용한다: 작업 순서, 수정 영역, 대상 파일, 완료 조건, 검증 방법
- 시작할 때 계획과 현재 변경 상태를 비교한다. 남은 작업을 수정 영역별로 짧게 보고한다.
- 계획의 수정 영역 단위로 실행하고 검증한다.
- 진행 중에는 완료한 영역, 검증 결과, 다음 작업을 보고한다.
- 검증한 항목만 완료로 표시한다.
- 실제 대상 파일이나 변경 범위가 계획과 다르면 변경 내용과 이유를 보고한다. 그다음 계획을 갱신한다.
- 계획 파일이 있으면 실행 상태와 검증 결과를 기록한다.
- 대화에서 확정한 계획도 같은 작업 순서와 수정 영역으로 보고한다.
- 실행 중 계획에 없는 결정이 생기면 묻지 않고 정한다. 기준은 계획의 판단 기준, 그다음 최소 변경이다. 그 결정은 ADR 후보로 맵에 보내고 종료 보고에 쓴다.
- 다음 경우에만 해당 항목을 멈추고 사용자에게 묻는다: 요구사항이나 범위가 바뀐다, 되돌리기 어려운 변경이다(데이터 삭제, 외부 시스템 변경).
- 독립 작업은 계속 진행한다.
- 가벼운 작업의 예: 파일 탐색, 테스트·빌드 실행, 로그 요약
- 가벼운 작업은 런타임이 서브에이전트 모델 지정을 지원하면 저가 모델 서브에이전트에 맡긴다. 지원하지 않으면 메인 모델이 처리한다.
- 저가 모델은 런타임에서 쓸 수 있는 최신 버전을 쓴다. 이전 버전을 고정해서 쓰지 않는다.
- 서브에이전트 단계는 맵 단계에 `agent`(모델 이름)를 넣는다. 모델과 토큰 표시는 [ct-progress](../ct-progress/SKILL.md)의 "모델과 토큰" 규칙을 따른다.
- 판단, 설계, 코드 수정, 사용자 질문은 메인 모델이 한다.
- 멈추고 물을 때는 먼저 맵에 `wait`를 보낸다. 선택지마다 이유를 보기 설명에 쓴다. 사용자가 고른 보기의 이유를 그 선택의 이유로 쓴다. 선택과 이유는 ADR 후보로 맵에 보낸다.

## 검증 루프

- 모든 수정 영역을 마치면 같은 작업 턴에서 [ct-verify](../ct-verify/SKILL.md)를 읽는다. 그 지침으로 검증하고 판정을 받는다.
- 실패 항목이 있으면 맵에 수정 단계와 재검증 단계를 추가한다. 실패 항목을 수정한 뒤 다시 검증한다.
- 모든 요구사항이 통과하거나 구체적인 장애로 막힐 때까지 반복한다. 임의의 횟수 제한을 두지 않는다.
- 수정과 재검증 반복은 `ct-apply`가 관리한다. `ct-verify`는 판정만 반환한다.
- 수정 방향도 묻지 않고 정한다. 기준은 위의 실행 중 결정 기준과 같다.

## 이해 확인 연쇄

- 모든 요구사항이 통과하면 같은 작업 턴에서 [ct-debrief](../ct-debrief/SKILL.md)를 읽는다. 그 지침으로 이해 확인을 진행한다.
- 막힌 요구사항이 남으면 이해 확인으로 넘어가지 않는다. 원인과 재개 지점을 보고한다.
- 실행이 끝나면 `ct-journal` 지침으로 실행 기록과 ADR 후보를 남긴다.

## 완료

- 다음 중 하나에 해당하면 종료한다. 임의의 횟수 제한으로 끝내지 않는다.
  - 모든 확정 작업을 검증하고 완료했다.
  - 구체적인 장애로 더 진행할 수 없다.
- 종료 전에 계획의 모든 요구사항과 실제 결과를 비교한다.
- 종료 보고는 확정 계획과 같은 작업 순서와 수정 영역의 표로 정리한다. 표 열은 다음 순서를 따른다: 수정 위치, 주요 변경, 검증 결과
- 수정 위치에는 파일 경로와 메서드나 함수명을 표시한다. 주요 변경에는 수정 이유와 변경 전후 동작을 요약한다.
- 메서드나 함수로 특정할 수 없는 코드는 해당 선언이나 설정 항목으로 표시한다.
- 같은 목적의 여러 파일은 한 묶음으로 나열한다. 설명은 한 번만 쓴다.
- 전체 검증 결과, 완료 여부, 계획 대비 변경점, 남은 작업은 표 아래에 짧게 설명한다. 막힌 작업이 있으면 원인과 재개 지점도 표시한다.
- 검증 회차, 최종 판정, 미검증 사항과 그 사유를 표 아래에 명시한다. 표의 내용을 반복하지 않는다.
- 해결한 도구 오류와 중간 시행착오는 종료 보고에서 제외한다.
- 이해 확인을 진행했으면 `ct-debrief` 완료 보고를 이어서 붙인다.
