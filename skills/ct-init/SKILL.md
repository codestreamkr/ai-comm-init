# CT Init

## 목적

프로젝트 기준 문서 3종을 언어별 표준에 맞게 만든다.

- 생성 대상:
  - `.docs/core_project.md`
  - `.docs/core_code_style.md`
  - `.docs/core_workflow.md`
- `AGENTS.md`에서는 ct-init 관리 블록만 갱신한다.
- 상세 구조, 스타일, 실행 절차는 `core_*` 3종으로 분리한다.

## 사용 시점

저장소 초기 기준 문서가 필요할 때 사용한다.

- 새 저장소를 세팅한 직후
- `.docs` 문서가 없거나 최신 기준으로 갱신해야 할 때
- `AGENTS.md`가 비대해져 상세를 `core_*` 문서로 분리하려고 할 때

## 실행 방식

먼저 프로젝트 유형을 확인한 뒤 reference를 하나만 읽는다.

- 스크립트를 실행하지 않는다.
- 파일 근거로 언어와 런타임을 판정한다.
- 판정한 reference의 생성 포맷에 따라 문서를 직접 작성한다.
- 언어별 reference를 여러 개 섞지 않는다.
- 판단 근거가 부족하면 `generic`을 사용하고 확인 필요 항목을 남긴다.

## 실행 모드

요청에 따라 하나의 모드를 선택한다.

- `sync`: 기본 모드다. 기존 core 문서의 확인된 프로젝트 기준과 이력을 보존하면서 최신 포맷으로 갱신한다.
- `reset`: 사용자가 `$ct-init --reset` 또는 core 문서 재생성을 명시한 경우에만 사용한다.
  - 기존 core 본문을 병합하지 않고 현재 저장소에서 다시 확인한 근거와 최신 템플릿으로 전체 재작성한다.
  - 기존 `## 이력관리`는 보존하고 같은 날짜 항목에 reset 사실을 합친다.
  - 확인할 수 없는 기존 값은 복사하지 않고 `확인 필요`로 기록한다.
- 두 모드 모두 `AGENTS.md` 관리 블록 밖의 내용은 보존한다. 관리 블록 밖의 중복 정리는 별도 확인 절차를 따른다.

## 언어 감지 순서

파일 근거를 우선한다.

1. Java
   - `pom.xml`
   - `build.gradle`, `build.gradle.kts`, `settings.gradle`
   - `src/main/java/**`, `src/test/java/**`
2. Node.js/TypeScript
   - `package.json`
   - `tsconfig.json`
   - `pnpm-lock.yaml`, `yarn.lock`, `package-lock.json`
   - `src/**/*.ts`, `src/**/*.tsx`, `app/**`, `pages/**`
3. Python
   - `pyproject.toml`
   - `requirements.txt`, `poetry.lock`, `uv.lock`, `Pipfile`
   - `src/**/*.py`, `tests/**/*.py`
4. Generic
   - 위 기준으로 주 언어를 확정하기 어렵거나 혼합 저장소인 경우

## reference 선택

감지 결과에 맞는 reference만 읽는다.

- Java: `references/ct-init-java.md`
- Node.js/TypeScript: `references/ct-init-node.md`
- Python: `references/ct-init-python.md`
- Generic: `references/ct-init-generic.md`

## 혼합 저장소 기준

여러 언어가 함께 있으면 주 런타임을 먼저 판단한다.

- 우선 기준:
  - 배포 산출물을 만드는 빌드 파일
  - 실제 실행 엔트리포인트
  - 테스트와 CI의 기본 명령
  - `README.md` 또는 기존 `AGENTS.md`의 실행 설명
- 주 런타임이 명확하면 해당 reference를 사용한다.
- 주 런타임이 불명확하면 `generic`을 사용한다.
- 판단 근거와 제외한 후보를 `.docs/core_project.md`에 남긴다.

## 공통 생성 정책

`sync` 생성 결과는 최신 포맷과 기존 사용자 규칙을 함께 보존한다.

- core 문서는 최신 포맷으로 본문을 갱신한다.
- 현재 저장소의 소스와 빌드·실행 설정에서 확인한 근거를 기존 core 문서보다 우선한다.
- 기존 core 문서에서는 현재 근거와 충돌하지 않는 프로젝트 고유 규칙과 `## 이력관리`만 최종본에 반영한다.
- 기존 core 문서와 현재 근거가 충돌하면 현재 근거로 갱신하고 변경 사유를 해당 core 문서의 이력과 실행 결과에 기록한다.
- 이력관리에는 `- YYYY-MM-DD: 변경 내용 요약` 형식만 사용하고, 같은 날짜가 있으면 기존 항목에 변경 내용을 합쳐 한 줄로 유지한다.
- `AGENTS.md`는 관리 마커 내부만 생성하거나 교체한다.
- 관리 마커 밖의 제목, 사용자 규칙, 프로젝트 라우팅은 보존한다.
- 확인 불가 항목은 추측하지 않고 `확인 필요`로 표기한다.
- 템플릿 플레이스홀더를 최종 문서에 남기지 않는다.
- 같은 정보가 둘 이상의 core 문서에 반복되면 안 된다.

`reset`에서는 현재 저장소에서 다시 확인한 프로젝트 기준만 본문에 반영하고 기존 본문은 병합하지 않는다. 이력관리와 `AGENTS.md` 관리 블록 밖의 내용은 보존한다.

## core 문서 메타 규칙

세 문서의 `문서 메타`는 같은 순서를 사용한다.

- `생성일`
- `목적`
- `문서 성격`
- `책임 범위(정본)`
- `포함 범위`
- `제외 범위`
- `연계 문서`
- `중복 방지 기준`

작성 기준:

- `책임 범위(정본)`은 이 주제의 최종 기준 문서를 명시한다.
- `중복 방지 기준`은 다른 core 문서로 보내야 하는 내용을 문장 단위로 적는다.
- 문서 간 중복이 생기면 책임 문서 한 곳에만 남긴다.

## core 문서 책임

세 문서의 책임을 분리한다.

- `core_project.md`
  - 프로젝트 목적, 아키텍처, 런타임, 코드 구조, 데이터 접근, 외부 연동, 변경 영향
- `core_code_style.md`
  - 네이밍, 파일/모듈 배치, 타입/모델 규칙, 오류 처리, 로깅, 테스트 작성 스타일
- `core_workflow.md`
  - 설치, 빌드, 테스트, 실행, 환경 변수, 배포, 장애 대응, 도구 버전

## 코드베이스 구조 규칙

구조 문서는 온보딩 기준으로 작성한다.

- `.docs/core_project.md`의 `코드베이스 구조`는 최소 3뎁스까지 표현한다.
- 기준은 저장소 루트 상대 경로다.
- 주요 디렉터리에는 역할 주석을 붙인다.
- 실제 구조가 3뎁스 미만이면 `최대 N뎁스` 사유를 한 줄로 남긴다.
- 실행 명령은 `core_project.md`에 쓰지 않고 `core_workflow.md`에만 쓴다.
- 테스트 섹션에는 테스트 위치와 대표 파일만 적고, 실행 명령은 `core_workflow.md`에만 쓴다.

## AGENTS 동기화 정책

`AGENTS.md`에서는 core 문서 라우팅 블록만 관리한다.

- `AGENTS.md` 상단에 `ct-init` 관리 블록을 유지한다.
- 관리 블록 범위:
  - `<!-- ct-init:core-docs:start -->`
  - `<!-- ct-init:core-docs:end -->`
- 관리 블록 밖의 기존 제목과 상세 정책은 변경하지 않는다.
- core 문서로 관리할 프로젝트 구조·스타일·실행 상세는 관리 블록의 링크로 연결한다.
- 관리 블록이 없으면 기존 문서를 보존한 채 첫 H1 제목 다음에 추가하고, H1 제목이 없으면 파일 시작에 추가한다.

관리 마커 상태에 따라 아래처럼 동기화한다.

- 정상 한 쌍: 마커 내부만 최신 관리 블록으로 교체한다.
- 마커 없음: 정해진 삽입 위치에 새 관리 블록을 추가한다.
- 완전한 관리 블록이 여러 개: 각 관리 블록 영역만 제거하고 첫 관리 블록 위치에 하나를 생성한다.
- 시작 또는 종료 마커만 있음: 고아 마커 한 줄만 제거하고 정해진 삽입 위치에 정상 관리 블록을 생성한다.
- 마커 중첩이나 범위를 안전하게 판정할 수 없는 상태: 내용을 삭제하지 않고 중단한 뒤 마커 위치를 보고한다.

## AGENTS 중복 정리

기존 상세 규칙의 이관과 정리는 명시적으로 요청받은 경우에만 수행한다.

- 기본 실행:
  - 관리 블록만 생성하거나 갱신한다.
  - 관리 블록 밖의 내용은 그대로 보존한다.
- 정리 실행 조건:
  - 사용자가 `AGENTS.md` 중복 정리 또는 core 문서 이관을 명시적으로 요청한다.
  - 삭제 전에 정리 후보를 사용자에게 제시하고 확인받는다.
- 확인 항목:
  - `AGENTS.md`의 원본 섹션명
  - 이관할 core 문서와 섹션
  - 이관할 고유 내용
  - 제거할 중복 범위
- 정리 순서:
  1. 후보를 구조·스타일·실행 책임에 따라 core 문서로 분류한다.
  2. 고유 내용을 대상 core 문서에 먼저 반영한다.
  3. 대상 문서에 내용이 반영됐는지 대조한다.
  4. 사용자가 확인한 중복 범위만 `AGENTS.md`에서 제거한다.
  5. 관리 블록 밖에 남은 규칙과 원문 대비 변경 범위를 보고한다.
- 보존 대상:
  - 에이전트 행동 규칙과 권한
  - 프로젝트 고유 라우팅
  - core 문서 책임에 포함되지 않는 운영 규칙
  - 이관 여부가 불명확한 내용

## 공통 AGENTS 템플릿

아래 관리 블록만 생성하거나 갱신한다.

```markdown
<!-- ct-init:core-docs:start -->
## Core 문서 참조 (ct-init 관리)
- 프로젝트 구조/모듈 상세: `.docs/core_project.md`
- 코딩 스타일/네이밍 상세: `.docs/core_code_style.md`
- 빌드/테스트/운영 상세: `.docs/core_workflow.md`
- 빌드, 테스트, 실행과 환경 버전 판단은 먼저 `.docs/core_workflow.md`를 확인한다.
- 프로젝트 구조, 스타일, 실행 상세는 위 문서에서 관리하고 기존 AGENTS 규칙은 보존한다.
- 마지막 동기화: {GENERATED_DATE}
<!-- ct-init:core-docs:end -->
```

## 완료 조건

작업 완료 전에 생성 범위와 보존 결과를 확인한다.

- `.docs/core_project.md`, `.docs/core_code_style.md`, `.docs/core_workflow.md`가 존재한다.
- 세 문서의 책임, 실행 명령, 작성 규칙이 서로 중복되지 않는다.
- 템플릿 플레이스홀더가 남아 있지 않다.
- `sync` 실행에서는 현재 근거와 충돌하지 않는 기존 프로젝트 고유 규칙과 `## 이력관리`가 최종본에 반영되어 있다.
- `sync` 실행에서 기존 core 문서와 현재 근거의 충돌은 현재 근거로 갱신되고 변경 사유가 이력과 실행 결과에 기록되어 있다.
- `reset` 실행에서는 기존 본문이 병합되지 않고 현재 저장소에서 다시 확인한 근거와 기존 이력만 반영되어 있다.
- 같은 날짜의 이력관리 항목이 중복되지 않는다.
- `AGENTS.md` 관리 마커가 정확히 한 쌍이고 내부 링크가 유효하다.
- 기본 실행에서는 관리 블록 밖의 내용이 원문과 같다.
- 중복 정리 실행에서는 사용자 확인 범위만 제거되고 고유 내용이 core 문서에 보존되어 있다.
- 확인할 수 없는 값과 실행하지 못한 검증이 결과에 기록되어 있다.

## 출력

처리 결과를 짧게 요약한다.

- 감지한 프로젝트 유형
- 적용한 실행 모드
- 사용한 reference
- 생성 또는 갱신한 파일
- `AGENTS.md` 관리 블록 갱신 여부
- 중복 정리를 수행한 경우 이관·보존·제거한 항목
- `sync`에서 충돌한 기존 기준과 현재 근거, 갱신 결과
- 확인 필요 항목
- 실행하지 못한 검증
