# ct-improve-plan

## 실행 원칙

- 증거 없이 문제를 단정하지 말고 코드, 설정, 테스트, 프로젝트 문서를 근거로 기록하라.
- 빠른 결과보다 정확한 구조 파악과 근거 검증을 우선하라.
- 성능(속도) 최적화보다 충분한 확인 시간을 확보한 정밀 점검을 우선하라.
- 지레짐작으로 결론내리지 말고, 추정은 가설로 표시한 뒤 검증 가능한 근거를 확보할 때만 확정하라.
- 독립 조사 축은 가능하면 병렬로 진행하되, 도구·세션 제약이 있으면 단일 조사로 대체하고 그 한계를 결과에 남겨라.
- 요청 범위를 넘는 기능 확장을 제안하지 말고 개선 대상의 우선순위를 먼저 고정하라.
- 이 스킬은 문서 작성 전용이다. 코드를 직접 수정하지 말고 `mvn`, 빌드, 테스트, 애플리케이션 실행 검증도 수행하지 마라.
- 한 문서만 작성하고 종료하지 마라. 미완성 항목은 삭제하지 말고 `검증 필요`로 전환한 뒤 마무리하라.
- 외부 PG, 메시지, 정산, 락, 배치, 후처리처럼 부작용이 있는 흐름은 기능 분리보다 `트랜잭션 경계`, `응답 계약`, `보상 처리`, `멱등성`을 먼저 확정하라.
- 주석 처리되거나 비활성화된 코드나 설정은 실수로 간주하지 말고, 의도적으로 꺼졌을 가능성을 우선 조사하라.
- 본 처리 실패, 후처리 실패, cleanup 실패를 같은 실패로 묶지 말고 각 실패가 실제 응답 코드와 운영 보정에 어떤 영향을 주는지 분리해서 정리하라.
- 대형 구조 개선 항목은 한 번에 치환하는 방향으로 끝내지 말고 `점진 전환 전략`과 `관찰 가능성 보강`을 함께 제시하라.

## 입력 확정

- 프로젝트 식별자 `{project}`를 확정하라.
- 사용자가 별도 경로를 지정하지 않으면 저장 위치를 현재 작업 루트로 사용하라.
- 출력 파일명은 반드시 아래 형식을 그대로 사용하라.
  - `{project}_improve_plan.md`
  - `{project}_improve_guide.md`
- 우선순위 산정 기준을 아래 기본값으로 시작하되, 사용자가 기준을 주면 덮어써라.
  - 영향도(1-5), 결함 위험도(1-5), 전파 범위(1-5), 구현 노력(1-5)
  - 기본 점수: `(영향도*2 + 결함위험도*2 + 전파범위) - 구현노력`
  - 기본 등급: P0(>=12), P1(9-11), P2(6-8), P3(<=5)
- 산정 결과는 내부 우선순위 결정에만 사용하고 문서 본문이나 표에는 노출하지 않는다.

## 작업 순서

1. 독립 조사 축(코드, 설정, 테스트, 프로젝트 문서)을 분리하고, 가능하면 병렬로 근거를 수집하라. 병렬이 불가능하면 단일 조사로 진행하고 누락 가능성을 결과에 남겨라.
2. 핵심 코드 경로를 먼저 정독하고, 입력부터 반환까지 주요 조건과 분기 지점을 확정하라.
3. 외부 부작용 지점(PG, 포인트, 메시지, 배치, 락, 알림, 외부 API)을 식별하고 본 처리, 후처리, cleanup 경계를 분리하라.
4. 호출과 전파 경로를 따라가며 영향 범위를 끝까지 확인하라.
5. 설정, 테스트, 프로젝트 문서를 코드와 대조해 누락, 불일치, 검증 공백을 확인하라.
6. 주석 처리, 비활성화, 우회 로직이 있으면 커밋 이력, 주변 코드, 호출 패턴을 통해 도입 배경 단서를 찾고, 확정하지 못하면 `검증 필요` 사유로 남겨라.
7. 실제 처리 결과와 응답 코드가 어긋나는 분기, cleanup 실패가 본 처리 결과를 덮어쓰는 분기, 중복 실행 위험이 있는 분기를 별도로 표시하라.
8. 점진 전환 가능 여부와 필요한 로그, 추적 포인트를 확인하라.
9. 위 확인이 끝난 뒤 개선 후보를 수집하고, 각 후보를 전략 관점의 `문제/근거`로 요약하라.
10. 중복과 종속 항목을 정리하고 개선 항목 ID(`IMP-001` 형식)를 부여하라.
11. 우선순위 점수를 계산하고 내부 우선순위를 확정하라. 문서에는 노출하지 마라.
12. `improve_plan` 문서를 작성하라.
13. `improve_guide` 문서를 작성하라.
14. 두 문서 간 ID 정합성과 역할 분리가 유지되는지 검증하라.
15. 완료 체크리스트로 누락을 다시 점검하고, 비어 있는 항목을 모두 보완하라.
16. 남은 누락이 없을 때만 종료하라.

## 문서 작성 규칙

- `improve_plan`은 판단 문서다. 무엇을 왜 바꿔야 하는지, 무엇을 먼저 바꿔야 하는지를 전략, 리스크, 영향 관점에서 정리하라.
- `improve_plan`은 항목별로 `ID`, `개선 영역`, `문제/근거`, `영향`, `우선순위 판단`, `핵심 설계 결정`, `실패/보상 정책`, `점진 전환 전략`, `관찰 가능성 보강`, `선행 조건`, `근거 목록`만 포함하라.
- `improve_plan` 본문과 표에는 우선순위 점수, 파일명, 코드 식별자, 라이브러리명이나 버전, URL, 테스트나 빌드 명령, diff를 적지 마라.
- 파일 경로, 코드 식별자, 라이브러리와 버전, 명령어, 내부 문서 경로 등 추적용 정보는 항목별 `근거 목록`에만 정리하라.
- `근거 목록`은 bullet 나열 대신 Markdown 표로 작성하라. 최소 컬럼은 `구분`, `위치/대상`, `확인 내용`을 사용하라.
- `근거 목록` 표의 `구분`은 가능하면 `코드`, `설정`, `테스트`, `문서`, `데이터`, `운영가정`처럼 읽는 사람이 맥락을 바로 파악할 수 있는 값으로 통일하라.
- `근거 목록:` 라인 다음에는 반드시 한 줄을 비운 뒤 표를 시작하라.
- `근거 목록`의 `위치/대상`에서 긴 파일 경로는 전체 경로를 그대로 쓰지 말고 파일 기준 상위 2개 디렉터리까지만 남겨라. 그보다 앞 경로는 `../`로 축약하라.
- 예시:
  - `src/main/java/com/example/domain/service/SampleService.java` -> `../domain/service/SampleService.java`
  - `src/main/webapp/WEB-INF/web.xml` -> `../WEB-INF/web.xml`
  - `.0_my/core_test_convention.md` -> `../.0_my/core_test_convention.md`
- 라인 번호나 범위가 필요하면 축약 경로 뒤에 공백으로 덧붙여 표기하라. 예시: `../domain/service/SampleService.java 120-180`
- 버전과 라이브러리 이슈는 `improve_plan`에서 라이브러리명이나 버전 자체를 노출하지 말고, 서비스 영향과 심각도(Critical, High, Medium, Low)만 기술하라.
- 보안 관련 개선 항목은 `근거 목록`에 취약 코드 경로, 입력이나 노출 범위, 관련 설정 또는 의존성 근거를 함께 명시하라.
- 보안과 의존성 항목은 중장기 정비와 긴급 패치를 분리해서 판단하라.
- 프레임워크와 의존성 개선 항목은 JDK, WAS, 배포 런타임 제약을 함께 확인하라.
- `improve_guide`는 실행 문서다. 개발자가 문서만 보고 코드를 수정하거나, 이 문서를 다시 AI에 입력해 구현을 맡길 수 있게 작성하라.
- `improve_guide`는 항목별로 `ID`, `변경 범위`, `설계 결정`, `응답/실패 계약`, `구현 순서`, `구현 패치(복붙용 diff 블록)`, `주의사항`, `검증 포인트`, `롤아웃/되돌리기`, `검증 필요`만 포함하라.
- `improve_guide`에는 긴 배경 설명, 우선순위 설명, 영향 설명, 근거 목록을 반복하지 말고 작업 지시형 문장과 파일별 diff 블록 중심으로 작성하라.
- diff 블록은 fenced code block(````diff`)의 unified diff 형식을 사용하고, 파일 헤더(`---`, `+++`)와 hunk(`@@`)를 포함하라.
- 각 diff 블록은 가능한 한 그대로 붙여넣어 `git apply` 가능한 형태로 제공하라.
- 다중 파일 변경은 파일별 diff 블록으로 분리하라.
- 외부 부작용이 있는 항목은 `설계 결정`과 `응답/실패 계약`이 먼저 확정되지 않으면 diff를 제시하지 마라.
- cleanup 실패가 본 처리 성공을 덮어쓰는 응답 설계는 그대로 diff로 제안하지 마라. 로그 경고, 후속 정리 배치, 운영 점검 등 대안을 먼저 적고 `검증 필요`로 전환하라.
- 동일 로직이 여러 컨트롤러에 반복될 경우 private 메서드 복제보다 공통 서비스나 헬퍼 승격 가능성을 먼저 검토하라.
- 동시성이나 cleanup 항목은 `롤아웃/되돌리기`에 고아 데이터 정리 방식이나 운영 점검 절차를 반드시 포함하라.
- 테스트 항목에서 `임시 제외`를 쓰면 해제 조건과 해제 판단 기준을 함께 적어라.
- 의존성 보안 항목은 `변경 범위`에 우선 검토 대상 라이브러리 목록을 직접 적어라.
- 근거가 불충분하면 단정하지 말고 `검증 필요`로 표시하고, `improve_guide`에는 diff 대신 `검증 필요`와 추가 확인 포인트만 남겨라.
- `검증 필요`에는 사유만 쓰지 말고 `확정 액션`, `확인 위치`, `완료 조건`을 함께 적어라.
- 아래 경우에는 반드시 `검증 필요`를 사용하라.
  - 호출 경로를 끝까지 확인하지 못한 경우
  - 설정 반영 여부를 확정하지 못한 경우
  - diff를 안전하게 제시할 만큼 맥락이 부족한 경우
  - 프로젝트 문서와 코드가 다르지만 원인을 확정하지 못한 경우
  - 외부 부작용 흐름의 트랜잭션 경계, 보상 정책, 응답 계약을 확정하지 못한 경우
  - 주석 처리나 비활성화 코드의 배경을 확인하지 못한 경우
  - cleanup 실패와 본 처리 실패의 구분이 정리되지 않은 경우
- 두 문서는 동일한 `ID`로만 연결하라. `improve_guide`가 `improve_plan`의 문장을 복사하지 않게 하라.

## 출력 체크리스트

- 두 파일이 모두 생성되었는가.
- `improve_plan`과 `improve_guide`의 항목 ID가 동일하게 매핑되는가.
- `improve_plan`이 판단 정보만 담고 있고, 파일 경로, 코드 식별자, diff를 본문에 노출하지 않았는가.
- `improve_plan`의 각 항목에 `영향`, `우선순위 판단`, `핵심 설계 결정`, `실패/보상 정책`, `점진 전환 전략`, `관찰 가능성 보강`, `선행 조건`, `근거 목록`이 포함되었는가.
- `근거 목록`이 Markdown 표 형식으로 정리되었는가.
- `근거 목록:` 다음 줄에 빈 줄이 있고, 표가 독립 표로 렌더링되는가.
- `근거 목록`의 `위치/대상`이 파일 기준 상위 2뎁스까지만 남기고 나머지는 `../`로 축약되었는가.
- 보안 관련 항목의 취약 코드 경로, 입력/노출 범위, 관련 설정 또는 의존성 근거가 `근거 목록`에 포함되었는가.
- 외부 부작용 항목에 트랜잭션 경계, 응답 계약, 보상 정책이 정리되었는가.
- cleanup 실패가 본 처리 성공 응답을 덮어쓰지 않도록 위험이 식별되었는가.
- 비활성화 코드나 설정의 원인 확인 없이 복구 diff를 제시하지 않았는가.
- 구조 개선 항목에 점진 전환 전략과 관찰 가능성 보강이 포함되었는가.
- `improve_guide`의 각 항목에 `설계 결정`, `응답/실패 계약`, `롤아웃/되돌리기`가 포함되었는가.
- 동시성이나 cleanup 항목의 `롤아웃/되돌리기`에 고아 데이터 정리 방식이나 운영 점검 절차가 포함되었는가.
- 테스트 항목의 `임시 제외`에 해제 조건이 명시되었는가.
- 의존성 보안 항목의 `변경 범위`에 우선 검토 대상 라이브러리 목록이 포함되었는가.
- 미검증 가정이 남아 있으면 `검증 필요`에 `확정 액션`, `확인 위치`, `완료 조건`이 명시되었는가.
- 위 항목 중 하나라도 비어 있으면 종료하지 않았는가.

## Completion Gate

- 아래 조건이 모두 충족되기 전에는 작업을 종료하지 마라.
  - `improve_plan` 작성 완료
  - `improve_guide` 작성 완료
  - 두 문서 ID 매핑 완료
  - 각 확정 항목의 `근거 목록` 작성 완료
  - 미확정 항목의 `검증 필요` 사유 작성 완료
  - 완료 체크리스트 재검토 완료
  - 남은 누락 없음 확인

## Implementation Guide 작성 예시 형식

- `ID`: IMP-00X
- `변경 범위`: 수정 대상 파일, 클래스, 설정 키를 명시
- `설계 결정`: 트랜잭션 경계, 공통화 대상, 단계 분리 기준을 짧게 명시
- `응답/실패 계약`: 본 처리 실패, 후처리 실패, cleanup 실패 시 응답 원칙을 명시
- `구현 순서`:
  1. 서비스나 도메인 로직 수정
  2. DTO, VO, Mapper, SQL 전파 반영
  3. 호출부 계약 보정
- `구현 패치(복붙용 diff 블록)`:
- `주의사항`: 기존 예외, 로그, 반환 계약 유지
- `검증 포인트`: null 입력, 경계값, 연관 경로 누락 여부 확인
- `롤아웃/되돌리기`: 단계 배포 순서와 원복 기준을 명시
- `검증 필요`: 확인되지 않은 호출 경로가 있으면 대상과 이유를 명시
  - `확정 액션`: 무엇을 확인해야 하는지
  - `확인 위치`: 확인할 코드, 문서, 담당 영역
  - `완료 조건`: 무엇이 확인되면 diff 제시 가능 상태인지
