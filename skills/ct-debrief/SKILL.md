# CT Debrief

AI가 만든 변경을 사용자가 설명할 수 있는지 확인한다. 확인 결과로 결정 이유와 이해 부채를 남긴다.

- 코드, 설정, 테스트는 변경하지 않는다.
- 진행 표시는 [ct-progress](../ct-progress/SKILL.md) 지침을 따른다.
- 기록은 [ct-journal](../ct-journal/SKILL.md)의 저장 구조를 따른다.
- ADR 형식은 [adr-format.md](references/adr-format.md)를 따른다.

## 호출

- `ct-apply`가 모든 검증을 통과한 뒤 같은 작업 턴에서 이 파일을 읽는다.
- 연쇄 흐름 밖에서 코드를 바꿨으면 커밋 전에 실행한다.
- `$ct-debrief`: 역할, 필요한 입력, 예제만 안내한다. 실행하지 않는다.
- `$ct-debrief <범위>`: 지정한 범위의 변경을 확인한다. 범위가 없으면 `HEAD` 이후의 모든 변경을 대상으로 한다.

예: `$ct-debrief 주문 취소 변경을 확인해줘`

## 입력 수집

- 변경: `git diff HEAD`와 추적하지 않는 새 파일
- 계획과 실행 결과: 이번 작업의 계획, `ct-apply` 종료 보고, `ct-verify` 판정
- ADR 후보: 이번 작업의 맵 ADR 이벤트, `.debrief/decisions/candidates.md`
- 흐름 밖 변경의 ADR 후보: 대화에서 사용자가 승인한 선택. 이유는 승인한 보기나 제안에 쓴 이유 문구를 쓴다. 이유 문구가 없으면 이유가 없는 후보로 처리한다.
- 이해 부채: 계획에 포함된 `.debrief/debt.md` 항목

## 질문 수

| 변경 종류 | 질문 |
|---|---|
| 문서, 오타, 포맷만 변경 | 없음. 요약만 보여 주고 통과한다. |
| 일반 변경 | 2개 |
| 구조 변경, 의존성 추가, 대안을 비교한 변경 | 3개 |

- 이유가 없는 ADR 후보는 후보마다 "왜" 질문을 하나 추가한다.
- 계획에 포함된 이해 부채는 항목마다 질문을 하나 추가한다.

## 질문 작성

| 유형 | 확인 내용 | 예 |
|---|---|---|
| 왜 | 결정 이유 | 환불을 재고 복원보다 먼저 처리한 이유는? |
| 만약 | 경계 조건, 실패 처리 | 부분 환불 금액이 0이면 어디서 어떻게 처리되는가? |
| 어디 | 위치와 연결 | 취소 가능 상태를 바꾸려면 어느 파일의 어떤 메서드를 고치는가? |

- 실제 diff에서 질문을 만든다. 일반 지식 질문을 하지 않는다.
- 객관식으로 묻는다. 보기는 3~4개이고 정답은 하나다.
- 오답 보기는 실제로 헷갈릴 만한 내용으로 만든다. 정답 위치는 질문마다 바꾼다.
- 런타임에 선택 질문 도구가 있으면 그 도구를 쓴다. 없으면 번호를 붙인 보기로 묻는다.
- 사용자는 보기 대신 직접 답할 수 있다.
- 보기와 맞출 수 없는 직접 답변은 판정하지 않는다. 예: "제안대로", "모르겠음". 보기로 한 번 더 고르게 한다. 그래도 고르지 않으면 오답으로 처리한다.
- "왜" 질문은 AI가 내린 결정의 근거를 묻는다. 정답이 있는 질문으로 만든다.
- 질문에 정답의 단서를 넣지 않는다.
- 질문마다 정답 보기와 그 근거를 먼저 정한다.
- 정답 근거는 diff의 코드 줄로 확인한다. 기억이나 설명에 기대어 정하지 않는다.

## 수행

1. 맵의 이해 확인 단계를 `wait`로 보낸다. `ask`에는 "이해 확인 질문 N개"를 쓴다.
2. 변경 요약을 보여 준다. 수정 영역별로 무엇을, 왜 바꿨는지, 어떤 위험이 있는지 쓴다.
3. 질문을 한 번에 보여 준다.
4. 고른 보기로 판정한다: 정답, 오답. 직접 답하면 정답 근거와 비교해 판정한다.
5. 오답이면 정답 보기와 근거를 바로 알려 준다. 근거에는 코드 위치를 붙인다. 그다음 같은 요지를 다른 표현과 다른 보기로 한 번 더 묻는다.
6. 두 번째도 정답이 아니면 정답과 근거를 다시 알려 준다. 그 항목을 이해 부채로 기록한다. 게이트는 통과시킨다.
7. ADR 후보를 처리한다. 확정과 폐기는 사용자에게 묻지 않고 아래 기준으로 판정한다.
   - "왜" 질문에서 사용자가 정답 보기를 고르면, 그 보기 문구와 덧붙인 말을 이유로 쓴다. 고치지 않는다.
   - 확정: 여러 스킬이나 모듈에 영향을 주거나 되돌리기 어려운 결정이고, 이유가 있다.
   - 확정: 외부 계약을 바꾸는 결정이고, 이유가 있다. 예: 공개 함수의 입출력, API, 데이터 형식
   - 폐기: 위 확정 기준에 해당하지 않는 한 파일 안의 세부 동작이라 쉽게 바꿀 수 있다. 또는 다른 후보와 내용이 겹친다.
   - 보류: 이유를 받지 못했다. 또는 "왜" 질문을 재질문까지 틀렸다. `candidates.md`에 남긴다.
   - 확정한 후보는 ADR 파일로 만든다. 폐기한 후보는 판정 이유와 함께 실행 기록에만 남긴다.
   - 맵에 ADR 상태 이벤트(`ok` 또는 `drop`)를 보낸다.
   - 완료 보고에 후보별 판정과 판정 이유를 쓴다. 사용자가 판정을 바꾸라고 하면 그때 고친다.
8. 계획에 포함된 이해 부채를 맞히면 `debt.md`에서 지운다.
9. `ct-journal` 지침으로 기록을 반영한다: ADR 파일, `decisions/README.md`, `candidates.md`, `debt.md`, 실행 기록
10. 맵의 이해 확인 단계를 `done`으로 보낸다.
11. 모든 기록을 마친 뒤 마지막으로 통과 표시를 남긴다: `node <skill-dir>/scripts/gate.js mark <저장소> "<run>"`

- 통과 표시는 작업 트리 전체 상태에 붙는다. 그래서 기록 파일을 쓴 뒤에 남겨야 한다.
- 통과 표시 뒤에 파일이 바뀌면 커밋 때 다시 debrief가 필요하다.
- Node.js가 없으면 통과 표시를 남길 수 없다. 완료 보고에 그 사실을 쓴다.

## 중단

- 사용자가 답변을 미루면 통과 표시를 남기지 않는다.
- 이 경우 이유가 없는 ADR 후보는 `candidates.md`에 남긴다. 확인하지 못한 질문의 요지는 `debt.md`에 남긴다.
- 다음 `ct-plan`이 남은 항목을 계획에 포함한다.

## 완료

완료 보고는 아래 표로 정리한다.

| 질문 | 판정 | 정답 (오답일 때) | 비고 |
|---|---|---|---|
| 1. 환불 우선 처리 이유 | 정답 | - | ADR 0007 확정 |
| 2. 부분 환불 0원 처리 | 재질문 후 정답 | `RefundService.calc`에서 0원이면 환불 호출을 생략한다 | - |
| 3. 취소 가능 상태 변경 위치 | 오답 | `OrderStatus.isCancelable`을 고친다 | 이해 부채 기록 |

- 표 아래에 다음 항목만 짧게 쓴다: 확정·폐기·보류한 ADR, 추가·해소한 이해 부채, 통과 표시 여부
- 기록한 파일 경로를 쓴다.
