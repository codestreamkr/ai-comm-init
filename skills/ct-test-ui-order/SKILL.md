# 주문 결제 UI 테스트

- 현재 프로젝트의 환경파일을 읽고 상품별 결제수단 조합을 실행하라.
- 브라우저 창 하나에서 결제 조합별 전용 탭을 사용하라. PG 팝업과 복귀 탭을 원래 조합에 연결하라.
- 사용자가 제공한 `base URL`에서 시작하라. 새 주문은 같은 창에 새 탭을 추가해 시작하라.
- 기존 주문완료 화면을 새 주문의 시작점이나 성공 증빙으로 재사용하지 마라.
- 상품·수단 매핑, 시나리오와 병렬 설정은 [실행 설정](references/execution.md)을 읽어라.
- `RANDOM` 실행은 환경파일 후보에서 상품·수단을 추첨한 뒤 진행하라. 재개 시 저장된 매핑을 유지하라.
- 병렬 테스트가 끝나거나 중단되면 결과를 보고하라. 실패 조합의 재실행은 [실행 설정](references/execution.md)의 절차를 따라라.
- 주문완료 검증과 증빙 저장 후 성공 탭을 닫아라. 실행 채팅에 결과를 안내하라.
- 테스트 단위의 이름은 `ct-test-ui-order`를 사용하라. 다른 UI 테스트 단위는 별도 `ct-test-ui-*` 스킬로 구성하라.
- 브라우저 조작은 사용 가능한 computer-use 스킬과 CUA API를 따라라. 브라우저 연결이 없으면 해당 제약을 보고하라.
- mall 프로젝트는 [references/mall.md](references/mall.md)를 읽어라. 다른 프로젝트는 실제 주문서와 프로젝트 지침으로 경로·결제수단을 확인하라.

## 트리거

| 요청 | 동작 |
| --- | --- |
| `$ct-test-ui-order` 또는 `주문 결제 UI 테스트` | 같은 실행 조건의 미완료 결과가 있으면 재개, 없으면 새 실행 |
| `$ct-test-ui-order 55만` | 지정 결제수단으로 실행 범위를 제한 |
| `$ct-test-ui-order 새로` | 완료 결과와 별개로 새 실행 생성 |
| `$ct-test-ui-order 이어서` | 지정 실행 또는 일치하는 미완료 실행을 확인하고 재개 |
| `$ct-test-ui-order 실패만 재실행 <run-id>` | 지정 실행의 `FAIL` 조합만 재실행. 기존 주문 상태를 확인한 뒤 새 시도 생성 |

- 자동 선택은 주문 결제 UI 테스트 요청에만 적용하라. 일반 코드 테스트·결제 구현·리뷰에는 적용하지 마라.
- 스킬 호출은 지정 범위의 테스트 실행 요청으로 해석하라. 스킬 생성·설명·검토 요청에서는 결제를 실행하지 마라.

## 실행 조건

1. 작업 디렉터리와 프로젝트 지침을 확인하라.
2. 사용자가 지정한 환경파일을 우선하라. 지정 파일이 없으면 프로젝트의 `.env.payment-local`, `.env.payment-test` 순으로 확인하라.
   시작 주소는 사용자가 제공한 `base URL`을 우선하라. 제공하지 않았으면 `PAYMENT_TEST_BASE_URL`을 사용하라. 둘 다 없으면 주소를 요청하라.
3. 상품번호, 결제수단 ID, 수량, 옵션, 주소 정책, 인증 정책을 읽어라. 누락된 필수값만 요청하라.
4. `PAYMENT_TEST_PAYMENT_MODE=TEST`와 실제 PG 테스트 환경을 모두 확인하라. 로컬 주소만으로 테스트 결제로 판정하지 마라.
   REAL이거나 환경이 불일치하면 실행을 중단하라. 사유를 알려라.
5. 로그인·결제 비밀번호가 환경파일에 있으면 입력에만 사용하라.
   값·토큰·세션·개인정보를 출력하거나 리포트·스크린샷 파일명에 포함하지 마라.
   기본 예제의 가짜 값이나 추측한 비밀번호를 입력하지 마라.
6. 환경파일을 키와 문자열 값으로 읽어라. 명령어나 코드로 실행하지 마라.
   접속 주소에는 인증값이 포함될 수 있다. 주소 전체와 환경파일 원문을 출력하지 마라.
7. 화면의 프로모션 정책을 따라라.
   단일 프로모션은 금액 조건을 만족하면 자동 선택된다. 선택 레이어를 열지 마라.
   복수 프로모션은 요청된 적용 조건이 없으면 수동 선택하지 마라.
   프로모션 삭제·수정은 테스트 요청에 포함하지 마라.

### 시작 차단 시 안내

- 테스트를 시작할 수 없으면 확인한 원인과 미확인 항목을 구분해 보고하라.
- 원인별 해결 방법과 해결 후 확인 기준을 제안하라. 사용자 조치가 필요하면 구체적인 절차를 안내하라.
- 서버 연결 실패는 서버 실행 상태·설정 주소·포트를 확인하도록 안내하라.
- 로그인이나 필수 입력값이 없으면 필요한 로그인 절차나 환경파일 키를 안내하라. 비밀값을 채팅으로 요청하지 마라.
- 단일 창의 다중 탭·병렬 실행 기능이 부족하면 필요한 도구 기능과 연결 방법을 안내하라. 지원 여부가 미확인인 방법은 명시하라.
- 요청한 병렬 실행을 시작할 수 없으면 순차 실행을 대안으로 제안할 수 있다. 사용자 요청 없이 순차 실행으로 전환하지 마라.
- 실제 PG 테스트 환경을 확인하지 못하면 확인할 설정과 화면을 안내하라. 확인 전에는 결제를 제출하지 마라.

## 탭 준비와 진행

1. 같은 창에 조합별 새 탭을 추가하라. 각 탭에서 시작 주소에 접속하고 상품·장바구니 경로로 주문서를 준비하라.
   상품별로 수량·옵션을 유지하라. 각 조합과 새 시도에 별도 주문번호를 사용하라.
   기존 주문완료 탭을 탐색·새로고침·복제해 새 주문을 시작하지 마라. 추가 탭이 필요하면 같은 창에 계속 추가하라.
2. 서로 다른 조합의 주문번호·상품·금액·결제수단을 확인해 실행 결과에 연결하라.
3. 같은 세션의 병렬 주문은 프로젝트 명세·실제 요청 코드 또는 검증된 테스트 결과로 주문정보가 주문번호별로 분리됨을 확인한 경우에만 진행하라.
4. 병렬 안전성이 미확인되거나 세션에 단일 주문정보를 보관하면 같은 창에서 지원하는 독립 세션 기능을 확인하라.
   창·탭 분리만으로 세션 격리를 가정하지 마라. 안전성을 확보하지 못하면 병렬 결제 제출을 보류하고 사유를 안내하라.
5. 세션 격리가 미확인된 상태에서 이전 `SUBMITTED`, `AUTH_REQUIRED`, `UNKNOWN` 주문이 미해소이면 다른 조합의 신규 결제 요청도 보류하라.
6. 독립 조합은 설정한 동시 실행 한도까지 여러 탭에서 병렬로 진행하라. 응답·인증 대기 중에는 다른 독립 조합을 진행하라.
   완료 조합이 생기면 남은 조합용 새 탭을 추가하라. 순차 실행이나 조합별 별도 창으로 임의 전환하지 마라.
7. UI 준비는 현재 DOM을 기준으로 진행하라. 반복적인 전체 화면 수집을 줄여라. 선택 상태, 오류 메시지, 주문완료처럼 다음 판단에 필요한 요소를 확인하라.
8. 로그인·앱 인증·추가 인증에 사용자 입력이 필요하면 [사용자 인증 대기](#사용자-인증-대기)를 따라라.
9. 결제 요청 직전에 조합을 `SUBMITTED`로 기록하라. 오류·타임아웃·브라우저 중단 뒤 같은 조합을 자동 재결제하지 마라.
10. 인증 취소·실패는 안내와 버튼 복구를 확인하라. 확인 결과를 기록하라. 설정에 따라 다음 조합으로 진행하라. 실패 탭은 진단과 증빙을 확보한 뒤 요청 범위에 맞게 정리하라.
11. 결제수단이 노출되지 않으면 `SKIP`과 사유를 기록하라. 노출되는 다른 수단으로 임의 대체하지 마라.

## 사용자 인증 대기

- 해당 조합을 `AUTH_REQUIRED`로 기록하라. 인증 탭과 연결된 주문 탭을 보존하라.
- 사용자에게 조합·탭 식별자·인증 종류·필요한 동작을 안내하라. 비밀번호·OTP를 채팅으로 요청하지 마라.
- 같은 인증 요청을 반복하지 마라. 인증 화면이나 필요한 동작이 바뀌면 변경 내용을 안내하라.
- 인증을 기다리는 동안 다른 독립 조합을 계속 진행하라. 공통 로그인이 필요하면 해당 로그인을 요구하는 조합을 함께 대기시켜라.
- 모든 진행 가능한 조합이 인증 대기이면 사용자 조치를 기다려라. 대기를 완료나 실패로 처리하지 마라.
- 사용자 완료 안내나 인증 상태 변화가 있으면 실제 화면과 기존 주문 상태를 확인하라. 인증 완료가 확인되면 같은 탭에서 재개하라.
- 대기 시간 경과만으로 인증 완료를 가정하지 마라. 인증이 만료되면 만료 사실과 필요한 재인증 절차를 안내하라.
- 대기 해제 후 새 주문으로 자동 재결제하지 마라. 기존 주문의 중복 결제를 방지하라.

## 성공 판정과 자동 닫기

1. 주문완료 페이지에서 주문번호·상품·수량·결제수단·최종금액을 수집하라.
2. 준비된 조합과 상품·수량·수단·금액이 일치하고 성공 안내가 표시되는지 확인하라.
3. 주문상세 또는 주문조회에서 해당 주문이 `결제완료`로 저장됐는지 확인하라. DB를 직접 조회하지 않아도 재조회 결과로 저장을 검증할 수 있다.
4. 승인 응답이나 주문완료 URL만으로 성공 처리하지 마라. 실제 PG 테스트 결과와 SDK 대역 검증을 구분하라.
5. 통과 결과와 필요한 스크린샷을 저장하라. 그 뒤 이 실행에서 생성한 성공 탭만 닫아라. 사용자 기존 탭은 닫지 마라.
6. 결과가 불명확하면 `UNKNOWN`으로 기록하라. 탭을 보존하라. 사용자 인증 대기는 `AUTH_REQUIRED`로 기록하라.
7. 상품·수량·수단·금액이 명확히 불일치하면 `FAIL`로 기록하라. 자동 닫기 대상에서 제외하라.

## 결과와 재개

- 실행별 결과를 프로젝트의 Git 비관리 출력 디렉터리에 저장하라. mall은 `target/ui-order-tests/<run-id>/results.json`과 `report.md`를 사용하라.
- 결과에는 실행 ID·시각·환경파일 경로·TEST 여부·상품·수량·옵션·결제수단·상태·주문번호·예상/실제 금액·실패 단계·사유·증빙 경로를 기록하라. 인증값과 개인정보는 저장하지 마라.
- 시나리오·기대 결과·선택 카드/계좌 구분·공통 창 식별자·조합별 탭 식별자·세션 격리 확인 결과를 기록하라.
  인증정보 대신 비밀값이 없는 실행용 세션 별칭을 사용하라.
- 상태는 `PENDING`, `SUBMITTED`, `AUTH_REQUIRED`, `PASS`, `FAIL`, `SKIP`, `UNKNOWN`을 사용하라.
- 다른 채팅에서 결과를 읽어 재개할 수 있다. 이전 채팅의 탭 제어 객체는 재사용하지 않고 현재 브라우저 상태로 다시 연결하라.
- 같은 실행 조건에 미완료 리포트가 여러 개 있으면 실행 ID를 확인하라. 완료 조합은 재실행하지 마라.
- `SUBMITTED`, `AUTH_REQUIRED`, `UNKNOWN`은 기존 주문 상태부터 조회하라. 완료 여부가 불명확하면 사용자 확인 없이 새 주문으로 재결제하지 마라.
- 기존 결과의 예상금액·수량·옵션·증빙이 누락됐으면 원래 실행 조건과 주문 조회에서 보완하라. 비교 근거를 복구하지 못하면 `UNKNOWN`으로 유지하라.
- 실행 결과는 테스트 산출물이다. 대화 기억·사용자 성향·세션 요약을 저장하거나 MEMORY 파일을 생성하지 마라.
- 최종 보고에 상품과 테스트 환경을 밝혀라. 결제수단별 결과·주문번호·금액·실패/대기 사유를 표 하나로 제공하라. 필요한 증빙 이미지를 표시하라. 결과 파일을 링크하라.
- 성공 탭은 자동으로 닫아라. 실패·인증 대기·불명확한 탭이 남았으면 그 이유를 안내하라.
