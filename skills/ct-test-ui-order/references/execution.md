# 실행 설정

## 설정 분리

- 실행값은 프로젝트 환경파일에서 읽어라. 실제 상품번호·계정·인증값을 스킬에 고정하지 마라.
- 업무 규칙은 프로젝트 결제 사양에서 확인하라. 스킬에 사양의 지원 목록과 금액 기준을 복제하지 마라.
- 초안 요청은 매핑과 테스트케이스 작성까지만 수행하라. 결제를 제출하지 마라.
- 환경파일의 후보 또는 확정 매핑 밖에 있는 상품·수단·시나리오를 자동 추가하지 마라.

## 상품·수단 매핑

| 키 | 값과 동작 |
| --- | --- |
| `PAYMENT_TEST_COMBINATION_MODE` | `RANDOM`: 후보에서 무작위 배정, `MAPPED`: JSON 매핑, `ALL`: 상품 목록 × 수단 목록 |
| `PAYMENT_TEST_CASES_JSON` | `MAPPED`의 조합 배열. 바깥쪽 작은따옴표를 제거한 뒤 JSON으로 파싱 |
| `PAYMENT_TEST_EXECUTION_MODE` | `PARALLEL`: 단일 창의 여러 탭에서 병렬 진행. 사용자 요청 없이 `SEQUENTIAL`로 전환 금지 |
| `PAYMENT_TEST_MAX_TABS` | 동시에 진행할 조합 수. 병렬 실행은 2 이상의 정수. 전체 생성 탭 수의 제한은 아님 |
| `PAYMENT_TEST_MAX_WINDOWS` | 기존 설정 호환용. `PAYMENT_TEST_MAX_TABS`가 없으면 동시 조합 수로 사용. 창은 하나만 사용 |
| `PAYMENT_TEST_SESSION_MODE` | `AUTO`: 공유 안전성 확인 후 공유 또는 격리, `ISOLATED`: 조합별 독립 세션 |

각 매핑 행은 다음 필드를 사용한다.

| 필드 | 형식과 의미 |
| --- | --- |
| `productId` | 필수 문자열. 상품번호 |
| `methodIds` | 필수 문자열 배열. 결제수단 ID |
| `quantity` | 필수 양의 정수. 주문 수량 |
| `options` | 필수 객체. 실제 화면의 옵션명과 값. 옵션이 없으면 `{}` |
| `productType` | `AUTO` 또는 사양에서 사용하는 상품 유형. 지정값과 실제 상품이 다르면 제출 보류 |
| `instrument` | `AUTO`, `CARD`, `ACCOUNT`. 카드·계좌 지정은 해당 선택을 지원하는 수단에만 사용 |
| `scenarios` | 필수 배열. `SUCCESS`, `AUTH_CANCEL`, `BLOCKED` |
| `expectedReason` | `BLOCKED`의 필수 문자열. 기대하는 차단 사유 |

```dotenv
PAYMENT_TEST_COMBINATION_MODE=MAPPED
PAYMENT_TEST_CASES_JSON='[{"productId":"PRODUCT_ID","methodIds":["50","51","55","59"],"quantity":1,"options":{},"productType":"AUTO","instrument":"AUTO","scenarios":["SUCCESS"]}]'
PAYMENT_TEST_EXECUTION_MODE=PARALLEL
PAYMENT_TEST_MAX_TABS=4
PAYMENT_TEST_SESSION_MODE=AUTO
```

- `MAPPED`에서는 기존 상품·수단·수량·옵션 목록과 합치지 마라.
- 각 행의 수단 × 시나리오를 조합으로 확장하라. 조합별 독립 주문번호를 사용하라.
- 중복 조합은 한 번만 실행하라. 상품·수량·옵션·수단·선택 카드/계좌 구분·시나리오로 중복을 판단하라.
- 빈 매핑·잘못된 JSON·알 수 없는 설정값은 실행 전에 보고하라. 기존 목록으로 대체하지 마라.
- `ALL`은 기존 상품·수단 목록과 공통 수량·상품별 옵션을 사용하라. 시나리오는 `SUCCESS`로 설정하라.
- 조합 모드가 없으면 `RANDOM`을 사용하라. 실행 설정이 없으면 `PARALLEL`, 동시 조합 수 `4`, 세션 `AUTO`를 사용하라.
- 병렬 요청과 `SEQUENTIAL` 또는 동시 조합 수 `1`이 충돌하면 충돌을 안내하라. 병렬 실행에 필요한 설정을 확인하라.
- 실행 순서는 `PAYMENT_TEST_EXECUTION_ORDER`를 따르라. 병렬 실행에서는 준비 순서로 사용하라.
- 수단 미노출은 환경파일의 제외 정책을 따르라. 다른 수단으로 대체하지 마라.

## 실행 시 무작위 매핑

- `RANDOM`은 `PAYMENT_TEST_PRODUCT_IDS`와 `PAYMENT_TEST_METHOD_IDS`를 후보로 사용하라. `PAYMENT_TEST_CASES_JSON`은 사용하지 마라.
- 새 실행마다 후보의 중복을 제거하라. 사용자가 수단을 제한하면 해당 후보에 먼저 적용하라.
- 상품별 공통 수량과 옵션은 `PAYMENT_TEST_QUANTITY`, `PAYMENT_TEST_PRODUCT_OPTIONS_JSON`에서 읽어라.
- 주문서에서 구매 가능 여부·옵션·수단 노출·최소금액·상품 제한을 확인하라. 이 단계에서는 결제를 제출하지 마라.
- 각 결제수단마다 실행 가능한 상품 후보 중 하나를 균등 무작위로 선택하라. 결제수단별 한 조합을 실행하라.
- `Get-Random` 또는 실행 도구의 난수 API를 사용하라. 임의 판단으로 상품을 선택하지 마라.
- 서로 다른 결제수단이 같은 상품을 선택할 수 있다. 상품 후보가 하나면 해당 상품을 사용하고 무작위 선택 여지가 없음을 보고하라.
- 실행 가능한 상품이 없는 수단은 제외 정책에 따라 `SKIP`하거나 실행을 중단하라. 후보 밖 상품·수단을 사용하지 마라.
- 무작위 매핑의 시나리오는 `SUCCESS`, 선택 카드/계좌 구분은 `AUTO`로 설정하라. 실패·차단 시험을 무작위로 추가하지 마라.
- 모든 추첨을 마친 뒤 조합의 준비 순서를 무작위로 섞어라. `RANDOM`에서는 `PAYMENT_TEST_EXECUTION_ORDER`보다 이 순서를 우선하라.
- 첫 결제 제출 전에 확정 매핑과 실행 순서를 `results.json`에 저장하고 채팅에 안내하라. 매핑 안내를 별도 승인 요청으로 처리하지 마라.
- 실행 결과에는 후보 상품·수단과 제외 사유를 함께 기록하라. 인증값과 환경파일 원문을 저장하지 마라.
- 같은 실행을 재개하면 저장된 매핑과 순서를 사용하라. 재추첨하거나 실패 조합을 다른 상품으로 바꾸지 마라.
- `새로` 요청은 새 실행 ID와 새 추첨을 사용하라. 이전 실행의 미확정 거래는 먼저 확인하라.

## 시나리오와 판정

| 시나리오 | 동작 | 통과 조건 |
| --- | --- | --- |
| `SUCCESS` | 정상 인증과 결제 진행 | 완료 화면과 주문 재조회에서 상품·수량·수단·금액·결제완료 상태 일치 |
| `AUTH_CANCEL` | PG가 제공하는 취소 버튼으로 인증 취소 | 취소 안내·화면 복원·버튼 복구 확인, 주문 재조회에서 결제완료가 아님을 확인 |
| `BLOCKED` | 지정 제한 조건에서 결제 시도 | 기대 사유 표시, 후속 PG 요청 중단, 결제완료 주문 미생성 확인 |

- `AUTH_CANCEL`은 임의 비밀번호나 인증 실패를 유도하지 마라. 사용자 앱에서 취소가 필요하면 개입을 요청하라.
- 기대한 차단과 인증 취소는 `PASS`로 기록하라. 시나리오와 관측 결과를 함께 남겨라.
- 후속 요청 중단을 확인할 수 없으면 차단 시나리오를 통과로 처리하지 마라.
- 과면세·공개키·프로모션 전달값은 관측 가능한 요청과 응답으로 확인하라. 화면 결과만으로 통과 처리하지 마라.
- 최소금액·포인트·프로모션 경계는 해당 조건을 구성할 실행값이 있을 때만 추가하라.
- 클레임은 원주문과 신청 유형이 명시된 별도 실행 조건이 필요하다. 일반 주문 매핑으로 클레임을 생성하지 마라.

## 단일 창의 여러 탭 병렬 실행

- 브라우저 창 하나를 사용하라. 각 조합과 새 시도는 같은 창의 새 탭에서 시작하라.
- 사용자가 제공한 `base URL`을 시작 주소로 사용하라. 제공하지 않았으면 `PAYMENT_TEST_BASE_URL`을 사용하라.
- 각 새 탭에서 시작 주소에 접속한 뒤 실제 상품·장바구니 경로로 주문서를 준비하라.
- 기존 주문완료 화면을 새 주문의 시작점이나 다른 조합의 성공 증빙으로 사용하지 마라.
- 동시 조합 수는 진행 중인 조합의 한도다. PG 팝업과 복귀 탭은 원래 조합에 포함하라.
- 인증 대기·실패·불명확한 탭을 보존하라. 동시 조합 한도 안에서 추가 조합을 진행할 수 있으면 새 탭을 계속 추가하라.
- PG가 별도 팝업 창을 강제하면 원래 조합에 연결하라. 이를 다른 조합의 실행 창으로 사용하지 마라.
- `AUTO`는 프로젝트 사양·요청 코드·검증 결과로 공유 세션의 주문정보 분리를 확인하라.
- 공유 안전성을 입증하지 못하면 같은 창에서 독립 세션을 지원하는지 확인하라. 탭 분리만으로 세션 격리를 판정하지 마라.
- `ISOLATED`는 같은 창에서 지원하는 독립 세션 기능을 사용하라. 세션별 로그인 상태를 확인하라.
- 단일 창에서 병렬 안전성을 확보하지 못하면 제약을 보고하라. 병렬 결제 제출을 보류하라.
- 응답 대기 중에는 다른 독립 탭을 진행하라. 한 조합의 종료까지 다른 모든 조합을 대기시키지 마라.
- 사용자 인증은 [사용자 인증 대기](../SKILL.md#사용자-인증-대기)를 따라라. 인증 완료를 확인한 뒤 같은 탭에서 재개하라.
- PIN은 환경파일의 지정값을 사용하라. 현재 가상키패드 배치를 확인하고 입력하라.
- `SUBMITTED`, `AUTH_REQUIRED`, `UNKNOWN` 주문은 재조회부터 수행하라. 불명확한 거래를 신규 주문으로 재시도하지 마라.
- 기대 결과와 증빙을 확보한 성공 조합의 생성 탭만 닫아라. 사용자 기존 탭과 결과가 불명확한 탭을 보존하라.

## 결과 보고와 실패 재실행

- 모든 조합에 고정 `caseId`를 부여하라. 재실행에서도 상품·수량·옵션·수단·선택 카드/계좌 구분·시나리오를 유지하라.
- `results.json`에 조합별 `attempts` 배열을 저장하라. 시도마다 `attemptId`·시작/종료 시각·상태·주문번호·금액·실패 단계·사유·증빙 경로를 기록하라.
- 상태가 바뀔 때마다 결과를 저장하라. 기존 시도를 덮어쓰거나 삭제하지 마라.
- 전체 완료와 실행 중단 모두 `report.md`를 생성하라. 총 조합 수와 상태별 건수, 요청/실제 동시 실행 수를 기록하라.
- 조합별 최신 시도를 표 하나로 보고하라. `caseId`·상품·수단·시나리오·상태·주문번호·금액·실패 사유·재실행 가능 여부를 포함하라.
- 실패 시 실제 요청에 적용한 `PG_TYPE`을 결과와 리포트에 기록하라. 설정 후보 목록에서 추측하지 마라.
- `PG_TYPE` 대신 클라이언트키를 보고하면 SDK 공개 클라이언트키만 사용하라. 시크릿키·토큰·인증값은 기록하지 마라.
- PG 호출 전에 실패했거나 적용값을 확인하지 못하면 해당 사유를 기록하라.
- 리포트에 이전 시도의 상태와 증빙 링크를 남겨라. 채팅에는 결과 요약과 결과 파일 링크를 제공하라.
- `FAIL` 조합이 있으면 실행 ID를 포함한 `$ct-test-ui-order 실패만 재실행 <run-id>` 명령을 안내하라.
- 실패 결과를 보고한 뒤 사용자의 확인과 명시적인 재실행 요청을 기다려라. 실패 감지나 원인 해소만으로 재실행하지 마라.
- 실패 재실행 요청에서는 해당 실행의 `FAIL` 조합만 선택하라. 성공·제외·미완료 조합을 포함하거나 무작위 매핑을 다시 추첨하지 마라.
- 기존 주문을 먼저 재조회하라. 미결제·취소·실패가 확정되고 원인이 해소된 조합만 재실행 가능으로 판정하라.
- 이미 결제된 주문은 재결제하지 마라. 결과 불일치와 기존 증빙을 유지하고 재실행 불가 사유를 보고하라.
- 주문 상태를 확인하지 못하면 `UNKNOWN`으로 기록하라. 신규 결제 제출을 보류하라.
- 재실행마다 새 `attemptId`와 별도 주문번호를 사용하라. 사용자 요청 한 번에 조합별 한 번만 재실행하라.
- 재실행에도 동시 실행 한도와 세션 격리 기준을 적용하라. 다시 실패하면 결과를 보고하고 자동 반복을 중단하라.
- 재실행 후 최신 상태별 건수와 최초/재실행 결과를 리포트에 반영하라. 원인이 남은 조합은 보류 사유를 기록하라.
