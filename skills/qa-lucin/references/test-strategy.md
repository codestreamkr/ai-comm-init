# 테스트 전략

## 목적

기능 요청을 받았을 때 어떤 레벨의 테스트를 먼저 둘지 판단한다. 루신은 무조건 E2E부터 가지 않는다. 빠르게 실패를 잡을 수 있는 레벨과 실제 사용자 흐름을 검증해야 하는 레벨을 나눠서 본다.

## 기본 원칙

- 변경 범위를 UI 계층, 서비스 계층, 데이터베이스 계층으로 나눈다.
- 회귀 위험이 큰 지점을 먼저 막는다.
- 같은 위험을 더 싸게 막을 수 있으면 낮은 레벨 테스트를 우선한다.
- 사용자 흐름에서만 드러나는 문제는 E2E로 본다.
- 상태 코드, 권한, 응답 구조는 엔드포인트 테스트로 먼저 고정한다.
- 영향이 큰 기능은 엔드포인트와 E2E를 같이 둔다.
- 자동화가 목적이 아니라 반복 가능한 검증과 위험 감소가 목적이다.
- 모든 테스트 기술을 수행하지 않고 사용자 영향, 장애 가능성, 반복 검증 가치를 기준으로 고른다.
- 둘 다 필요한 경우의 자세한 순서는 아래 섹션을 따른다.

## 풀스택 테스트 기술

루신은 필요한 테스트 기술만 선택한다.

- 모바일 테스트:
  - 모바일 브라우저, 반응형 화면, 터치 조작, 기기별 제약을 확인한다.
- 수동 탐색적 테스트:
  - 요구사항에 드러나지 않은 예외 흐름, 비정형 사용자 행동, UX 결함을 찾는다.
- 자동화된 기능 테스트:
  - 주요 사용자 흐름, API 계약, 회귀 가능성이 높은 기능을 반복 검증한다.
- 지속적 테스트:
  - CI, 배포 전 검증, 변경 영향 범위 확인에 필요한 테스트를 설계한다.
- 데이터 테스트:
  - 저장값, 조회값, 상태 전이, 마이그레이션, 정합성 오류를 확인한다.
- CFR 테스트:
  - Cross Functional Requirement 관점으로 안정성, 호환성, 운영 요구를 확인한다.
  - 프로젝트에서 CFR 정의가 따로 있으면 해당 정의를 우선한다.
- 시각적 테스트:
  - 레이아웃 깨짐, 겹침, 잘림, 색상 대비, 컴포넌트 상태 표시를 확인한다.
- 보안 테스트:
  - 인증, 인가, 입력값 검증, 민감정보 노출, 권한 우회를 확인한다.
- 성능 테스트:
  - 응답 시간, 병목, 대량 데이터, 동시성, 화면 렌더링 지연을 확인한다.
- 접근성 테스트:
  - 키보드 조작, 포커스 이동, 스크린리더, 명도 대비, 의미 있는 마크업을 확인한다.

## 계층별 판단 기준

루신은 변경 대상을 계층별로 나누어 위험을 판단한다.

### UI 계층

사용자가 직접 보는 화면과 조작 흐름을 검증한다.

- 대상:
  - 화면
  - 컴포넌트
  - 브라우저
  - 모바일 화면
  - 사용자 입력과 조작
- 우선 테스트:
  - 모바일 테스트
  - 수동 탐색적 테스트
  - 자동화된 기능 테스트
  - 시각적 테스트
  - 접근성 테스트
  - 성능 테스트 일부
  - 보안 테스트 일부
- 확인 기준:
  - 사용자가 주요 흐름을 완료할 수 있는가
  - 화면 깨짐, 겹침, 잘림이 없는가
  - 모바일과 데스크톱에서 사용할 수 있는가
  - 키보드와 보조 기술로 조작할 수 있는가
  - 민감정보가 화면에 노출되지 않는가

### 서비스 계층

API와 비즈니스 규칙이 안전하게 동작하는지 검증한다.

- 대상:
  - Controller
  - API
  - Service
  - 외부 연동
  - 인증과 인가
  - 비즈니스 규칙
- 우선 테스트:
  - 자동화된 기능 테스트
  - 지속적 테스트
  - CFR 테스트
  - 보안 테스트
  - 성능 테스트
  - 수동 탐색적 테스트 일부
- 확인 기준:
  - API 계약이 지켜지는가
  - 정상, 예외, 경계 조건이 처리되는가
  - 권한 없는 요청이 차단되는가
  - 외부 연동 실패가 안전하게 처리되는가
  - CI에서 반복 검증할 수 있는가

### 데이터베이스 계층

데이터 저장과 상태 전이가 정확한지 검증한다.

- 대상:
  - 테이블
  - 쿼리
  - 트랜잭션
  - 상태값
  - 데이터 정합성
  - 마이그레이션
- 우선 테스트:
  - 데이터 테스트
  - 자동화된 기능 테스트
  - 지속적 테스트
  - 성능 테스트
  - 보안 테스트 일부
- 확인 기준:
  - 저장, 수정, 삭제 결과가 정확한가
  - 상태 전이가 도메인 규칙과 맞는가
  - 트랜잭션 경계가 안전한가
  - 중복, 누락, 불일치 데이터가 생기지 않는가
  - 대량 데이터에서도 쿼리가 감당 가능한가

## 우선순위 판단 기준

### 위험이 큰 기능

- 생성, 수정, 삭제, 승인, 결제, 정산
- 권한에 따라 결과가 달라지는 기능
- 화면과 API가 동시에 바뀐 기능
- 데이터 저장 구조나 상태 전이가 바뀐 기능
- 장애 재발 이력이 있는 기능

이 경우 둘 다 검토한다.

### 화면만 바뀐 경우

- UI 계층 중심으로 본다.
- 시각적, 모바일, 접근성, 수동 탐색적 테스트를 우선한다.
- 주요 사용자 흐름이 바뀌었으면 Playwright E2E를 검토한다.

### API나 비즈니스 로직이 바뀐 경우

- 서비스 계층 중심으로 본다.
- 자동화된 기능, 보안, CFR, 지속적 테스트를 우선한다.
- 계약 검증이 핵심이면 엔드포인트 테스트를 먼저 둔다.

### 저장 구조나 쿼리가 바뀐 경우

- 데이터베이스 계층 중심으로 본다.
- 데이터, 성능, 트랜잭션, 회귀 테스트를 우선한다.
- 화면 테스트만으로 데이터 정합성 검증을 대체하지 않는다.

### 여러 계층이 함께 바뀐 경우

- 사용자 흐름 기준 E2E 테스트를 최소 1개 잡는다.
- 각 계층별로 더 작은 테스트를 배치한다.
- UI 테스트만으로 서비스와 데이터 검증을 대체하지 않는다.

### 엔드포인트 테스트가 더 효율적인 경우

- 입력 검증이 복잡하다.
- 상태 코드 조합이 많다.
- 권한 조합이 많다.
- 브라우저 없이 빠르게 확인할 수 있다.
- 프론트보다 백엔드 계약 안정화가 먼저다.

### E2E 테스트가 더 필요한 경우

- 로그인부터 완료까지 흐름이 중요하다.
- 필터, 폼, 모달, 테이블, 라우팅, 세션이 같이 움직인다.
- 브라우저 상호작용에서만 문제를 볼 수 있다.
- 프론트와 백엔드가 붙었을 때만 오류가 드러난다.

## 선택 규칙

### 엔드포인트만 두는 경우

- API 계약 검증이 핵심이고, UI 흐름 위험은 낮다.
- 빠른 회귀 보호가 더 중요하다.

### E2E만 두는 경우

- 내부 API가 이미 안정적이고, 실제 사용자 흐름 검증이 핵심이다.
- 화면 상호작용과 상태 변화가 주요 리스크다.

### 둘 다 두는 경우

- 기능 영향이 크다.
- API와 UI가 함께 바뀌었다.
- 같은 장애가 다시 나올 가능성이 높다.
- 낮은 레벨과 높은 레벨에서 모두 의미 있는 실패 지점이 있다.

## 둘 다 필요한 경우의 순서

1. 엔드포인트 테스트로 상태 코드, 권한, 검증 로직, 응답 구조를 먼저 고정한다.
2. 빠르게 실패해야 하는 계약 지점을 먼저 막는다.
3. 이후 E2E 테스트로 실제 화면 흐름, 상태 반영, 프론트-백 연동을 검증한다.

## 최소 세트 권장안

### 엔드포인트 테스트 최소 세트

- 정상 요청 1건
- 대표 입력 검증 실패 1건 이상
- 권한 실패 1건 이상
- 주요 응답 필드 검증

### E2E 테스트 최소 세트

- 대표 정상 흐름 1건
- 대표 실패 흐름 1건 또는 상태 변화 검증 1건
- 저장 후 화면 반영 확인

## 결과 정리 방식

- 왜 이 레벨을 선택했는지 분명히 적는다.
- 계층별 영향 범위를 적는다.
- 선택한 테스트 기술과 제외한 테스트 기술을 적는다.
- 자동화에서 제외한 항목은 이유를 남긴다.
- 직접 실행하지 못한 항목은 남은 위험으로 분리한다.
