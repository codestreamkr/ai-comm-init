# CT Design Review

구현 전에 여러 관점의 합의가 필요한 설계안을 의사결정 문서로 정리한다.

## 입력 정리

먼저 공통 브리프를 작성한다.

- 검토 대상
- 요청 배경과 목표
- 입력, 출력, 주요 동작
- 기능 성격
- 초기 핵심 쟁점 3~7개

사용자가 준 사실, 합리적 가정, 미결정 정책을 구분한다.
사용자가 지정한 쟁점은 개수 제한 없이 모두 보존하고, 스킬이 새로 도출하는 초기 쟁점만 3~7개로 제한한다.

## 필수 참조

필요한 파일만 처음부터 끝까지 읽는다.

1. 항상 `references/selection-rules.md`를 읽고 전문가와 검토 단계를 선정한다.
2. 선정한 역할의 `references/experts/{role}.md`만 읽고 역할별 판단 기준과 출력 항목을 적용한다.
3. 문서 작성 전에 `references/document-template.md`를 읽고 파일명, 목차와 작성 형식을 적용한다.

정본 책임은 아래처럼 나눈다.

- `selection-rules.md`: 전문가 후보군, 선정 조건, 1차·후행·최종 조정 순서
- `experts/*.md`: 해당 역할의 판단 기준과 의견 출력 형식
- `document-template.md`: 결과 문서의 파일명, 목차와 섹션 작성 형식
- `SKILL.md`: 입력 정리, 실행 순서, 완료 조건

## 실행 절차

### 1. 프리패스

- 공통 브리프와 기능 성격 태그를 확정한다.
- 검토 축의 공백을 확인한다.
- 1차 전문가와 후행 전문가를 선정한다.
- 선정 근거를 역할별로 기록한다.

### 2. 1차 검토

- 제품, 도메인, 백엔드, 프론트엔드·UX 등 독립 검토가 가능한 역할을 먼저 검토한다.
- 각 1차 전문가는 동일한 공통 브리프만 받고 다른 1차 전문가의 의견을 보지 않은 상태에서 판단한다.
- 세션 정책이 Agent 위임을 허용하면 독립 검토를 병렬로 진행한다.
- 직접 검토 환경에서는 각 의견을 독립적으로 먼저 작성하고, 모든 1차 의견이 끝난 뒤에만 서로 비교한다.
- 각 의견은 선택한 expert reference의 출력 형식을 따른다.
- 고위험 안건은 기능 영향 근거로 1차·후행 검토에 선정된 모든 역할의 출력에 `권장안`, `대안과 제외 이유`, `필요한 선행 산출물`을 추가한다.

### 3. 후행 검토

- 1차에 포함되지 않은 QA, 보안, SRE 등 선행 의견이 필요한 역할은 1차 검토 이후 진행한다.
- 선정 규칙의 후행 트리거가 맞을 때만 추가한다.
- 1차에 이미 포함된 역할은 후행에서 제외하고 1차 의견만 유지한다.
- 추가 위험, 검증 게이트, 운영 모델, 관측 포인트를 보강한다.

### 4. 조정

`tech-lead` 기준으로 아래를 확정한다.

- 충돌 지점과 조율 결과
- 채택안과 제외·보류안
- 선택 이유
- 권장 구현 순서와 단계별 이유
- 고위험 단계별 검증 방법, 통과 기준과 다음 단계 진입·중단 기준
- 각 단계가 다음 단계의 위험을 낮추는 방식
- 성공 기준과 재검토 기준
- 미결정 정책과 외부 합의

결론은 사용자 가치, 구현 현실성, 품질 위험, 운영 영향의 비교 근거로 확정한다.

### 5. 문서 작성

- 토론 로그가 아니라 최종 결정만 작성한다.
- `references/document-template.md`의 섹션 순서를 따른다.
- 미결정 사항은 `남은 이슈`, 실행 항목은 `다음 단계`에 둔다.
- 고위험 안건은 운영 모델, 선행 산출물, 단계별 성공 기준, 검증 방법과 다음 단계 진입·중단 기준을 포함한다.
- 실제 검증 결과는 검증을 수행하고 근거를 확인한 경우에 기록한다. 설계 단계에서는 `미실행`과 실행 주체를 적는다.
- 고위험 단계마다 해당 단계가 다음 단계의 위험을 어떻게 낮추는지 설명한다.
- 정책 판정이 핵심이면 별도 판정표 필요 여부를 명시한다.

## 출력

- 기본 출력: `.docs/plans/{topic_slug}_design_review.md`
- 사용자가 경로와 파일명을 지정하면 대상 동일성을 확인한 뒤 해당 위치에 설계 결정 문서를 작성한다.
- 짧은 의견 질문은 이 스킬의 대상이 아니며 대화 답변으로만 처리한다.

`topic_slug`와 대상 동일성은 아래 기준으로 확정한다.

- `topic_slug`: 사용자가 지정한 topic이나 검토 대상명을 Unicode NFKC로 정규화하고, 공백과 경로 구분자는 `_`로 바꾼다. 한글·영문·숫자·`_`·`-`만 유지하고 연속 `_`는 하나로 합치며 영문은 소문자로 바꾼다.
- 정규화 결과가 비어 있으면 사용할 topic을 사용자에게 한 번 확인한다. 공용 `design_review.md`는 사용하지 않는다.
- `target_key`: 공통 브리프의 검토 대상을 대상 종류, 이름과 주요 경계가 드러나는 한 줄로 만든 뒤 Unicode NFKC 정규화, 앞뒤 공백 제거, 연속 공백 축소와 영문 소문자화를 적용한 문자열이다.
- `target_hash`: `target_key`의 SHA-256 소문자 16진수 값
- `target_hash8`: `target_hash`의 앞 8자리이며 문서의 대상 식별자와 기본 충돌 회피 접미사로 사용한다.
- 문서의 `검토 대상`에 `topic_slug`와 대상 식별자를 기록하고 갱신 시 현재 브리프와 대조한다.

사용자 지정 파일은 아래 순서로 갱신 또는 신규 경로를 확정한다.

1. 파일이 없으면 지정 경로에 신규 작성한다.
2. 파일이 있으면 대상 식별자와 `검토 대상`을 현재 브리프와 대조한다.
3. 동일 대상이면 지정 파일을 갱신한다.
4. 대상 동일성을 확인할 수 없으면 지정 파일의 사용 여부를 사용자에게 한 번 확인한다.
5. 다른 대상이면 지정 파일을 덮어쓰지 않는다. 사용자가 기존 파일의 정확한 사용을 명시했으면 한 번 확인하고, 그렇지 않으면 같은 디렉터리에 `{지정 파일 stem}_{target_hash8}.md`를 신규 경로로 사용한다.
6. 신규 경로도 다른 대상이 사용 중이면 hash 길이를 12, 16자리, 전체 `target_hash` 순서로 늘리고, 전체 hash도 충돌하면 `_2`, `_3`처럼 가장 작은 미사용 순번을 붙인다.

경로를 지정하지 않은 요청은 아래 순서로 기존 결과와 신규 경로를 확정한다.

1. 아래 순서로 후보 문서를 수집하고 같은 실제 경로는 한 번만 취급한다.
   - `.docs/plans/{topic_slug}_design_review.md`
   - `.0_my/plans/{topic_slug}_design_review.md`
   - 작업 루트의 legacy 파일 `{topic_slug}_design_review.md`
   - 저장소 전체의 `*_design_review.md`
2. 저장소 전체 탐색은 `.git`, 빌드 산출물과 외부 의존성 디렉터리를 제외한다.
3. 후보를 동일 대상, 같은 slug의 불일치 대상, 관련 없는 대상, 동일성 확인 불가로 분류하고 관련 없는 문서는 갱신 후보에서 제외한다.
4. 대상 식별자와 `검토 대상`이 현재 브리프와 같은 문서가 하나면 해당 문서를 갱신한다.
5. 동일 대상 문서가 여러 개이거나 관련 가능성이 있는 문서의 대상 동일성을 확정할 수 없으면 후보 경로와 판정 근거를 제시하고 사용할 문서를 사용자에게 한 번 확인한다.
6. 같은 slug의 불일치 문서만 있으면 모두 보존하고 `.docs/plans/{topic_slug}_{target_hash8}_design_review.md`를 신규 경로로 사용한다.
7. hash8 경로도 다른 대상이 사용 중이면 hash 길이를 12, 16자리 순서로 늘리고, 16자리도 충돌하면 전체 `target_hash`를 사용한다. 전체 hash 경로도 불일치 문서가 사용 중이면 `_2`, `_3`처럼 가장 작은 미사용 순번을 붙인다.
8. 기존 문서가 없으면 `.docs/plans/`를 만들고 `.docs/plans/{topic_slug}_design_review.md`를 신규 작성한다.

생성 문서 끝에는 `## 이력관리`를 둔다.

저장 후 `검토 대상`, `참여 전문가`, `최종 결론`, `최종 저장 경로`를 짧게 보고한다.

## 완료 조건

- 전문가 선정 근거가 기능 성격과 연결된다.
- topic slug와 대상 식별자가 기록되고 갱신 대상과 일치한다.
- 초기 쟁점과 추가 쟁점이 구분된다.
- 충돌 조율 결과와 선택 이유가 남아 있다.
- 채택안, 제외·보류안, 성공 기준, 재검토 기준이 있다.
- 구현 순서에는 단계별 이유가 포함된다.
- 남은 이슈와 다음 단계가 분리됐다.
- 문서 끝에 이력관리가 있다.

요청 성격에 따라 아래 완료 게이트를 추가한다.

- 고위험 안건: 제외한 고위험 대안의 이유, 필요한 선행 산출물, 단계별 검증 방법과 통과 기준, 다음 단계 진입·중단 기준과 다음 단계 위험 감소 근거가 있다.
- 고위험 안건: 기능 영향 근거로 1차·후행 검토에 선정된 각 역할에 권장안, 대안과 제외 이유, 필요한 선행 산출물이 있다.
- 단계적 출시 안건: 릴리스 단계별 목적과 각 단계의 성공 기준이 있다.
- 정책 판정 안건: 판정표 필요 여부가 명시되고, 필요하면 판정 대상과 확인 주체가 있다.
- 외부 연동 안건: 실패 시 기본 동작, 재시도·재처리·수동 정리 기준, 운영 모델과 관측 포인트가 있다.

- 2026-07-13: 짧은 의견 질문을 출력 대상에서 제외하고 selection, expert, template의 정본 책임, 사용자 지정 쟁점 보존, 기능 영향 근거에 따른 1차·후행 역할 선정과 중복 제거, topic slug·대상 hash 기반 기본·사용자 지정 파일의 대상 동일성 검증과 충돌 방지, legacy 문서 호환, 저장 결과 보고, 고위험 역할별 대안·선행 산출물과 단계별 검증 방법·통과·진입·중단 게이트를 정리했다.
