# 설계 검토 문서 템플릿

## 구성

- 파일명과 필수 목차
- 전문가별 의견 형식
- 최종 결론과 권장 구현 방향
- 작성 기준

## 파일명 규칙

- 사용자가 파일명을 지정하면 그대로 사용한다.
- 지정하지 않으면 `SKILL.md`에 정의된 `.docs/plans/`, `.0_my/plans/`, 작업 루트와 저장소 전체의 후보 탐색 순서로 갱신 대상을 먼저 확정한다.
- 기존 문서가 없으면 `.docs/plans/{topic_slug}_design_review.md`로 저장한다.
- `topic_slug`를 확정할 수 없으면 사용자에게 한 번 확인하며 공용 `design_review.md`는 사용하지 않는다.
- 같은 slug의 다른 대상 문서가 있으면 기존 파일을 보존하고 `SKILL.md`의 대상 hash 길이 확장 규칙으로 충돌 없는 신규 경로를 사용한다.

## 작성 기준

- `검토 대상`의 topic slug와 대상 식별자는 `SKILL.md`의 정규화와 SHA-256 규칙으로 작성하고 기존 문서의 대상 동일성 판정에 사용하라.
- `기능 요약`에는 입력, 출력, 주요 동작 범위를 짧게 적어라.
- `기능 성격 분류`에는 분류 결과와 그 이유를 3줄 이내로 적어라.
- `참여 전문가`는 섹션 4의 분류 결과와 연결되도록 `선정 근거`를 적어라.
- `핵심 쟁점`은 초기 쟁점과 검토 중 추가된 쟁점을 구분하라.
- 사용자가 지정한 쟁점은 모두 보존하고 새로 도출하는 초기 쟁점만 3~7개로 제한하라.
- 고위험 안건은 기능 영향 근거로 1차·후행 검토에 선정된 모든 역할 의견에 `권장안`, `대안과 제외 이유`, `필요한 선행 산출물`을 추가하라.
- `권장 구현 방향`은 개발팀이 바로 참고할 수 있게 범위와 우선순위를 적어라.
- `단계별 구현 순서와 이유`에는 순서와 선행 이유를 함께 적어라.
- 고위험 안건은 각 단계의 검증 방법과 통과 기준, 다음 단계 진입·중단 기준과 다음 단계 위험 감소 근거를 함께 적어라.
- 실제 검증 결과는 검증을 수행하고 근거를 확인한 경우에 기록하라. 설계 단계에서는 `미실행`과 실행 주체를 적어라.
- 단계적 출시가 필요한 안건은 `릴리스 단계 구분`과 `단계별 성공 기준`을 함께 적어라.
- 외부 연동, 정합성, 정산, 비동기 후처리, 운영 복잡도가 큰 안건은 `권장 구현 방향`에 운영 모델 권장안을 반드시 적어라.
- `제품 관점 성공 기준`은 운영 비용, 사고 예방, 대응 시간 단축, 사용자 혼선 감소처럼 제품/운영 관점에서 확인 가능한 기준으로 적어라.
- `성공 기준`은 설계 채택 후 어떤 상태가 되면 성공으로 볼지 적고, `재검토 기준`은 어떤 증상이나 조건이 보이면 다시 판단할지 적어라.
- 실패 처리, 재시도, 수동 정리, 중복 요청 판정이 핵심인 안건은 후속 산출물을 `판정표` 하나로 묶어 적는 방식을 우선하라.
- `남은 이슈`와 `다음 단계`를 섞지 말고, 미해결 사항과 실행 액션을 분리하라.
