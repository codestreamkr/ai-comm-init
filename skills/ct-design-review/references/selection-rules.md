# 전문가 선정 규칙

## 검토 축

전문가 선정 전에 아래 축의 공백을 확인한다.

- 제품·범위: 사용자 가치, MVP, 제외 범위
- 정책·도메인: 업무 규칙, 예외, 판정표 필요 여부
- 데이터·API: 요청·응답, 상태 전이, 저장 구조, 호환성
- 화면·상태: 사용자 흐름, 입력, 빈 상태, 오류, 클라이언트 상태
- 검증: 성공 기준, 회귀 위험, QA 게이트
- 보안: 권한, 민감정보, 입력 검증, 오남용
- 운영: 배포, 장애, 재처리, 관측, 롤백
- 외부 경계: webhook, callback, queue, third-party API

## 후보군

| 전문가 | 기본 역할 |
|--------|-----------|
| product | 사용자 가치, 범위, 우선순위 판단 |
| domain | 업무 규칙, 정책, 현업 맥락 검토 |
| backend | 서버 구조, 데이터/API 흐름, 확장성 검토 |
| frontend-ux | 사용자 흐름, 화면 구조, 입력/오류 경험 검토 |
| qa | 테스트 전략, 회귀 위험, 검증 기준 검토 |
| security | 권한, 민감정보, 오남용 위험 검토 |
| sre | 배포, 장애 영향, 운영 복잡도 검토 |
| tech-lead | 충돌 정리와 최종 결론 도출 |

| 업무 정책 해석 충돌, 규정/정책 의존 로직 | domain |

## 고위험 판정

아래 항목이 하나 이상 확인되면 고위험 안건으로 분류한다.

- 결제, 정산, 인증, 권한 또는 개인정보 처리
- 외부 승인 성공 후 내부 저장·상태 반영처럼 부분 실패가 가능한 흐름
- 비가역 상태 변경, 대량 데이터 변경 또는 복구 절차가 필요한 마이그레이션
- 장애가 다른 서비스로 전파되거나 수동 재처리가 필요한 외부 연동·비동기 처리
- 서비스 중단, 데이터 정합성 훼손 또는 보안 사고로 이어질 수 있는 배포 변경

모든 1차·후행 역할은 해당 기능에 미치는 영향 근거가 확인된 경우에만 선정한다. 고위험 안건은 이렇게 선정된 모든 1차·후행 역할에 `권장안`, `대안과 제외 이유`, `필요한 선행 산출물`을 추가한다. 실제 검증을 수행하지 않은 설계 단계에서는 검증 방법, 통과 기준과 중단 기준을 작성한다.

## 선정 절차

1. 기능 요약에서 입력, 출력, 주요 동작 범위를 정리하라.
2. 기능 성격 분류에서 아래 태그 중 필요한 것을 고르라.
   - `crud`
   - `workflow`
   - `ui`
   - `api`
   - `policy`
   - `security-sensitive`
   - `ops-sensitive`
   - `external-integration`
3. 성격 태그와 기능 영향 근거로 1차 전문가를 선정하고 역할별 근거를 기록하라.
4. 후행 검토 트리거와 기능 영향 근거에 해당하는 전문가를 추가하되, 1차에 이미 포함된 역할은 후행에서 제외하고 1차 배정을 유지하라.
5. 항상 `tech-lead`를 마지막 조정자로 포함하라.

## 단계 운영 권장안

- 1차: 기능 성격 표로 선택한 product, domain, backend, frontend-ux 역할을 포함한다. 보안/인증이 핵심이면 security, 외부 연동이 핵심이면 sre를 1차에 포함한다.
- 후행: qa, security, sre, domain 중 규칙에 맞는 역할 추가
- 최종 조정: tech-lead

## 병렬과 순차 사용 기준

- 1차 독립 검토는 병렬을 우선하라.
- 후행 검토는 1차 산출물을 본 뒤 순차로 진행하라.
- 세션 정책상 서브에이전트 위임이 불가능하면 단계는 유지하되 직접 작성하라.
