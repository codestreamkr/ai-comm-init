# CT Implement

## 목적

영향 범위가 넓은 구현을 코드 반영부터 전파 확인과 검증까지 일관되게 완료한다.

- 입력은 기능 설명, 개발문서, 개선 계획 문서, 설계 검토 문서를 허용한다.
- 운영 코드 구현과 연관 영향 수정을 함께 완료한다.
- 사용자가 별도 문서를 요청하지 않으면 중간 문서를 만들지 않는다.

## 협업 책임

여러 스킬이 함께 적용되면 각 스킬의 판단과 실행 책임을 분리한다.

- `external-architect`: 외부 연동 구조, 상태 전이, 실패 조건, 멱등성 기준과 테스트 시나리오를 정의한다.
- `spring`: 프로젝트 컨벤션에 맞는 Spring 구현 방식과 테스트 기술을 결정한다.
- `ct-implement`: 요구사항 해석, 영향 범위 확인, 코드 반영, 기본 검증과 요청된 테스트 실행을 통제한다.
- 다른 스킬이 테스트 포인트를 제시해도 사용자가 테스트를 요청하지 않으면 테스트 코드 작성과 실행으로 확장하지 않는다.

## 실행 원칙

판단은 이번 실행에서 확인한 코드와 문서를 근거로 한다.

- 입력에서 확정 요구사항, 합리적 가정, 미결정 정책을 구분한다.
- 계획 문서와 설계 검토 문서는 구현 요청과 함께 제공된 경우에만 구현 입력으로 사용한다.
- 설계 검토 문서의 `최종 결론`과 `권장 구현 방향`은 확정 방향으로 사용하고, `남은 이슈`는 미결정 항목으로 분류한다.
- 기존 반환 계약, 오류 처리, 로그 패턴은 변경 요구가 없으면 유지한다.
- 사용자 요청 범위를 임의로 축소하지 않는다.
- 핵심 영향 범위와 조치 판단은 `파일:라인` 또는 검색 결과로 역추적할 수 있게 한다.

## 진행 판단

명확한 구현 요청은 추가 승인 없이 실행한다.

- 사용자가 `수정해줘`, `구현해줘`, `반영해줘`, `고고`처럼 구현을 명시하고 기존 계약 안에서 처리할 수 있으면 바로 구현한다.
- 계획 문서나 설계 검토 문서가 입력이라는 이유만으로 추가 승인을 요청하지 않는다.
- 아래 미결정 사항이 구현 결과를 바꾸는 경우에만 사용자 확인을 받는다.
  - API 요청·응답 계약
  - 상태 전이
  - 저장 모델
  - 보상 처리
  - 외부 시스템 계약
- 사용자가 검토나 제안만 요청하면 코드를 수정하지 않는다.
- 한 번에 안전하게 완료하기 어려운 경우에만 독립적으로 완료 가능한 단계와 이유를 제시하고 범위를 합의한다.

## 실행 절차

아래 순서로 구현하고 최종 검증 이후에 결과를 보고한다.

1. 입력 해석
   - 기능, 제약, 예외와 완료 범위를 추출한다.
   - 복수 문서의 결론이 다르면 적용할 기준과 근거를 정한다.
2. 실행 가능 여부 판단
   - 바로 구현할 항목, 가정으로 진행할 항목, 확인이 필요한 미결정 항목을 구분한다.
3. 영향 범위 탐색
   - 서로 독립적인 영역은 병렬로 확인한다.
   - 변경과 관련된 진입점, 처리 로직, 호출 체인, 데이터 계약, 저장 경계, 변환 경계, 화면·상태 경계를 확인한다.
   - 큰 변경은 영향 범위 매트릭스, 작은 변경은 근거가 포함된 요약으로 정리한다.
4. 구현
   - 요구사항을 운영 코드에 반영한다.
   - 동일 정책을 사용하는 연관 경로를 함께 수정한다.
   - 필요한 경우에만 공통 검증 또는 공통 처리 구조를 도입한다.
5. 전파 보정
   - 필드의 생성, 전달, 변환, 저장, 응답 경로를 확인하고 누락을 보정한다.
   - 성공, 실패, 예외 처리 계약을 호출 경로 전체에서 일관되게 맞춘다.
   - 배치, 스케줄, 운영 API, callback, webhook, worker 등 보조 경로의 적용 여부를 확인한다.
6. 요구사항 차이 점검
   - 사용자와 합의한 기능, 제약, 예외, 로그, 순서, 반환 계약을 변경 내용과 비교한다.
   - 코드 미반영이나 전파 누락이 있으면 보완한 뒤 다시 점검한다.
7. 기본 검증
   - 기본 검증 정책에 따라 프로젝트 언어에 맞는 운영 코드 검증을 수행한다.
8. 조건부 테스트
   - 테스트가 명시적으로 요청된 경우에만 테스트케이스를 작성하거나 수정하고 실행한다.
9. 결과 보고
   - 모든 코드 보완과 검증을 마친 최종 상태만 보고한다.

## 기본 검증 정책

별도 테스트 요청이 없으면 운영 코드의 컴파일, 타입 검사 또는 구문 검사까지만 수행한다.

- 프로젝트의 `AGENTS.md`와 빌드·실행 기준 문서, 빌드 설정을 먼저 확인한다.
- 저장소에 명시된 검증 명령이 있으면 해당 명령을 우선한다.
- 테스트, 애플리케이션 실행, 외부 서비스 연결을 포함하지 않는 명령을 사용한다.
- 여러 언어가 섞인 저장소는 변경한 운영 코드가 속한 각 언어의 기본 검증을 수행한다.
- 기본 검증 이후 운영 코드를 수정하면 영향받는 검증을 다시 수행한다.

### 언어별 기본 검증

| 프로젝트 | 기본 검증 | 선택 기준 |
|---|---|---|
| Java·Kotlin | 운영 코드 compile 또는 classes task | Maven·Gradle 설정과 프로젝트 문서에 정의된 테스트 제외 명령을 사용한다. |
| TypeScript | 기존 typecheck script 또는 `tsc --noEmit` | 프로젝트의 `tsconfig`와 package script를 우선한다. |
| JavaScript | 기존 compile·typecheck script 또는 변경 파일 구문 검사 | 테스트와 bundle 실행을 포함하지 않는 명령만 사용한다. |
| Python | 대상 package·module의 bytecode cache를 만들지 않는 구문 검사 | 프로젝트가 제공하는 무부작용 정적 검증 명령이 있으면 우선하고, 없으면 AST parse 등 `.pyc`를 생성하지 않는 방식을 사용한다. |
| 기타 | 저장소가 정의한 운영 코드 compile·typecheck·syntax 명령 | 명령이 없으면 검증을 임의로 만들지 않고 미실행 사유를 보고한다. |

- 테스트를 포함할 수 있는 `build`, `check`, `verify`를 명령 내용을 확인하지 않고 기본 검증으로 사용하지 않는다.
- lint, formatter, 애플리케이션 기동은 컴파일·타입·구문 검사의 대체 수단으로 사용하지 않는다.

### 기본 검증 실패 처리

- 이번 변경으로 발생한 컴파일, 타입 또는 구문 오류는 원인을 수정하고 다시 검증한다.
- 기존 코드에서 발생한 오류는 이번 변경과의 관련성을 확인한다.
- 관련 없는 기존 오류를 수정하기 위해 요청 범위를 확장하지 않는다.
- 기존 오류로 검증을 완료하지 못하면 실행 명령, 실패 위치, 이번 변경과의 관련성을 보고한다.

## 조건부 테스트 정책

테스트 관련 표현이 명시된 요청만 테스트 요청으로 판단한다.

- 다음 요청이 있으면 테스트케이스 작성 또는 수정과 대상 테스트 실행을 수행한다.
  - 테스트케이스 작성
  - 단위 테스트
  - 통합 테스트
  - API 테스트
  - 회귀 테스트
  - 테스트 실행
  - 테스트로 검증
- `검증해줘`, `확인해줘`만 요청한 경우에는 프로젝트 언어에 맞는 기본 검증까지만 수행한다.
- 사용자가 기존 테스트 실행만 요청하면 테스트케이스를 추가하지 않고 지정된 테스트만 실행한다.
- 사용자가 테스트 범위를 지정하면 해당 범위만 작성하고 실행한다.
- 전체 테스트는 전체 회귀 테스트를 요청한 경우에만 실행한다.

### 테스트케이스 작성 기준

변경된 운영 동작을 검증하는 데 필요한 테스트만 작성한다.

1. 변경된 운영 코드의 진입점과 관찰할 결과를 확인한다.
2. 해당 진입점을 실행하는 기존 테스트와 검증 범위를 확인한다.
3. 기존 테스트 실행, 기존 기대값 수정, 기존 테스트에 케이스 추가, 신규 테스트 작성 중 필요한 조치를 선택한다.
4. 변경과 관련된 기존 테스트와 추가·수정한 테스트를 함께 실행한다.

테스트는 변경과 관련된 결과를 검증한다.

- 반환값
- 상태 변경
- 저장 결과
- 외부 호출
- 정상, 경계, 실패 또는 회귀 동작

다음 기준을 적용한다.

- 같은 진입점과 테스트 구성을 사용하면 기존 테스트에 케이스를 추가한다.
- 별도 책임이나 테스트 수준을 검증하면 신규 테스트 파일을 작성한다.
- 운영 책임이 이동하면 기존 검증을 변경된 운영 진입점에 연결한다.
- 프로젝트의 테스트 구조, 명명, fixture와 mocking 방식을 따른다.
- 외부 연동 테스트는 `external-architect`가 정한 시나리오와 계약을 적용한다.
- Spring 테스트는 `spring`이 정한 테스트 계층과 구현 방식을 적용한다.

### 외부 연동 테스트 3세트

외부 연동이 변경되고 테스트가 요청된 경우 세 경계의 필요성을 각각 판단한다. 세 파일을 일괄 생성하지 않는다.

| 테스트 경계 | 실행할 운영 코드 | 대체 경계 | 검증 목적 |
|---|---|---|---|
| 실제 연동 Integration | 실제 외부 Client와 HTTP 전송 | Service와 DB 제외 | 실제 인증, endpoint와 요청·응답 계약 |
| 외부 Client Unit | 실제 외부 Client | HTTP 전송만 Fake | URL, headers, body, 멱등 키와 응답 변환 |
| Service Unit | 실제 Service | 외부 Client와 저장 계층 Mock | 업무 검증, 상태 전이, 저장, 보상과 복구 |

- 프로젝트 관례가 맞으면 `*ExternalApiIntegrationTest`, `*ExternalApiClientUnitTest`, `*ServiceUnitTest` 이름을 사용한다.
- 외부 계약만 변경되면 외부 Client Unit을 우선하고 실제 환경 검증이 필요하면 Integration을 추가한다.
- 업무 규칙, 저장 또는 보상 흐름이 변경되면 Service Unit을 사용한다.
- 두 책임이 함께 변경되면 외부 Client Unit과 Service Unit을 각각 둔다.
- 실제 연동 Integration은 유효한 인증, endpoint와 테스트 데이터가 준비된 경우에만 실행한다.
- Fake와 Mock은 테스트 대상 밖의 경계만 대체하고 테스트 대상 운영 코드는 실제로 실행한다.
- 하드코딩한 성공값을 반환하고 같은 값만 확인하는 테스트는 작성하지 않는다.
- 기존 테스트가 같은 운영 책임을 검증하면 새 파일을 만들지 않고 유지하거나 필요한 케이스만 보완한다.

### 테스트 실행과 실패 처리

- 변경에 직접 관련된 테스트부터 실행한다.
- 테스트 실패가 구현 결함이면 운영 코드를 수정하고 기본 검증을 다시 수행한 뒤 테스트를 재실행한다.
- 요구사항 변경으로 기존 기대값이 달라진 경우에만 테스트 코드를 수정한다.
- 테스트 통과만을 목적으로 검증 조건이나 assertion을 완화하지 않는다.
- 이번 변경과 관련 없는 기존 테스트 실패는 수정하지 않고 실행 명령, 실패 테스트, 관련성 판단을 보고한다.

## 완료 기준

아래 기준을 충족한 경우에만 구현 작업을 완료로 보고한다.

- 요구사항 대비 운영 코드 미반영이 없다.
- 관련 호출 체인과 데이터 전달 경로의 전파 누락이 없다.
- 영향 범위의 적용·미적용 판단과 근거가 확인됐다.
- 프로젝트 언어에 맞는 운영 코드 기본 검증이 성공했다. 기존 오류로 실패한 경우에는 실패 근거와 변경 관련성을 확인했다.
- 테스트 요청이 있으면 기존 테스트 활용 여부를 판단하고 필요한 테스트 작성·수정과 실행 결과를 확인했다.
- 테스트 요청이 없으면 테스트 코드 작성과 실행을 수행하지 않았다.

## 결과 보고

핵심 결과를 먼저 짧게 보고한다.

- 변경 내용
- 변경 파일
- 영향 범위 반영 결과
- 기본 검증 명령과 결과
- 테스트 요청 여부와 수행 결과
- 보류 항목 또는 남은 위험

보고 항목은 실제 결과가 있는 경우에만 작성한다.

- 테스트 요청이 없으면 `테스트 미요청으로 미실행`으로 표시한다.
- 보류 항목이나 남은 위험이 없으면 해당 항목을 생략한다.
- 큰 변경에서만 영향 범위 매트릭스를 사용한다.
- 완료 표현은 `요구사항 대비 코드 미반영 없음`, `영향 범위 전파 누락 없음`, `운영 코드 기본 검증 성공`처럼 검증 수준을 구분해 작성한다.
- 테스트를 수행한 경우에만 `요청된 테스트 통과`를 사용한다.
