# CT 구현 문서

검증된 구현 정보를 짧고 탐색하기 쉬운 문서로 만든다.

이 문서는 형식 기준만 정한다. 무엇을 담을지, 어떤 섹션을 쓸지, 어디까지 파고들지, 문서를 몇 개로
나눌지는 대상 코드와 독자를 보고 판단한다.

## 단독 호출

사용자가 이 스킬만 호출했거나 작업 정보가 부족하면 파일을 변경하지 말고 다음 내용을 안내한다.

> 구현 문서를 새로 작성하거나, 여러 자료를 통합하거나, 기존 문서를 정리할 수 있습니다.
>
> 다음 정보를 알려주세요.
>
> - 작업 유형: 신규 작성 / 자료 통합 / 기존 문서 정리 / 현재 구현으로 갱신
> - 대상 범위
> - 참고할 문서·코드·설정 또는 디렉터리
> - 결과 파일 경로
> - 강조할 항목이 있다면 해당 항목

이미 대화나 작업공간에서 확인할 수 있으면 다시 묻지 않는다. 결과를 크게 바꾸는 정보만 질문한다.

## 작업 방식

1. 적용되는 작업공간 지침과 사용자 요청을 확인한다.
2. 대상 문서, 관련 자료와 구현 코드를 식별한다.
3. 각 자료의 역할과 정본을 판단한다.
4. 검증된 정보를 병합하고 중복을 제거한다.
5. 필요한 섹션과 표현을 선택해 작성한다.
6. 경로, 식별자, 링크, Markdown 구조와 누락 여부를 검증한다.

기존 문서를 수정할 때는 기술적 의미와 사용자 고유 표현을 보존한다. 요청 범위를 넘어 다른 문서를
일괄 정리하지 않는다.

## 자료와 정본

프로젝트에 정본 판단 기준이 있으면 그대로 따른다. 없으면 다음 순서로 판단한다.

1. 사용자가 지정한 정본
2. 실제 코드와 설정
3. 구체적이고 최신인 자료
4. 일반 자료 또는 이전 자료

충돌은 임의로 섞지 말고 정본을 선택한다. 의미 있는 차이는 문서에 짧게 남긴다. 자료 간 연결이
확인되지 않으면 추론해 추가하지 않는다.

### 코드에서 확인할 항목

아래는 자료에서 옮기지 않고 코드와 설정에서 직접 확인한다.

- 소스 구조와 파일 경로
- 클래스·메서드·필드 이름
- 진입점과 엔드포인트
- 위치 표기
- 설정 키와 기본값

자료와 코드가 다르면 코드를 적고, 무엇이 어떻게 달랐는지 보고한다.

### 문서가 여럿일 때

변경 가능성이 있는 상세 규칙과 값은 한 문서만 정본으로 둔다. 다른 문서에는 요약과 참조를 허용하되
상세 값을 복제하지 않는다. 참조에는 문서명과 그 문서가 무엇을 정하는지 한 줄로 적는다.

## 원본 처리

자료를 통합한 뒤 원본을 정리할 때 적용한다.

- 원본에만 있고 결과 문서에도 코드에도 없는 사실이 남았는지 대조한다.
- 원본을 가리키는 참조 링크를 먼저 갱신한다. 끊어질 링크를 남기지 않는다.
- 버전관리 추적 여부를 확인한다. 복구 경로가 없으면 삭제하지 않고 사용자에게 먼저 알린다.

## 섹션

다음은 기본 후보다. 내용이 있는 섹션만 쓰고 문서 성격에 맞게 순서를 조정한다.

- 문서 제목과 범위
- 목차
- 개요
- 소스 구조
- 흐름 한눈에 보기
- 처리 흐름
- 주요 코드
- 핵심 규칙
- 제한 조건
- 테스트
- 관련 문서

빈 섹션이나 형식을 맞추기 위한 섹션은 만들지 않는다. 기술적 의미를 전달하는 데 다른 섹션이
필요하면 추가한다. 저장소가 공통으로 쓰는 섹션이 있으면 그 관례를 따른다.

### 머리말

제목 아래에 한 문장 요약을 두고, 읽는 사람이 먼저 알아야 할 기준만 짧게 밝힌다.

- 정본이 무엇인지. 코드가 정본이면 위치 표기가 커밋에 따라 밀린다는 점을 함께 적는다.
- 이 문서가 다루지 않는 범위와 그것을 다루는 문서.
- 저장소 공통 규칙 문서로 넘길 내용.

### 위치 표기

`파일:라인` 또는 문맥이 분명하면 `:라인`으로 통일한다. 라인 번호는 찾아가기 위한 값이고 정본이
아니다.

## 표현

아래 표현을 우선한다. 기술적 의미를 명확하게 전달하는 데 필요하면 짧은 설명 문단, 코드 예시와
다른 Markdown 표현도 사용한다.

- 한두 문장의 요약
- 짧은 불릿 목록
- 번호가 있는 처리 단계
- 2~4열 표
- 고정폭 소스 트리
- `<details>`로 접은 상세 호출 경로
- 반드시 강조해야 하는 주의사항 인용 블록

표가 넓어지면 열을 늘리지 말고 표를 나누거나 설명을 목록으로 내린다. 표 셀 안에 `<br>`을 넣지
않는다.

처리 흐름이 여러 개면 먼저 `흐름 한눈에 보기` 표를 둔다. 각 흐름은 업무 단계가 먼저 보이게
쓴다. 상세 호출 경로가 길거나 본문 흐름을 방해할 때만 접는다. 반응형 다이어그램보다 단계 표와
고정폭 트리를 기본으로 한다.

### 처리 흐름 기본형

필요한 부분만 사용한다.

~~~~markdown
#### 흐름 이름

> **요약:** 시작 → 주요 처리 → 최종 결과

| 단계 | 처리 | 핵심 내용 |
|---:|---|---|
| **1** | 진입 | 엔드포인트 또는 이벤트 |
| **2** | 검증 | 주요 검증 조건 |
| **3** | 실행 | 핵심 처리 주체 |
| **4** | 결과 | 이동 또는 반환값 |

<details>
<summary><strong>상세 호출 경로</strong></summary>

```text
Endpoint
└─ Controller
   └─ Service
      └─ Repository 또는 외부 연동
```

</details>
~~~~

## 지면 기준

가로 A4 한 장에 들어가는 폭을 기준으로 쓴다. 가로 스크롤이나 자동 줄바꿈에 기대지 않는다.

| 대상 | 한 줄 상한 |
|---|---|
| 본문과 목록 | 120칸 |
| 표의 한 행 전체 | 120칸 |
| 코드 펜스와 고정폭 소스 트리 | 100칸 |

칸은 반각 기준이고 한글과 전각 문자는 2칸으로 센다.

- 상한을 넘을 때만 의미 단위로 나눈다. 폭을 맞추려고 내용을 줄이거나 값을 훼손하지 않는다.
- 긴 나열은 전체를 목록이나 표로 바꾸고, 넓은 표는 열을 줄이거나 나누거나 설명을 목록으로 내린다.
- URL, 파일 경로, 해시, 메서드 시그니처처럼 나누면 의미가 달라지는 원문 값은 상한을 넘겨도
  그대로 둔다.

## 문체

- 결론과 업무 흐름을 먼저 쓴다.
- 한 문장에는 하나의 중심 정보를 담는다.
- 코드, 식별자, 명령어, 로그와 경로는 원문을 유지한다.
- 요약과 상세에서 같은 설명을 반복하지 않는다.
- 짧은 문장과 명사형 표제를 쓰되 의미가 끊기지 않게 한다.

## 검증

- 문서에 적은 경로와 식별자가 자료 또는 코드에 존재하는지 확인한다.
- 파일을 옮기거나 지웠다면 참조 문서의 링크도 확인한다.
- 코드 펜스, 표, `<details>`와 상대 링크가 올바른지 확인한다.
- 한 줄 상한을 넘긴 곳과, 상한 안인데 불필요하게 나눈 곳이 없는지 확인한다.
- 자동 검증을 실행하지 않은 구간은 실행한 것처럼 표현하지 않는다.
- 문서와 구현의 차이를 발견하면 적용한 정본과 영향을 보고한다.
- 정본으로 확인할 수 없어 제외한 항목은 목록으로 보고한다. 그 자료가 유일한 기록이면 보존 여부를
  사용자에게 확인받는다.

## 필수 제한

- 확인되지 않은 사실을 만들어내지 않는다.
- 보기 좋게 만들기 위해 기술적 의미를 변경하거나 필요한 예외를 숨기지 않는다.
- 비밀값이나 마스킹되지 않은 개인정보를 기록하지 않는다.
