# Document Pair Template

## 파일명

프로젝트의 기존 문서 네이밍을 우선한다.

- 기준 문서: `.docs/plans/{feature_name}.md`
- 개발 가이드: `.docs/plans/{feature_name}_dev_guide.md`

이미 유사한 문서가 있으면 같은 접두어, 도메인명과 디렉터리를 따른다.

- 사용자 지정 디렉터리: 기존 디렉터리 또는 `/`로 끝나는 경로에는 `{feature_name}.md`와 `{feature_name}_dev_guide.md`를 둔다.
- 사용자 지정 기준 문서: 기존 파일 또는 `.md` 경로가 `_dev_guide.md`로 끝나지 않으면 해당 파일을 기준 문서로 사용하고 같은 디렉터리에 `{지정 파일의 확장자를 제외한 이름}_dev_guide.md`를 둔다.
- 사용자 지정 개발 가이드: 파일명이 `_dev_guide.md`로 끝나면 해당 파일을 개발 가이드로 사용하고 같은 디렉터리에 `_dev_guide`를 제거한 기준 문서를 둔다.
- 비 Markdown 파일: 기존 파일명이 `.md`로 끝나지 않으면 덮어쓰지 않고 사용할 `.md` 경로를 한 번 확인한다.
- 모호한 경로: 존재하지 않고 `.md` 또는 `/`로 끝나지 않으면 파일인지 디렉터리인지 한 번 확인한다.
- 후보 수집: 사용자 지정 경로가 없을 때 프로젝트 문서 규칙, `.docs/plans/`, 작업 루트와 저장소의 같은 이름 문서를 모두 찾는다.
- 후보 판정: 같은 디렉터리의 문서 쌍 또는 한쪽 문서를 하나의 후보로 센다.
- 분산 문서: 기준 문서와 개발 가이드가 서로 다른 디렉터리에 있으면 복수 후보로 처리한다.
- 후보가 하나면 같은 디렉터리에서 문서 쌍을 완성한다.
- 후보가 복수면 갱신 대상을 확인한다.
- 후보가 없으면 `.docs/plans/`를 만들고 신규 문서 쌍을 생성한다.

## 기준 문서 구성

기준 문서는 판정 기준과 응답 형태를 담는다.

권장 섹션:

- `## 문서 역할`
- `## 관련 문서`
- `## 주요 기준`
- `## 영역 구분 기준` 또는 기능에 맞는 데이터 구분 기준
- `## 최종 응답` 또는 최종 데이터 예시
- `## 필드 기준`
- `## 정렬 기준`
- `## 빈 응답 기준`
- `## 완료 기준`
- `## 이력관리`

작성 기준:

- 섹션 첫 문장은 짧은 서술형으로 쓴다.
- 기준, 대상, 예외, 조치는 개조식으로 쓴다.
- 테이블명과 컬럼명은 원문을 유지한다.
- 응답 필드는 기존 직렬화와 네이밍 컨벤션에 맞춘다.
- 요청·응답 외부 계약, 저장 모델·경계와 상태 전이 등 구현 차단 계약은 코드·테스트 근거 또는 사용자 답변으로 확정한다.
- 운영 일정, 담당자와 후속 관측 기준 등 구현 결과를 바꾸지 않는 항목만 `확인 필요`로 표시한다.
- 개발 절차, 코드 블록, 조회·저장 상세는 개발 가이드에 둔다.

## 개발 가이드 구성

개발 가이드는 구현 흐름과 상세 구현 기준을 담는다.

권장 섹션:

- `## 구현 범위`
- `## 관련 문서`
- `## 개발 진행 방향`
- `## 구현 구조`
- `## 수정 대상`
- `## 추가 대상`
- `## 네이밍 기준`
- `## 데이터 모델 추가 기준`
- `## 응답 모델 필드`
- `## 조회·저장 추가 기준`
- `## 애플리케이션 조립 절차`
- `## 저장 경계 메서드`
- `## 테스트 기준`
- `## 테스트 기대 결과`
- `## 이력관리`

작성 기준:

- 먼저 전체 개발 진행 방향을 정리한다.
- 기존 코드에 붙일 위치를 명시한다.
- 수정과 추가를 구분한다.
- 데이터 모델, 조회·저장, 애플리케이션 처리, 저장 경계와 테스트가 같은 이름과 필드 기준을 사용하게 쓴다.
- 조회·저장 필드와 저장 경계의 반환 모델을 맞춘다.
- 애플리케이션 조립 절차는 최종 응답 구조와 같은 순서로 쓴다.
- 테스트 기대 결과는 기준 문서의 정책과 일치해야 한다.
- `확인 필요`인 후속 항목을 테스트 기대 결과에서 확정값처럼 사용하지 않는다.
- 실제 변경 대상이 여러 런타임에 걸치면 런타임별 구현 구조와 수정 대상을 구분하고 런타임 사이의 전달 계약과 실패 전파를 연결한다.

## 생성 문서 이력 규칙

문서 본문은 최종본만 남긴다.

- 변경 이력은 문서 맨 끝 `## 이력관리`에만 쓴다.
- 항목 형식은 `- YYYY-MM-DD: 변경 내용 요약`으로 쓴다.
- 같은 날짜가 이미 있으면 기존 날짜 항목에 요약을 정리해 합친다.
