# Document Pair Template

## 파일명

프로젝트의 기존 문서 네이밍을 우선한다.

- 기준 문서: `{feature_name}.md`
- 개발 가이드: `{feature_name}_dev_guide.md`

이미 유사한 문서가 있으면 같은 접두어와 도메인명을 따른다.

## 기준 문서 구성

기준 문서는 판정 기준과 응답 형태를 담는다.

권장 섹션:

- `## 문서 역할`
- `## 관련 문서`
- `## 주요 기준`
- `## 영역 구분 기준` 또는 기능에 맞는 데이터 구분 기준
- `## 최종 JSON` 또는 최종 응답 예시
- `## 필드 기준`
- `## 정렬 기준`
- `## 빈 응답 기준`
- `## 완료 기준`
- `## 이력관리`

작성 기준:

- 섹션 첫 문장은 짧은 서술형으로 쓴다.
- 기준, 대상, 예외, 조치는 개조식으로 쓴다.
- 테이블명과 컬럼명은 원문을 유지한다.
- 응답 필드는 기존 코드 컨벤션에 맞는 lower camelCase로 쓴다.
- 개발 절차, 코드 블록, SQL 상세는 개발 가이드에 둔다.

## 개발 가이드 구성

개발 가이드는 구현 흐름과 상세 구현 기준을 담는다.

권장 섹션:

- `## 구현 범위`
- `## 관련 문서`
- `## 개발 진행 방향`
- `## 구현 구조`
- `## 수정 대상`
- `## 추가 대상`
- `## 네이밍 기준`
- `## VO 추가 기준`
- `## 응답 VO 필드`
- `## SQL 추가 기준`
- `## Service 조립 절차`
- `## DAO 메서드`
- `## 테스트 기준`
- `## 테스트 기대 결과`
- `## 이력관리`

작성 기준:

- 먼저 전체 개발 진행 방향을 정리한다.
- 기존 코드에 붙일 위치를 명시한다.
- 수정과 추가를 구분한다.
- VO, SQL, Service, DAO, 테스트가 같은 이름과 필드 기준을 사용하게 쓴다.
- SQL 조회 컬럼과 Row VO 필드를 맞춘다.
- Service 조립 절차는 최종 JSON 구조와 같은 순서로 쓴다.
- 테스트 기대 결과는 기준 문서의 정책과 일치해야 한다.

## 이력관리

문서 본문은 최종본만 남긴다.

- 변경 이력은 문서 맨 끝 `## 이력관리`에만 쓴다.
- 항목 형식은 `- YYYY-MM-DD: 변경 내용 요약`으로 쓴다.
- 같은 날짜가 이미 있으면 기존 날짜 항목에 요약을 정리해 합친다.
