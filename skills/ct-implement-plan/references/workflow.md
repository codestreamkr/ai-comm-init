# Workflow

## 진행 흐름

기능 설명을 개발 가능한 문서 2개로 고정한다.

1. 사용자가 준 기능 설명에서 대상 기능, 입력, 출력, 기존 연결 지점을 추출한다.
2. 저장소에서 관련 Controller, Service, DAO, Mapper, VO, DTO, 테스트, 문서를 검색한다.
3. 기존 흐름에 붙일지, 기존 파일을 확장할지, 새 파일을 추가할지 판단한다.
4. 기존 네이밍을 확인하고 새 이름이 필요하면 후보를 명확히 정한다.
5. 테이블, 컬럼, 기존 메서드, 기존 VO 이름을 실제 코드 기준으로 맞춘다.
6. 구현에 필요한 기준이 부족하면 질문을 하나씩 한다.
7. 기준 문서와 개발 가이드를 작성한다.
8. 두 문서 간 불일치, 누락, 중복을 찾아 해결한다.

## 코드 조사 기준

기존 구현에 붙일 수 있는 지점을 먼저 찾는다.

- Controller: API 진입점과 응답 래핑 방식
- Service: 기존 조립 흐름과 트랜잭션 경계
- DAO/Mapper: SQL 네임스페이스, resultType, parameterType
- VO/DTO: 응답 필드, lower camelCase, 기존 JSON 필드명
- 테스트: 기존 단위 테스트, 통합 테스트, fixture 작성 방식
- 문서: 기존 `.docs` 문서명, 섹션 순서, 이력관리 형식

## 질문 기준

바로 개발 가능한 문서를 만들 수 없으면 질문한다.

- 대상 기능이 불명확하다.
- 입력 조건이나 조회 조건이 없다.
- 출력 JSON 또는 응답 형태가 없다.
- 기준 테이블 또는 주요 데이터 출처가 없다.
- 기존 코드 연결 위치를 코드 검색으로 찾을 수 없다.
- 정책, 폴백, 빈 응답, 정렬 기준 중 구현 판단에 필요한 값이 빠졌다.

질문은 한 번에 하나만 한다.

## 작성 후 점검

문서 작성 후 불일치를 해결한다.

- 기준 문서와 개발 가이드의 규칙이 서로 다르면 한쪽을 수정한다.
- JSON 필드와 VO 필드가 다르면 맞춘다.
- SQL 조회 컬럼과 Row VO 필드가 다르면 맞춘다.
- Service 조립 절차가 JSON 구조와 다르면 맞춘다.
- 테스트 기대 결과가 기준 문서와 다르면 맞춘다.
- 같은 설명이 여러 섹션에 반복되면 한곳만 남긴다.
