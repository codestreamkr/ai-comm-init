# Workflow

## 진행 흐름

기능 설명을 개발 가능한 문서 2개로 고정한다.

1. 사용자가 준 기능 설명에서 대상 기능, 입력, 출력, 기존 연결 지점을 추출한다.
2. `stack-mapping.md`에서 실제 변경 대상이 있는 영향 런타임별 책임 매핑을 모두 선택한다.
3. 저장소에서 관련 진입점, 애플리케이션 처리, 저장 경계, 데이터 모델, 조회·저장 정의, 테스트와 문서를 검색한다.
4. 기존 흐름에 붙일지, 기존 파일을 확장할지, 새 파일을 추가할지 판단한다.
5. 기존 네이밍을 확인하고 새 이름이 필요하면 후보를 명확히 정한다.
6. 데이터 원천, 필드, 기존 메서드와 모델 이름을 실제 코드 기준으로 맞춘다.
7. 입력 검증, 오류 응답, 빈 결과, 정렬과 중복 입력 정책을 코드와 테스트에서 확인한다.
8. 확인되지 않은 정책은 구현 차단 계약과 후속 확인 가능 항목으로 분류한다.
9. 구현 차단 계약이 부족하면 질문을 하나씩 하여 확정한다.
10. 구현 결과를 바꾸지 않는 후속 확인 가능 항목만 `확인 필요`로 분리한다.
11. 기준 문서와 개발 가이드를 작성한다.
12. 두 문서 간 불일치, 누락, 중복을 찾아 해결한다.

## 코드 조사 기준

기존 구현에 붙일 수 있는 지점을 먼저 찾는다.

- 요청 진입점: API·메시지·배치 진입점과 응답 래핑 방식
- 애플리케이션 처리: 기존 조립 흐름과 트랜잭션 경계
- 저장 경계: Repository·DAO·Mapper·data-access 계층과 호출 계약
- 데이터 모델: DTO·VO·schema·type·model의 필드와 직렬화 이름
- 조회·저장 정의: SQL·Mapper XML·ORM·query builder의 원천 필드와 매핑
- 테스트: 기존 단위 테스트, 통합 테스트, fixture 작성 방식
- 문서: 기존 `.docs` 문서명, 섹션 순서, 이력관리 형식

## 질문 기준

바로 개발 가능한 문서를 만들 수 없으면 질문한다.

- 대상 기능이 불명확하다.
- 입력 조건이나 조회 조건이 없다.
- 출력 JSON 또는 응답 형태가 없다.
- 기준 테이블, 저장소 또는 주요 데이터 출처가 없다.
- 기존 코드 연결 위치를 코드 검색으로 찾을 수 없다.
- 정책, 폴백, 빈 응답, 정렬 기준 중 구현 결과를 바꾸는 값이 빠졌다.
- HTTP 상태, 오류 본문, 중복 입력 처리 등 요청·응답 외부 계약을 코드와 테스트에서 확인할 수 없다.
- 테이블·컬렉션·파일·외부 저장소, 저장 시점, 트랜잭션 경계 등 저장 모델·경계를 확정할 수 없다.
- 생성·변경·완료·실패 상태와 허용 전이, 전이 조건 또는 멱등성 기준을 확정할 수 없다.

질문은 한 번에 하나만 한다.

구현 차단 계약은 사용자 답변이나 코드·테스트 근거로 확정되기 전까지 문서 쌍을 완료하지 않는다. 운영 일정, 담당자, 배포 순서, 후속 관측 임계값처럼 구현 결과를 바꾸지 않는 항목은 `확인 필요`로 남길 수 있다.

## 기존 문서 탐색

갱신 위치는 후보를 모두 수집한 뒤 결정한다.

1. 사용자 지정 경로가 있으면 기존 디렉터리·`/` 경로와 기존 파일·`.md` 경로를 구분한다.
2. 사용자 지정 기존 파일명이 `.md`로 끝나지 않으면 덮어쓰지 말고 사용할 `.md` 경로를 한 번 확인한다.
3. 사용자 지정 파일명이 `_dev_guide.md`로 끝나면 개발 가이드로 사용하고 접미어를 제거한 기준 문서를 짝으로 정한다.
4. 그 밖의 사용자 지정 `.md` 파일은 기준 문서로 사용하고 같은 디렉터리에 `_dev_guide.md`를 붙인 개발 가이드를 짝으로 정한다.
5. 사용자 지정 경로가 없으면 프로젝트 문서 네이밍 규칙을 확인한다.
6. 프로젝트 문서 규칙, `.docs/plans/`, 작업 루트와 저장소 전체에서 기준 문서명과 개발 가이드 문서명을 모두 수집한다.
7. 같은 디렉터리의 문서 쌍 또는 한쪽 문서를 하나의 후보로 묶는다.
8. 서로 다른 디렉터리에 문서가 하나씩 흩어져 있으면 복수 후보로 판정한다.
9. 후보가 하나면 같은 디렉터리에서 문서 쌍을 완성하고, 복수면 갱신 대상을 한 번 확인하며, 없으면 `.docs/plans/`에 새 문서 쌍을 만든다.

## 작성 후 점검

문서 작성 후 불일치를 해결한다.

- 기준 문서와 개발 가이드의 규칙이 서로 다르면 한쪽을 수정한다.
- 응답 필드와 데이터 모델 필드가 다르면 맞춘다.
- 조회·저장 필드와 저장 경계의 반환 모델이 다르면 맞춘다.
- 애플리케이션 조립 절차가 응답 구조와 다르면 맞춘다.
- 테스트 기대 결과가 기준 문서와 다르면 맞춘다.
- 코드 근거가 없는 구현 차단 계약은 질문으로 확정하며 `확인 필요`로 대체하지 않는다.
- 구현 결과를 바꾸지 않는 후속 확인 항목만 `확인 필요`로 유지한다.
- 같은 설명이 여러 섹션에 반복되면 한곳만 남긴다.
