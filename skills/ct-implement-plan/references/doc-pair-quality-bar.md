# Document Pair Quality Bar

## 품질 기준

문서는 읽고 바로 개발을 시작할 수 있어야 한다.

- 기존 코드 연결 위치가 명확하다.
- 수정할 파일과 추가할 파일이 명확하다.
- 새 메서드, VO, SQL ID, 테스트명 후보가 명확하다.
- VO, SQL, Service 조립, DAO, 테스트 기준이 하나의 흐름으로 이어진다.
- 응답 JSON과 VO 필드가 맞다.
- SQL 컬럼과 Row VO 필드가 맞다.
- 폴백, 빈 응답, 정렬, 필터 기준이 두 문서에서 일치한다.
- 기준 문서는 판정 기준을 담고, 개발 가이드는 구현 기준을 담는다.
- JSON, SQL, Service 절차에 이미 드러난 기준은 별도 서술로 반복하지 않는다.

## 기준 문서 품질

기준 문서는 최종 판단 기준을 빠르게 확인하게 쓴다.

- 기능 범위와 문서 역할이 짧게 드러난다.
- 주요 기준은 실제 테이블과 컬럼명으로 쓴다.
- 최종 JSON 또는 응답 예시가 있다.
- 필드별 원천 테이블과 컬럼이 있다.
- 정렬 기준과 빈 응답 기준이 있다.
- 완료 기준은 개발 가이드에 포함되어야 할 기준을 확인하는 용도로만 쓴다.

## 개발 가이드 품질

개발 가이드는 구현자가 전체 흐름을 이해한 뒤 상세 코드로 내려가게 쓴다.

- 구현 범위가 기존 코드 연결 기준으로 정리되어 있다.
- 개발 진행 방향이 먼저 나온다.
- 수정 대상과 추가 대상이 구분되어 있다.
- VO 필드 정의가 JSON과 맞다.
- SQL 초안이 실제 테이블, 컬럼, Mapper 방식과 맞다.
- Service 조립 절차가 단계별로 구현 가능하다.
- DAO 메서드와 테스트 기준이 있다.
- 기획 목적이나 사용자 가치 설명을 넣지 않는다.

## 불합격 기준

아래 상태면 문서를 완료하지 않는다.

- 기능 설명만 다시 풀어쓴 개요 문서다.
- 기존 코드 검색 없이 일반론으로 작성했다.
- JSON은 있는데 VO 또는 SQL 매핑이 없다.
- SQL은 있는데 Service 조립 기준이 없다.
- 두 문서의 정책, 폴백, 정렬, 필터 기준이 다르다.
- 수정/추가할 파일과 네이밍이 불명확하다.
