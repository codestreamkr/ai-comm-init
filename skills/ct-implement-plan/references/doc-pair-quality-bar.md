# Document Pair Quality Bar

## 품질 기준

문서는 읽고 바로 개발을 시작할 수 있어야 한다.

- 기존 코드 연결 위치가 명확하다.
- 수정할 파일과 추가할 파일이 명확하다.
- 새 메서드, 데이터 모델, 조회·저장 식별자와 테스트명 후보가 명확하다.
- 데이터 모델, 조회·저장, 애플리케이션 조립, 저장 경계와 테스트 기준이 하나의 흐름으로 이어진다.
- 응답 필드와 직렬화 모델 필드가 맞다.
- 조회·저장 필드와 저장 경계의 반환 모델이 맞다.
- 폴백, 빈 응답, 정렬, 필터 기준이 두 문서에서 일치한다.
- 요청·응답 외부 계약, 저장 모델·경계와 상태 전이 등 구현 차단 계약은 코드·테스트 근거 또는 사용자 답변으로 확정되어 있다.
- 운영 일정, 담당자와 후속 관측 기준 등 구현 결과를 바꾸지 않는 항목만 `확인 필요`로 구분되어 있다.
- 기준 문서는 판정 기준을 담고, 개발 가이드는 구현 기준을 담는다.
- 응답 예시, 조회·저장 정의와 처리 절차에 이미 드러난 기준은 별도 서술로 반복하지 않는다.

## 기준 문서 품질

기준 문서는 최종 판단 기준을 빠르게 확인하게 쓴다.

- 기능 범위와 문서 역할이 짧게 드러난다.
- 주요 기준은 실제 데이터 원천과 필드명으로 쓴다.
- 최종 응답 또는 데이터 예시가 있다.
- 필드별 데이터 원천과 원천 필드가 있다.
- 관계형 DB가 저장 경계이면 실제 테이블과 컬럼명을 사용한다.
- 정렬 기준과 빈 응답 기준이 있다.
- 완료 기준은 개발 가이드에 포함되어야 할 기준을 확인하는 용도로만 쓴다.

## 개발 가이드 품질

개발 가이드는 구현자가 전체 흐름을 이해한 뒤 상세 코드로 내려가게 쓴다.

- 구현 범위가 기존 코드 연결 기준으로 정리되어 있다.
- 개발 진행 방향이 먼저 나온다.
- 수정 대상과 추가 대상이 구분되어 있다.
- 데이터 모델 정의가 응답 계약과 맞다.
- 조회·저장 초안이 실제 데이터 원천, 필드와 프로젝트 접근 방식에 맞다.
- 애플리케이션 조립 절차가 단계별로 구현 가능하다.
- 저장 경계 메서드와 테스트 기준이 있다.
- 실제 변경 대상이 있는 모든 variant의 최소 구체화 항목이 `stack-mapping.md` 기준으로 포함되어 있다.
- 런타임을 넘는 호출의 전달 계약, 실패 전파와 런타임별 수정 대상이 연결되어 있다.
- 기획 목적이나 사용자 가치 설명을 넣지 않는다.

## 불합격 기준

아래 상태면 문서를 완료하지 않는다.

- 기능 설명만 다시 풀어쓴 개요 문서다.
- 기존 코드 검색 없이 일반론으로 작성했다.
- 응답 계약은 있는데 데이터 모델 또는 조회·저장 매핑이 없다.
- 조회·저장 정의는 있는데 애플리케이션 조립 기준이 없다.
- 두 문서의 정책, 폴백, 정렬, 필터 기준이 다르다.
- 코드 근거 없이 HTTP 상태, 오류 본문, 빈 결과 또는 중복 입력 처리를 관례로 확정했다.
- 구현 차단 계약을 사용자에게 확인하지 않고 `확인 필요`로 남겼다.
- 실제 변경 대상이 있는 런타임의 variant 구현 기준이 빠졌다.
- 수정/추가할 파일과 네이밍이 불명확하다.
