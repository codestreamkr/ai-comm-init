# CT Implement Plan

## 목적

이 스킬은 기능 개발 전에 필요한 문서 2개를 완성한다.

- 기준 문서: 기능의 판정 기준, 응답 형태, 필드 기준, 예외 기준을 정리한다.
- 개발 가이드: 개발자가 전체 진행 방향을 먼저 이해한 뒤 데이터 모델, 조회·저장, 처리 흐름, 저장 경계와 테스트 기준으로 넘어가도록 정리한다.

## 지원 범위

기술 스택에 맞는 실제 코드 명칭으로 책임을 매핑한다.

- 공통 책임: 요청 진입점, 애플리케이션 처리, 저장 경계, 데이터 계약, 조회·저장 정의, 테스트
- 지원 variant: Java/Spring/MyBatis·JPA, Node.js/TypeScript, Python, Generic/Other
- 혼합 저장소: 실제 변경 대상이 있는 런타임별 variant를 모두 선택하고 런타임 사이의 호출과 데이터 계약을 연계 책임으로 기록한다.
- 세부 매핑: `references/stack-mapping.md`에서 실제 변경 대상에 해당하는 모든 variant를 적용한다.

## 필수 참조

문서를 작성하기 전에 아래 파일을 읽는다.

- `references/workflow.md`: 조사, 질문, 작성, 정합성 해결 흐름
- `references/stack-mapping.md`: 기술 스택 감지와 책임별 실제 코드 명칭
- `references/doc-pair-quality-bar.md`: 문서 품질 기준
- `references/doc-pair-template.md`: 기준 문서와 개발 가이드 구성

## 호출 방식

- `$ct-implement-plan 기능 설명`
- `$ct-implement-plan 주문서 결제수단 영역 개발 문서 만들어줘`

## 기본 원칙

기능 설명만으로 얕은 문서를 만들지 않는다.

- 기존 코드를 검색해 연결 위치, 수정 대상, 추가 대상을 판단한다.
- 필요한 데이터 원천, 필드, 메서드, 모델과 저장 경계 이름은 실제 코드 기준으로 맞춘다.
- 입력 허용값, 잘못된 입력, 중복 입력, 빈 결과와 오류 응답 정책은 기존 코드와 테스트에서 확인한다.
- 요청·응답 외부 계약, 저장 모델·경계, 상태 전이처럼 구현 결과를 바꾸는 계약은 코드와 테스트에서 확인되지 않으면 질문으로 확정한다.
- 구현 결과를 바꾸지 않는 운영 일정, 담당자, 후속 관측 기준은 `확인 필요`로 남길 수 있다.
- 정보가 부족하면 질문을 하나씩 한다.
- 질문 없이 진행할 수 있으면 가정을 짧게 명시하고 문서를 작성한다.
- 문서 2개를 작성한 뒤 불일치, 누락, 중복을 해결한다.

## 산출물

기본 산출물은 문서 2개다.

- `.docs/plans/{feature_name}.md`
- `.docs/plans/{feature_name}_dev_guide.md`

생성과 갱신은 기존 문서 호환성을 기준으로 결정한다.

1. 사용자 지정 경로가 기존 디렉터리이거나 `/`로 끝나면 해당 디렉터리에 `{feature_name}.md`와 `{feature_name}_dev_guide.md`를 생성하거나 갱신한다.
2. 사용자 지정 경로가 기존 파일이거나 `.md`로 끝나면 파일 경로로 판정하고 같은 디렉터리에서 문서 쌍을 완성한다.
   - 기존 파일명이 `.md`로 끝나지 않으면 덮어쓰지 말고 사용할 `.md` 파일 경로를 한 번 확인한다.
   - 파일명이 `{feature_name}_dev_guide.md`이면 지정 파일을 개발 가이드로 사용하고 `_dev_guide`를 제거한 `{feature_name}.md`를 기준 문서로 사용한다.
   - 그 밖의 `.md` 파일은 지정 파일을 기준 문서로 사용하고 같은 이름에 `_dev_guide`를 붙인 파일을 개발 가이드로 사용한다.
3. 사용자 지정 경로가 존재하지 않고 `.md` 또는 `/`로 끝나지 않으면 파일인지 디렉터리인지 한 번 확인한다.
4. 사용자 지정 경로가 없으면 프로젝트 문서 규칙에서 신규 문서의 생성 디렉터리와 네이밍 규칙을 확인한다.
5. 프로젝트 문서 규칙의 생성 경로, `.docs/plans/`, 작업 루트와 저장소에서 같은 이름의 기존 문서를 모두 수집한다.
6. 같은 디렉터리에 있는 완성된 문서 쌍 또는 한쪽 문서를 하나의 후보로 센다.
7. 두 문서가 서로 다른 디렉터리에 흩어져 있으면 복수 후보로 처리하고 임의로 이동하거나 합치지 않는다.
8. 후보가 하나면 해당 디렉터리에서 문서 쌍을 완성하고 새 경로에 중복 생성하지 않는다.
9. 후보가 복수면 갱신 대상을 한 번 확인한다.
10. 후보가 없고 프로젝트 문서 규칙이 신규 생성 경로를 정의하면 해당 경로와 네이밍 규칙으로 문서 쌍을 생성한다.
11. 후보와 신규 생성 경로 규칙이 모두 없으면 `.docs/plans/`를 만들고 신규 문서 쌍을 생성한다.

## 코드 수정 기준

이 스킬은 기본적으로 구현 문서를 만든다.

- 코드 수정은 하지 않는다.
- 기존 코드는 검색하고 읽어서 문서에 반영한다.
- 사용자가 구현까지 요청하면 별도 구현 작업으로 전환한다.

## 완료 조건

완료 전 아래를 확인한다.

- 기준 문서와 개발 가이드가 같은 규칙을 말한다.
- 응답 필드, 데이터 모델, 조회·저장 필드와 애플리케이션 조립 절차가 서로 맞는다.
- 수정할 파일과 추가할 파일이 개발 가이드에 명확하다.
- 네이밍이 기존 코드 컨벤션과 맞는다.
- 요청·응답 외부 계약, 저장 모델·경계와 상태 전이 등 구현 차단 계약이 코드·테스트 근거 또는 사용자 답변으로 확정되어 있다.
- 운영 일정, 담당자와 후속 관측 기준 등 구현 결과를 바꾸지 않는 항목만 `확인 필요`로 구분되어 있다.
- 실제 변경 대상이 여러 런타임에 걸치면 영향 런타임별 variant의 구현 기준이 모두 포함되어 있다.
- 불일치, 누락, 중복을 확인하고 문서에 반영했다.
- 기존 문서의 갱신 또는 신규 문서의 생성 경로를 결과에 보고했다.
