# CT Docs Weekly Report

Git 이력을 근거로 간결한 월별 업무 보고를 작성한다. 사용자가 여러 브랜치를 주면 합산하지 말고 브랜치마다 완전한 보고 세트를 각각 만든다.

## 도움말 호출

스킬 이름 뒤의 요청이 없거나 `?`, `help`, `도움말`, `설명`, `사용법` 중 하나뿐이면 Git 명령을 실행하지 않고 사용 예시만 보여준다. 기능 설명, 입력 항목 설명, 처리 기준은 출력하지 않는다.

다음과 같은 실행 가능한 예시를 코드 블록으로 출력한다.

```text
$ct-docs-weekly-report를 사용해서 현재 브랜치 보고서를 작성해줘.
```

```text
$ct-docs-weekly-report를 사용해서 2026-08-21~2026-09-20 기간의 아래 브랜치를 각각 작성해줘.

- branch-a
- branch-b
```

```text
$ct-docs-weekly-report로 9월 보고서를 작성해줘.
형식은 .docs/월별보고/8월보고서.md를 참고하고 branch-a와 branch-b를 각각 정리해줘.
```

도움말 호출에는 제목이나 부연 설명을 붙이지 않으며, 저장소 조회, 보고서 생성 또는 파일 수정을 수행하지 않는다.

## 입력 결정

- 작성자가 명시되지 않으면 `P268083`을 사용한다. 이름과 이메일은 대소문자를 구분하지 않는다.
- 브랜치가 없으면 현재 브랜치만 사용한다.
- 브랜치가 하나 이상이면 각 브랜치를 독립적으로 분석한다. 브랜치 사이의 커밋이나 파일 수를 합치지 않는다.
- 보고 기간이 명시되면 그대로 사용한다.
- 보고 기간과 대상 월이 모두 없으면 요청 시점의 한국 시간(`Asia/Seoul`)이 속한 달을 기준 월로 사용한다.
- 대상 월만 주어지면 그 달을 기준 월로 사용한다.
- 기준 월 1일이 포함된 월요일~일요일 구간을 기준 월 1주차로 본다.
- 기본 보고 기간은 기준 월 1주차 바로 전 월요일 00:00:00부터 기준 월 3주차 일요일 23:59:59까지다. 날짜를 고정하지 않고 기준 월의 달력에 따라 계산한다.
- 기본 보고 기간의 첫 주를 전월 마지막 주로 표기하고, 이어지는 세 주를 기준 월 1~3주차로 표기한다.
- 기존 보고서가 제공되면 제목, 대상, 기간, 주차 명칭 등 문서 형식을 따른다.

## Git 수집

기간 규칙으로 산정한 `Since`와 `Until`을 넣어 먼저 다음 스크립트를 실행한다.

```powershell
& "<skill-dir>/scripts/collect_weekly_git.ps1" `
  -Author "P268083" `
  -Since "2026-08-21T00:00:00+09:00" `
  -Until "2026-09-20T23:59:59+09:00" `
  -Branches @("branch-a", "branch-b")
```

스크립트 결과의 각 `branches` 항목이 독립된 보고 세트다.

- merge commit은 부모가 둘 이상인 커밋으로 판별해 제외한다.
- `infi merge`처럼 한 명의 작성자로 기록됐지만 타인 변경을 묶을 수 있는 통합 커밋도 기본적으로 제외한다.
- 같은 브랜치 안에서는 커밋 해시와 파일 경로를 중복 제거한다.
- 다른 브랜치에 같은 커밋이 있어도 브랜치별 결과에는 각각 포함한다.
- 브랜치를 체크아웃하거나 작업 트리를 변경하지 않는다.

스크립트가 반환한 커밋 제목만으로 의미가 불명확하면 `git show --stat <hash>`와 관련 파일의 제한된 diff를 확인한다. 실제 변경에서 확인되지 않은 업무를 추정하지 않는다.

## 주차별 업무 작성

- 기존 보고서의 주차 구분을 우선한다. 별도 기준이 없으면 월요일부터 일요일까지를 한 주로 본다.
- 같은 기능에 속하는 연속 커밋은 하나의 업무로 합친다.
- 하나의 큰 커밋에 서로 다른 기능이 있으면 확인된 기능 단위로 나눌 수 있다.
- 주차별 3~4건을 목표로 하되, 근거가 부족하면 개수를 억지로 채우지 않는다.
- 병합, 포맷 정리, 단순 파일 이동은 독립 업무로 부풀리지 않는다.
- 업무명은 구현 결과 중심의 명사형 문장으로 간결하게 작성한다.

예시:

```markdown
### 9월 2주차

- 결제 프로모션 DB 구조 변경과 응답 항목 확장
- 클라이언트별 PG 키 조회·검증 및 승인 구조 적용
- 주요 간편결제 분기와 주문·클레임 화면 처리 개선
```

## 대표 파일 산정

각 브랜치에서 보고 대상 커밋이 변경한 파일을 중복 제거해 계산한다.

- Java: `src/main/java` 아래의 `.java`만 집계한다. `src/test/java`는 기본 수치에서 제외한다.
- JSP: 경로와 관계없이 `.jsp`를 집계한다.
- 대표 파일은 해당 브랜치의 대상 커밋에서 가장 자주 변경된 파일로 정한다.
- 빈도가 같으면 보고서의 주요 작업을 가장 잘 대표하는 파일을 고른다.
- 표기는 전체 고유 파일 수에서 대표 파일 하나를 뺀 `외 N개` 형식을 사용한다.
- 해당 유형의 파일이 없으면 `해당 없음`으로 적는다.

```markdown
### Java

OrderMngApiController.java 외 35개

### JSP

ecoupon_order_mng_after.jsp 외 25개
```

테스트 파일 수는 사용자가 요구할 때만 별도로 표시한다.

## 출력 구조

브랜치가 하나면 기존 보고서 구조를 유지한다. 브랜치가 여러 개면 아래 구조를 브랜치별로 반복한다.

```markdown
## branch-a

### 주차별 업무

#### 9월 1주차

- 작업 내용

### 대표 파일

#### Java

Representative.java 외 N개

#### JSP

representative.jsp 외 N개
```

## 파일 생성

보고서는 사용자가 파일 생성을 별도로 요청하지 않아도 항상 Markdown 파일로 저장한다.

- 출력 경로를 지정하면 해당 경로를 사용한다.
- 기존 보고서를 형식 기준으로 제공하면 별도의 출력 경로가 명시되지 않은 경우 그 파일을 갱신한다.
- 그 외에는 저장소 루트의 `.docs/월별보고/YYYY-MM-업무보고.md`에 생성한다. `YYYY-MM`은 보고 기간 종료일이 속한 연월이다.
- 상위 폴더가 없으면 생성한다.
- 동일한 출력 파일이 있으면 해당 보고 기간과 브랜치의 보고 내용을 새 수집 결과로 갱신하고, 관련 없는 기존 내용은 보존한다.
- 생성 후 파일을 다시 읽어 제목, 기간, 브랜치, 주차별 업무, 대표 파일이 빠지지 않았는지 확인한다.

## 결과 보고

사용자 응답은 다음 내용만 간략히 보고하고 보고서 전문을 반복하지 않는다.

- 생성 또는 수정한 파일 경로
- 적용한 작성자, 기간, 브랜치
- 반영 커밋 수와 제외한 통합 커밋 수
- 검증하지 못한 항목이 있으면 그 사유
