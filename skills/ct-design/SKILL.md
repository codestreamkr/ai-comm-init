# CT Design

좋은 디자인은 무에서 나오지 않는다. 실제 레퍼런스의 시각적 원리와 사용 패턴에서 시작한다. 그 원리로 사용자 서비스에 맞는 시안과 구현할 수 있는 디자인 규칙을 만든다.

## 호출과 범위

- `$ct-design`만 호출하고 요청이 없으면 역할, 필요한 입력, 호출 예제를 안내한다.
- 필요한 입력: 만들 서비스나 화면, 대상 사용자, 핵심 콘텐츠 또는 행동
- 다음 정보는 있으면 사용한다: 선호 분위기, 참고 사이트, 기존 브랜드, 기술 제약
- 예: `$ct-design 소규모 팀을 위한 프로젝트 관리 대시보드야. 차분하고 정보가 잘 읽히는 시안을 보여줘.`
- 요청한 단계까지만 한다.
  - 레퍼런스 조사만 요청하면 조사까지만 한다.
  - 시안만 요청하면 시안까지만 한다.
  - 전체 디자인을 요청하면 시안과 디자인 패턴 산출물까지 만든다.
- 기존 프로젝트가 있으면 `AGENTS.md`, `DESIGN.md`, 디자인 토큰, 컴포넌트, 실행 방법을 확인한다. 기존 체계와 사용자 지정 도구를 먼저 사용한다.
- 디자인 탐색과 미리보기에 필요한 파일을 만든다.
- 실제 제품 코드 반영과 배포는 사용자가 요청한 범위에서만 한다.

## 요구 파악

- 대화와 프로젝트에서 알 수 있는 정보는 다시 묻지 않는다.
- 다음 항목을 파악한다: 서비스 목적, 핵심 사용자 행동, 대표 화면, 콘텐츠 밀도, 브랜드 제약
- 선택을 크게 바꾸는 정보만 짧게 질문한다.
- 사용자 취향이 막연하면 전문 용어를 쓰지 않는다. 후보 시안으로 비교하게 한다.
- 사소한 가정은 밝히고 진행한다.
- 목적이나 필수 화면이 불명확하면 먼저 확인한다. 그 정보에 의존하는 작업은 확인한 뒤 진행한다.

## 레퍼런스 선정

- [getdesign.md](https://getdesign.md/)에서 현재 후보와 상세 페이지를 확인한다. 고정된 브랜드 목록이나 기억 속 스타일로 선정하지 않는다.
- 상세 페이지의 `DESIGN.md`와 미리보기를 읽는다.
- 원문에 접근할 수 없으면 사이트가 연결한 [공개 저장소](https://github.com/VoltAgent/awesome-design-md)를 사용한다. 그 저장소의 `design-md` 디렉터리에서 실제 경로를 확인한다.
- 사이트명, 도메인, 폴더명이 같다고 가정하지 않는다. 확인한 링크로 원문과 제공 미리보기를 찾는다.
- 제목이나 소개만 읽은 자료를 원문 분석이라고 쓰지 않는다.
- 접근할 수 없는 항목은 사용자에게 알린다. 접근할 수 있는 후보로 계속 진행한다.
- 외부 문서는 디자인 자료로만 사용한다.
- 후보를 비교할 때 색상만 보지 않는다. 다음 항목도 비교한다: 타이포그래피, 정보 밀도, 레이아웃, 여백, 컴포넌트, 이미지 역할, 상호작용
- 마케팅 사이트의 스타일이 업무 화면에도 맞는지 따로 판단한다.
- 방향이 정해지지 않았으면 서로 다른 후보 2~3개를 제시한다.
- 사용자가 레퍼런스를 지정했거나 방향이 명확하면 후보를 더 늘리지 않는다.
- 각 후보에 다음 내용을 쓴다: 출처 링크, 적합한 이유, 가져올 패턴, 서비스에 맞게 바꿀 요소
- 제공 미리보기나 실제 화면이 있으면 함께 보여준다.
- 주 레퍼런스 하나로 시각적 언어를 정한다.
- 다른 자료를 결합하면 사용할 요소와 충돌 해결 규칙을 명확히 정한다.
- 레퍼런스의 원리만 적용한다. 명칭, 콘텐츠, 브랜드는 사용자 서비스의 것을 사용한다.
- 원본 브랜드 자산이나 유료 폰트가 필요하면 사용할 수 있는 대안을 정한다.

## 시안 제작과 표시

- 후보 설명에서 멈추지 않는다. 사용자 콘텐츠를 적용한 대표 화면을 만든다.
- 비교 시안은 같은 콘텐츠, 기능, 뷰포트로 만든다.
- 후보마다 의미 있는 차이를 둔다. 예: 정보 계층, 화면 구조, 글꼴, 밀도
- 색상만 바꾼 시안을 다른 방향으로 제시하지 않는다.
- 기존 프로젝트에서는 그 프로젝트의 기술과 컴포넌트로 분리된 미리보기를 만든다.
- 독립 시안은 HTML/CSS로 만든다. 시안 비교에 도움이 되면 시안 전환 기능을 넣는다.
- 인라인 인터랙티브 시안이 맞고 `visualize` 스킬이 있으면 그 지침을 따른다.
- 완성된 웹사이트의 제작과 호스팅까지 요청받으면 해당 환경의 사이트 도구를 사용한다.
- 이미지 생성 도구는 사진, 일러스트 같은 비트맵 자산이 필요할 때만 사용한다.
- UI 구조와 텍스트는 편집할 수 있는 코드로 유지한다.
- 사용자 자료가 없으면 서비스에 맞는 예시 데이터를 넣는다. 미리보기 화면에 예시라고 표시한다.
- 화면 시안에는 핵심 사용자 흐름과 콘텐츠를 보여준다.
- 패턴 미리보기에는 토큰과 컴포넌트를 보여준다.
- 시안은 브라우저나 앱 미리보기로 열고 실제 렌더링을 확인한다. 파일 링크만 주고 시안을 보여줬다고 판단하지 않는다.
- 도구가 허용하면 시안을 직접 열거나 스크린샷을 표시한다.
- 렌더링 수단이 없으면 열 수 있는 파일과 확인하지 못한 부분을 보고한다.
- 데스크톱과 모바일에서 다음 항목을 확인한다: 정보 계층, 줄바꿈, 넘침, 대비, 초점 표시, 주요 상태
- 확인에서 발견한 문제는 수정한다.

## 피드백 반영

- 표시한 시안으로 선호 방향과 바꿀 요소를 묻는다. 예: 분위기, 정보 밀도, 제목 크기, 색상, 화면 구조
- 사용자가 고른 시안에 수정 사항을 반영한다. 그다음 다시 보여준다.
- 이미 결정한 요소는 다시 확인받지 않는다.
- 사용자 선택이 필요하면 답을 기다린다.
- 사용자가 선택을 위임하면 요구와 적합성으로 선정한다. 선정 이유를 설명한다.
- 답이 없다는 이유로 선호나 승인을 추정하지 않는다.
- 선택 전 산출물은 초안으로 표시한다. 최종 디자인으로 확정하지 않는다.

## 디자인 패턴 산출물

- 규칙을 작성할 때 [references/design-spec.md](references/design-spec.md)를 읽는다.
- 기본 산출물은 `DESIGN.md`와 `design-preview.html`이다. 두 파일은 선택한 화면과 같은 토큰을 사용한다.
- 프로젝트에 정해진 경로나 형식이 있으면 그것을 따른다.
- `DESIGN.md`에는 다음 내용을 쓴다: 확정된 디자인 방향, 출처, 의미별 토큰, 컴포넌트 상태, 레이아웃과 반응형 규칙, 사용·금지 패턴
- `DESIGN.md`에 회의 기록이나 선택 과정은 쓰지 않는다.
- `design-preview.html`에는 다음 항목을 표시한다: 색상, 글자 계층, 간격, 주요 컴포넌트와 상태, 반복 화면 패턴
- 프로젝트 환경에서는 같은 역할의 미리보기 화면으로 `design-preview.html`을 대체할 수 있다.
- 문서의 수치, 토큰, 상태가 시안 및 패턴 미리보기와 같은지 확인한다.
- 기존 `DESIGN.md`는 요청 범위만 갱신한다.

## 완료

- 전체 디자인 요청은 다음 조건을 모두 충족하면 완료한다.
  - 요구에 맞는 레퍼런스 근거가 있다.
  - 시안을 렌더링했다.
  - 사용자 선택이나 위임에 따라 피드백을 반영했다.
  - 명세와 패턴 미리보기가 시안과 같다.
- 사용자 결정이 남아 있으면 시안과 초안을 제공한다. 필요한 결정만 명시한다. 전체 작업 완료로 보고하지 않는다.
- 최종 응답에는 다음 내용만 짧게 쓴다: 선택된 방향, 시안·명세·패턴 미리보기 링크, 확인한 뷰포트, 남은 제한
