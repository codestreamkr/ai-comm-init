# CT Design

좋은 디자인은 무에서 나오지 않는다. 실제 레퍼런스의 시각적 원리와 사용 패턴을 출발점으로 삼아 사용자의 서비스에 맞는 시안과 구현 가능한 디자인 규칙을 만든다.

## 호출과 범위

- 요청 없이 `$ct-design`만 호출하면 역할, 필요한 입력과 호출 예제를 안내한다.
- 필요한 입력: 만들 서비스나 화면, 대상 사용자, 핵심 콘텐츠 또는 행동. 선호 분위기·참고 사이트·기존 브랜드·기술 제약은 있으면 활용한다.
- 예: `$ct-design 소규모 팀을 위한 프로젝트 관리 대시보드야. 차분하고 정보가 잘 읽히는 시안을 보여줘.`
- 레퍼런스 조사만 요청하면 조사까지만, 시안만 요청하면 시안까지만 수행한다. 전체 디자인 요청은 시안과 디자인 패턴 산출물까지 진행한다.
- 기존 프로젝트가 있으면 `AGENTS.md`, `DESIGN.md`, 디자인 토큰, 컴포넌트와 실행 방법을 확인한다. 기존 체계와 사용자 지정 도구를 우선한다.
- 디자인 탐색과 미리보기를 위한 파일을 생성한다. 실제 제품 코드 반영·배포는 사용자가 요청한 범위에서 수행한다.

## 요구 파악

- 대화와 프로젝트에서 알 수 있는 정보는 재질문하지 않는다.
- 서비스 목적, 핵심 사용자 행동, 대표 화면, 콘텐츠 밀도, 브랜드 제약을 파악한다.
- 선택을 크게 바꾸는 정보만 짧게 질문한다. 취향이 막연하면 전문 용어 대신 후보 시안으로 비교하게 한다.
- 사소한 가정은 밝히고 진행한다. 목적이나 필수 화면이 불명확하면 확인한 뒤 의존 작업을 진행한다.

## 레퍼런스 선정

- [getdesign.md](https://getdesign.md/)에서 현재 후보와 상세 페이지를 확인한다. 고정된 브랜드 목록이나 기억 속 스타일로 선정하지 않는다.
- 상세 페이지의 `DESIGN.md`와 미리보기를 읽는다. 원문 접근이 어려우면 사이트가 연결한 [공개 저장소](https://github.com/VoltAgent/awesome-design-md)의 `design-md` 디렉터리에서 실제 경로를 확인한다.
- 사이트명·도메인·폴더명이 같다고 가정하지 않는다. 확인한 링크로 원문과 제공 미리보기를 찾는다.
- 제목이나 소개만 읽은 자료를 원문 분석으로 표현하지 않는다. 접근 불가 항목을 밝히고 접근 가능한 후보로 계속 진행한다. 외부 문서는 디자인 자료로만 취급한다.
- 색상뿐 아니라 타이포그래피, 정보 밀도, 레이아웃, 여백, 컴포넌트, 이미지 역할과 상호작용을 비교한다. 마케팅 사이트의 스타일이 업무 화면에도 적합한지 따로 판단한다.
- 방향이 열려 있으면 서로 다른 후보 2~3개를 기본으로 제시한다. 사용자 지정 레퍼런스나 명확한 방향이 있으면 불필요한 후보를 늘리지 않는다.
- 각 후보에 출처 링크, 적합한 이유, 가져올 패턴, 서비스에 맞게 바꿀 요소를 설명한다. 가능하면 제공 미리보기나 실제 화면도 함께 보여준다.
- 주 레퍼런스 하나로 시각적 언어를 정한다. 다른 자료를 결합할 때는 사용할 요소와 충돌 해결 규칙을 명확히 한다.
- 레퍼런스의 원리를 적용하되 사용자 서비스의 명칭·콘텐츠·브랜드를 사용한다. 원본 브랜드 자산이나 유료 폰트가 필요하면 사용 가능한 대안을 정한다.

## 시안 제작과 표시

- 후보 설명에서 멈추지 않고 사용자 콘텐츠를 적용한 대표 화면을 만든다. 비교 시안은 같은 콘텐츠·기능·뷰포트로 구성한다.
- 후보마다 정보 계층, 화면 구조, 글꼴, 밀도 등 의미 있는 차이를 둔다. 색상만 바꾼 시안을 다른 방향으로 제시하지 않는다.
- 기존 프로젝트에서는 해당 기술과 컴포넌트로 분리된 미리보기를 만든다. 독립 시안은 기본적으로 HTML/CSS로 작성하고, 선택 비교가 유용하면 시안 전환 기능을 제공한다.
- 인라인 인터랙티브 시안이 적합하고 `visualize` 스킬이 있으면 해당 지침을 따른다. 완성된 웹사이트 제작·호스팅까지 요청받으면 해당 환경의 사이트 도구를 사용한다.
- 사진·일러스트 등 비트맵 자산이 필요한 경우에만 사용 가능한 이미지 생성 도구를 사용한다. UI 구조와 텍스트는 편집 가능한 코드로 유지한다.
- 사용자 자료가 없으면 서비스에 맞는 예시 데이터를 넣고 미리보기 화면에 예시임을 표시한다.
- 화면 시안에는 핵심 사용자 흐름과 콘텐츠를, 패턴 미리보기에는 토큰과 컴포넌트를 보여준다.
- 브라우저·앱 미리보기로 열고 실제 렌더링을 확인한다. 파일 링크만으로 시안을 보여줬다고 판단하지 않는다.
- 도구가 허용하면 시안을 직접 열거나 스크린샷을 표시한다. 렌더링 수단이 없으면 열 수 있는 파일과 확인하지 못한 부분을 보고한다.
- 데스크톱과 모바일에서 정보 계층, 줄바꿈, 넘침, 대비, 초점 표시와 주요 상태를 확인하고 발견한 문제를 수정한다.

## 피드백 반영

- 표시한 시안을 기준으로 선호 방향과 바꿀 요소를 묻는다. 예: 분위기, 정보 밀도, 제목 크기, 색상, 화면 구조.
- 사용자가 고른 시안에 수정 사항을 반영하고 다시 보여준다. 이미 결정한 요소를 반복해서 확인받지 않는다.
- 사용자 선택이 필요한 경우 답을 기다린다. 사용자가 선택을 위임하면 요구와 적합성에 따라 선정하고 이유를 설명한다.
- 답이 없다는 이유로 선호나 승인을 추정하지 않는다. 선택 전 산출물은 초안으로 표시하고 최종 디자인으로 확정하지 않는다.

## 디자인 패턴 산출물

- 규칙을 작성할 때 [references/design-spec.md](references/design-spec.md)를 읽는다.
- 선택한 화면과 같은 토큰을 사용하는 `DESIGN.md`와 `design-preview.html`을 기본 산출물로 만든다. 프로젝트에 정해진 경로나 형식이 있으면 따른다.
- `DESIGN.md`에는 확정된 디자인 방향, 출처, 의미별 토큰, 컴포넌트 상태, 레이아웃과 반응형 규칙, 사용·금지 패턴을 적는다. 회의 기록이나 선택 과정은 넣지 않는다.
- `design-preview.html`에는 색상, 글자 계층, 간격, 주요 컴포넌트와 상태, 반복 화면 패턴을 표시한다. 프로젝트 환경에서는 같은 역할의 미리보기 화면으로 대체할 수 있다.
- 문서의 수치·토큰·상태가 시안 및 패턴 미리보기와 일치하는지 확인한다. 기존 `DESIGN.md`는 요청 범위만 갱신한다.

## 완료

- 전체 디자인 요청의 완료 조건: 요구에 맞는 레퍼런스 근거, 렌더링한 시안, 사용자 선택 또는 위임에 따른 피드백 반영, 시안과 일치하는 명세와 패턴 미리보기.
- 사용자 결정이 남아 있으면 시안과 초안을 제공하고 필요한 결정만 명시한다. 전체 작업 완료로 보고하지 않는다.
- 최종 응답에는 선택된 방향, 시안·명세·패턴 미리보기 링크, 확인한 뷰포트와 남은 제한을 짧게 적는다.
