# 전환 계획 작성 기준

이 문서는 현재 구조 판단, 목표 구조, 책임 분리와 계약 유지 기준을 정한다.

## 구성

- 현재·목표 CallTree와 구조 판단
- 전환 기준과 입출력 전파
- 기존 유지·신규 제안과 변경 효과
- 서비스 책임과 메서드 매핑
- 실패·보상, 응답, 검증과 로그

## CallTree

- 루트는 사용자가 지정한 메서드다.
- depth 1은 루트가 직접 호출하는 의미 있는 메서드다.
- depth 2는 depth 1이 직접 호출하는 의미 있는 메서드다.
- 별도 노드 허용 유형: Service, DAO/Mapper, 외부 API, 메시지, 결제, 재고, 파일, 알림, DB 쓰기, 상태 변경, 보상, 후처리
- getter/setter, 단순 컬렉션 조작, DTO 필드 설정은 부모 노드 설명에 필요한 경우만 요약한다.
- 2depth 밖의 세부 흐름은 구조 판단이나 서비스 책임에서 요약한다.

## 현재 구조 판단

문제와 코드 근거를 한 단위로 작성한다.

```markdown
- 문제점: {판단}
  - 근거
    - {CallTree와 메서드에서 확인한 사실}
```

작은 기능마다 섹션을 만들지 않고 책임 집중, 저장 경계, 외부 호출, 실패 처리, 응답 조립처럼 결정에 필요한 문제로 묶는다.

## 목표 구조

- 흐름 제어와 실패 기준 조율이 필요하면 Facade 책임으로 둔다.
- 기존 DTO, List, Map, JSON 입력을 기본값으로 유지한다.
- 신규 command, request, assembler는 입력 계약 분리 근거가 확인된 경우 제안한다.
- DB 저장, 외부 호출, 결과 반영, 후처리는 각각 확인된 트랜잭션 경계를 사용한다.
- 외부 호출과 내부 저장·상태 반영의 책임을 분리한다.
- 기존 Service, DAO, 외부 연동 모듈은 이름을 유지하고 목표 서비스에서 사용한다.

## 전환 기준

- 기존 처리 순서와 실패 기준을 유지한다.
- 기존 메서드명과 입출력 계약을 우선 유지한다.
- 기본 전환에서는 기존 메서드를 분해하거나 병합하지 않는다.
- 진입점의 인라인 로직은 같은 순서와 실패 기준으로 목표 서비스에 이관한다.
- 내부 메서드 분해·병합은 회귀 테스트를 확보한 뒤 후속 과제로만 제안한다. 기본 전환의 목표 CallTree와 현재 메서드 매핑에는 반영하지 않는다.
- 승인·반영·보상 분리는 현재 코드의 독립 경계와 실패 계약이 확인된 범위에서 제안한다.

## 입력과 출력 전파

사용자가 입출력 요구를 주면 먼저 기존 계약 유지와 목표 계약 변경으로 구분한다.

적용 우선순위는 아래와 같다.

1. 사용자가 명시한 목표 계약 변경
2. 변경 요청이 없는 기존 처리 순서, 실패 기준과 입출력 계약
3. 코드 근거가 부족한 항목의 `확인 필요` 분리

- 기존 계약 유지: 현재 필드, 타입, 응답 코드와 처리 순서를 그대로 보존한다.
- 목표 계약 변경: 사용자가 요청한 신규·변경 계약을 우선 적용하고 기존 계약과 달라지는 지점, 영향 범위와 확인 필요 항목을 함께 기록한다.
- 변경 요구가 기존 코드와 충돌해 확정할 수 없으면 임의로 유지 계약으로 되돌리지 않고 `확인 필요`로 분리한다.

| 계약 | 반영 섹션 |
|---|---|
| 입력 DTO, List, Map, JSON | 목표 CallTree, 전환 기준, 현재 메서드 매핑 |
| 응답 DTO와 JSON | 목표 CallTree, 응답 유지 기준 |
| 응답 코드와 메시지 | 실패·보상 처리 기준, 응답 유지 기준 |
| 외부 상태 코드 | 서비스 책임, 응답 유지 기준 |
| 처리 순서 | 전체 흐름 기준, 목표 CallTree, 메서드 매핑 |

기존 계약은 코드에서 확인한 필드와 타입을 그대로 기록한다. 사용자가 확정하지 않은 신규 계약 후보는 `목표 후보`로 표시한다.

## 기존 유지와 신규 제안

기존 코드에서 확인한 사실과 목표 후보를 구분한다.

- 기존 유지: 입력 객체, 응답 구조, 응답 코드, 외부 상태 코드, 실패·후처리 정책
- 신규 제안: 서비스 경계, 목표 CallTree, 처리 단계값, 로그 패턴, 메서드 매핑

목표 서비스명과 메서드명은 후보임을 표시한다. 현재 코드 근거처럼 쓰지 않는다.

## 변경 효과

각 효과는 하나 이상의 근거와 연결한다.

| 효과 유형 | 연결 근거 |
|---|---|
| 책임 집중 완화 | 현재 구조 판단의 문제점과 목표 서비스 경계 |
| 변경 영향 축소 | 유지한 입력·응답·상태 계약 |
| 실패 격리 | 외부 호출과 내부 반영의 경계 |
| 회귀 위험 축소 | 유지한 처리 순서와 기존 메서드 |
| 운영 추적 향상 | 처리 단계값과 로그 식별자 |

효과 항목에는 근거가 되는 현재 노드, 문제점 또는 목표 서비스를 함께 적는다.

## 서비스 책임

서비스 책임은 표로 작성한다.

| 서비스 | 책임 | 출력 |
|---|---|---|
| `TargetFacadeService` | 처리 순서와 실패 기준 제어 | 처리 결과 |
| `TargetValidationService` | 저장 전 검증 | 검증 결과 |

서비스명은 벤더나 구현 기술보다 업무 도메인을 우선한다.

## 현재 메서드 매핑

현재 코드와 목표 책임을 연결한다.

표 앞에는 아래 용어를 정의한다.

- 목표 서비스: 신규 생성 대상 서비스
- 기준 메서드: 기존 메서드명을 유지한 채 이관하거나 목표 서비스 내부에서 호출할 대상
- 인라인 로직: 기존 순서와 실패 기준을 유지한 채 목표 서비스로 이동할 대상

| 기존 위치 | 목표 서비스 | 기준 메서드 또는 로직 |
|---|---|---|
| `{rootMethod}` 입력 조립 구간 | `TargetFacadeService` | 기존 입력 조립 순서 유지 |

현재 메서드명은 실제 코드 이름을 사용한다.

## 실패와 보상

현재 코드에서 확인한 항목을 아래 형식으로 작성한다.

| 실패 지점 | 실행 조건 | 보상·저장 | 응답 | 운영 확인 |
|---|---|---|---|---|
| `{step}` | `{exception-or-result}` | `{compensation-or-integrity-action}` | `{response-contract}` | `{log-or-manual-action}` |

허용 항목:

- 예외 유형별 응답
- 보상 호출 조건
- 무결성 등록·삭제 조건
- 외부 성공 후 내부 반영 실패 처리
- 운영 확인이 필요한 실패 지점

코드 근거가 부족한 셀은 `확인 필요`로 기록한다.
응답, 상태 코드와 보상 정책의 존재 여부 또는 유지 여부를 코드에서 확정할 수 없으면 근거가 없는 내용을 만들지 않고 해당 항목을 `확인 필요`로 판정한다. 이 판정은 근거 부재를 확인한 결과이며 전환 계획의 완료를 막지 않는다.

## 응답 유지

- 성공 응답 구조
- 조건부 경고 응답
- 실패 응답 코드와 메시지
- 외부 노출 상태 코드
- 후처리 실패 시 응답과 저장·로그 기준

변경 요구가 없는 항목은 `기존 계약 유지`로 작성한다.

## 검증과 로그

- 상세 테스트케이스는 사용자가 요청한 경우 별도 문서로 분리한다.
- 프로젝트 로그 규칙이 있으면 해당 형식을 따른다.
- 로그 형식의 fallback은 기존 코드에서 확인한 식별자와 태그 패턴이다.
- 처리 단계값은 `RECEIVED`, `VALIDATED`, `EXTERNAL_REQUESTED`, `EXTERNAL_SUCCEEDED`, `INTERNAL_APPLIED`, `COMPENSATED`, `COMPLETED`, `FAILED` 중 실제 흐름에 해당하는 값만 선택한다.
- 로그 항목은 컴포넌트, 태그, 업무 식별자, 단계값, 결과 요약에서 선택한다.
- 민감정보 기준은 프로젝트 규칙 또는 기존 마스킹 코드로 확정하며, 미확정 상태는 `확인 필요`로 기록한다.

## 필수 차단

- 현재 코드 근거가 없는 응답, 상태 전이, 보상 정책의 확정
- 회귀 테스트 없이 기존 메서드의 분해·병합을 기본 전환 범위에 포함
- 외부 승인부터 내부 반영까지 전체 흐름을 근거 없이 하나의 트랜잭션으로 결합
- 민감정보와 전체 요청 객체의 로그 출력
